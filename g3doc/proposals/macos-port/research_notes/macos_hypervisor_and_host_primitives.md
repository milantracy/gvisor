# macOS kernel/user-space primitives for a gVisor-style sandbox platform (as of late 2026)

Scope: what macOS (11 through 26 "Tahoe") offers for (a) running untrusted code in a separate address space and intercepting its syscalls/page faults, and (b) host primitives for memory, signals and event notification. Each section ends with an assessment of which gVisor platform model (KVM-like, ptrace-like, systrap/seccomp-like) the mechanism maps to.

Version legend used below: [11] macOS 11 Big Sur, [12.1], [13], [15], [26] = first macOS version in which the API is available, per Apple's reference pages.

---

## Key question 1: Hypervisor.framework (HVF) on Apple Silicon (arm64): API surface, constraints, pitfalls

### Takeaway
HVF on Apple Silicon is a thin, KVM-shaped userspace API (one VM per process, one vCPU per pthread, `hv_vm_map` as the memory-slot primitive, `hv_vcpu_run` returning a raw ESR_EL2 syndrome). The guest runs at EL1/EL0 (EL2 for the guest only with the macOS 15+/M3+ nested-virt option). The hard constraints an engineer must design around are: 16 KB host page size (hence 16 KB `hv_vm_map` alignment unless the macOS 26 4 KB IPA-granule option is used), strict vCPU thread affinity, no in-kernel PSCI/WFI/timer handling, and no ioeventfd/irqfd/dirty-log equivalents.

### Cited Findings

**Framework model and requirements**
- Apple: "There can only be one virtual machine at a time per process; the virtual machine creates it with `hv_vm_create(_:)`." "Virtual CPUs (vCPUs) in a virtual machine map to POSIX threads. Create a new vCPU for the current thread with `hv_vcpu_create(_:_:_:)`." "Access to memory outside the mapped range causes `hv_vcpu_run(_:)` to exit." — [Apple Hypervisor overview](https://developer.apple.com/documentation/hypervisor)
- Apple: "Hypervisor abstracts virtual machines as processes, and virtual processors as threads." Runtime availability is checked with `sysctl kern.hv_support`. Apple Silicon requires the Virtualization Extensions; Intel requires VT-x with EPT and Unrestricted Mode. — [Apple Hypervisor overview](https://developer.apple.com/documentation/hypervisor)
- Apple's Apple Silicon index lists: `hv_vm_config_create` / `hv_vm_create(hv_vm_config_t?)` / `hv_vm_destroy`; vtimer functions `hv_vcpu_get/set_vtimer_mask`, `hv_vcpu_get/set_vtimer_offset`; nested-virt `hv_vm_config_get_el2_supported`, `hv_vm_config_get_el2_enabled`, `hv_vm_config_set_el2_enabled`; GIC functions and registers. — [Apple Silicon topic page](https://developer.apple.com/documentation/hypervisor/apple-silicon)
- Newer additions on the framework index (macOS 26 era): `hv_vm_config_get_default_ipa_granule`, `hv_vm_config_get_ipa_granule`, `hv_vm_config_set_ipa_granule`, `HV_IPA_GRANULE_4KB`, `HV_IPA_GRANULE_16KB`, `hv_vcpu_invalidate_tlb(hv_vcpu_t, hv_tlbi_op_t, UInt64)` with `HV_TLBI_OP_*` ops (VMALLE1IS, VAE1IS, ASIDE1IS, RVAE1IS...; ERRATUM: the Apple reference page lists its availability as macOS 27.0+, not 26), `hv_vcpu_get/set_serror`, `hv_vcpu_get_wait_for_interrupt_time`, feature regs `ID_AA64ISAR2/MMFR3/MMFR4/PFR2`. — [Apple Hypervisor overview](https://developer.apple.com/documentation/hypervisor)

**Memory mapping (`hv_vm_map`, `hv_vm_unmap`, `hv_vm_protect`, `hv_vm_allocate`)**
- `hv_vm_map(addr, ipa, size, flags)` [11]: "`addr`: The address in the current process. It must be page-aligned." "`ipa`: ... It must be page-aligned." "`size`: ... It must be a multiple of the page size." Discussion: "The host memory must encompass a single VM region, typically allocated with `mmap` or `mach_vm_allocate` instead of `malloc`." — [Apple hv_vm_map](https://developer.apple.com/documentation/hypervisor/hv_vm_map(_:_:_:_:))
- `hv_vm_protect(ipa, size, flags)` [11]: ipa page-aligned, size multiple of page size; "Modifies the permissions of a region in the guest physical address space of the VM." Apple's memory-management page: "Modify the guest's access permissions over the entire region or subregions with `hv_vm_protect`." — [Apple hv_vm_protect](https://developer.apple.com/documentation/hypervisor/hv_vm_protect(_:_:_:)); [Apple memory management](https://developer.apple.com/documentation/hypervisor/memory-management)
- `hv_vm_allocate(uvap, size, flags)` is available from macOS 12.1 (page has no prose). — [Apple hv_vm_allocate](https://developer.apple.com/documentation/hypervisor/hv_vm_allocate(_:_:_:))
- Memory flags are `HV_MEMORY_READ`, `HV_MEMORY_WRITE`, `HV_MEMORY_EXEC` (third-party binding index). — [docs.rs hypervisor ffi](https://docs.rs/crate/hypervisor/latest/source/src/ffi.rs)
- Page-size constant in Apple Silicon bindings: `pub const PAGE_SIZE: usize = 0x4000;` (16 KiB). — [applevisor-sys lib.rs](https://docs.rs/applevisor-sys/latest/aarch64-unknown-linux-gnu/src/applevisor_sys/lib.rs.html)
- Third-party mapper comment: all `hv_vm_map` sizes and guest addresses must be multiples of the 16 KB granule. — [supermachine dax_mapper.rs](https://docs.rs/crate/supermachine/latest/source/src/hvf/dax_mapper.rs)
- QEMU developers: "macOS ARM64 requires 16KB alignment for hv_vm_map(), but the guest kernel uses 4KB pages"; HVF "will not call hv_vm_map() for misaligned regions and that causes Data Abort" which QEMU then emulates. — [QEMU patch series (March 2026)](https://patchew.org/QEMU/20260309214906.92578-1-lucaaamaral@gmail.com); [qemu-devel thread](https://go.mail-archive.com/qemu-devel@nongnu.org/msg1155957.html)
- macOS 26 fix: `hv_vm_config_set_ipa_granule(config, granule)` [26] "Set the intermediate physical address granule size in virtual machine configuration." — [Apple hv_vm_config_set_ipa_granule](https://developer.apple.com/documentation/hypervisor/hv_vm_config_set_ipa_granule(_:_:))
- QEMU patch commit message: "On ARM64, Apple Silicon supports stage-2 translation with 4KB page granules regardless of the host OS"; adds an `ipa-granule` property (auto/4k/16k), falls back to the host page size (16 KB) on macOS < 26. — [QEMU v4 patch 2/3](https://patchew.org/QEMU/20260317175744.32469-1-lucaaamaral@gmail.com/20260317175744.32469-3-lucaaamaral@gmail.com)
- Hyperlight's macOS backend requires macOS 26 for the 4 KiB IPA granule (raises `IpaGranuleUnsupported` otherwise) and notes "guard pages are sized to the host page size, 16 KiB on Apple silicon." — [hyperlight PR #1681](https://github.com/hyperlight-dev/hyperlight/pull/1681)
- `hv_vm_config_set_ipa_size(config, ipa_bit_length)` [13] exists (page has no prose). QEMU comments: "We clamp any IPA size we want to back the VM with to a valid PARange value." — [Apple hv_vm_config_set_ipa_size](https://developer.apple.com/documentation/hypervisor/hv_vm_config_set_ipa_size(_:_:)); [QEMU target/arm/hvf/hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)
- File-backed mappings: a third-party DAX mapper passes `mmap(MAP_SHARED)` file-backed memory to `hv_vm_map` for writable mappings and `MAP_PRIVATE` for read-only ones, noting that `hv_vm_map` "still requires a writable host VA on Apple Silicon" (third-party comment, not Apple documentation). — [arcbox-vmm dax.rs](https://docs.rs/crate/arcbox-vmm/latest/source/src/dax.rs)
- Memory accounting pitfall (macOS 27.0.1 beta build 26A434 / M5 per the poster): `hv_vm_map` of `mmap(MAP_PRIVATE|MAP_ANON)`, `mmap(MAP_SHARED|MAP_ANON)`, `mach_vm_allocate`, and a `mach_make_memory_entry_64(MAP_MEM_NAMED_CREATE)` object all succeeded, but pages written by both host and guest were counted twice in `phys_footprint` (2 GB -> 4099 MB). Apple engineer (Benjamin Poulain) replied that `hv_vm_allocate()` creates regions that are not counted per mapping; the poster confirmed this fixed it. — [Apple Developer Forums thread 851651](https://developer.apple.com/forums/thread/851651)
- Dirty tracking: no `KVM_GET_DIRTY_LOG` equivalent; QEMU and libkrun implement dirty logging via `hv_vm_protect` write-faults (re-enable write on the faulting page, mark dirty, resume without advancing PC). A 2021 QEMU fix found that omitting `HV_MEMORY_EXEC` during dirty logging caused instruction faults on Apple Silicon. — [QEMU hvf dirty-tracking patch](https://patchew.org/QEMU/20220302130417.18551-1-ubzeme@gmail.com/20220302130417.18551-6-ubzeme@gmail.com); [patchwork 2021](https://patchwork.kernel.org/comment/24452327); [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)

**vCPUs, thread affinity, limits**
- `hv_vcpu_create(vcpu, exit, config)` [11] "Creates a vCPU instance for the current thread." `exit` is "The pointer to the vCPU exit information. The function `hv_vcpu_run(_:)` updates this structure on return." — [Apple hv_vcpu_create](https://developer.apple.com/documentation/hypervisor/hv_vcpu_create(_:_:_:))
- Apple: "Call functions that operate on the vCPU from the same thread with the exception of `hv_vcpus_exit(_:_:)`." "Warning: Don't use vCPUs on dispatch queues, because work from a single queue can run on different threads." — [Apple vCPU Management](https://developer.apple.com/documentation/hypervisor/vcpu-management)
- `hv_vcpu_run(vcpu)` [11]: "Call blocks until the next exit of the vCPU. The owning thread must call this function." — [Apple hv_vcpu_run](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run(_:))
- `hv_vcpus_exit(vcpus, count)` [11]: "Forces an immediate exit of a set of vCPUs of the VM." (callable from another thread per the vCPU Management page). QEMU's kick: `cpus_kick_thread(cpu); hv_vcpus_exit(&cpu->accel->fd, 1)`. — [Apple hv_vcpus_exit](https://developer.apple.com/documentation/hypervisor/hv_vcpus_exit(_:_:)); [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)
- `hv_vm_get_max_vcpu_count(&n)` [11] "Returns the maximum number of vCPUs that the hypervisor supports." No number is documented. — [Apple hv_vm_get_max_vcpu_count](https://developer.apple.com/documentation/hypervisor/hv_vm_get_max_vcpu_count(_:))
- Register access: `hv_vcpu_get/set_reg(hv_reg_t)`, `hv_vcpu_get/set_simd_fp_reg`, `hv_vcpu_get/set_sys_reg(hv_sys_reg_t)`, `hv_vcpu_get/set_pending_interrupt(hv_interrupt_type_t)`, `hv_vcpu_get_exec_time`, `hv_vcpu_set_trap_debug_exceptions`, `hv_vcpu_set_trap_debug_reg_accesses`, `hv_vcpu_config_get_feature_reg`, `hv_vcpu_config_get_ccsidr_el1_sys_reg_values`. — [Apple vCPU Management](https://developer.apple.com/documentation/hypervisor/vcpu-management)
- `hv_vcpu_set_pending_interrupt(vcpu, type, pending)` [11]: "Important: This function must be called by the owning thread." QEMU calls it with `HV_INTERRUPT_TYPE_IRQ`/`FIQ` before each `hv_vcpu_run`. — [Apple hv_vcpu_set_pending_interrupt](https://developer.apple.com/documentation/hypervisor/hv_vcpu_set_pending_interrupt(_:_:_:)); [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)
- No reset state: Apple engineer on the forums: HVF "generally does not provide a reset state for vCPUs"; the caller programs every system register; the current EL is set through `HV_REG_CPSR` (PSTATE, same format as `SPSR_ELx`, M field). — [Apple forums thread 775546](https://developer.apple.com/forums/thread/775546)

**Exits and syndrome decoding**
- `hv_vcpu_exit_exception_t` fields: `syndrome: hv_exception_syndrome_t` ("The vCPU exception syndrome causing the exception"), `virtual_address: hv_exception_address_t`, `physical_address: hv_ipa_t` ("The intermediate physical address of the exception"). Exit descriptor `hv_vcpu_exit_t` and `hv_exit_reason_t`. — [Apple hv_vcpu_exit_exception_t](https://developer.apple.com/documentation/hypervisor/hv_vcpu_exit_exception_t); [Apple Exits](https://developer.apple.com/documentation/hypervisor/exits)
- Exit reasons used by QEMU/libkrun: `HV_EXIT_REASON_CANCELED` (kicked), `HV_EXIT_REASON_EXCEPTION` (EC = `(syndrome >> 26) & 0x3f`), `HV_EXIT_REASON_VTIMER_ACTIVATED`; QEMU `g_assert_not_reached()` on anything else. — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c); [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- EC classes handled by QEMU: `EC_DATAABORT` (MMIO; asserts on `s1ptw` and `!isv`, advances PC by 4), `EC_SYSTEMREGISTERTRAP` (injects `EXCP_UDEF` when unhandled), `EC_WFX_TRAP` (WFI halts, WFE does not), `EC_AA64_HVC` and `EC_AA64_SMC` (PSCI; "SMC advances PC; HVC does not"), `EC_BREAKPOINT`, `EC_WATCHPOINT`, `EC_AA64_BKPT`, `EC_SOFTWARESTEP`, `EC_INSNABORT` (traced then error). — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)
- libkrun decodes data aborts from ISS: `isv` bit 24, `iswrite` bit 6, `sas` bits 23:22, `srt` bits 20:16 (31 = xzr); faulting IPA from `exception.physical_address`. Pitfall: "HVF cannot finish a read inside the handler. libkrun stores the pending read and advances the PC on the next run() entry." — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- HVC pitfall for a syscall-trap design: Carrick's guest EL1 vector originally forwarded syscalls via `hvc #0`, "but Hypervisor.framework silently consumed some of those calls as SMCCC when x0 looked like a function ID. Switching to `hvc #2` fixed it." — [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)
- QEMU dispatches HVC/SMC to PSCI only when the PSCI conduit matches; unknown SMCCC calls return -1. In-kernel PSCI does not exist; userspace must act as PSCI firmware. — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c); [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)

**Timers and interrupts**
- Apple: "On an Apple Silicon, if the exit is of type `HV_EXIT_REASON_VTIMER_ACTIVATED`, the VTimer is automatically masked. As a result, no timer fires until the timer is unmasked with `hv_vcpu_set_vtimer_mask(_:_:)`." — [Apple hv_vcpu_run](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run(_:))
- QEMU: vtimer value is `mach_absolute_time() - vtimer_offset` (set with `hv_vcpu_set_vtimer_offset`); "HVF only delivers HV_EXIT_REASON_VTIMER_ACTIVATED during hv_vcpu_run()", so QEMU uses a host timer to wake WFI-halted vCPUs. — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)
- libkrun's WFI handling: read `CNTV_CTL_EL0`/`CNTV_CVAL_EL0`, compare with `mach_absolute_time()`, park the thread; device IRQs wake it; vtimer mask "must be synced on each exit". — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- GICv3 [15]: `hv_gic_create(hv_gic_config_t)` "creates a GICv3 device for a VM"; only one per VM; must be called after VM creation and before any vCPU is created; vCPUs must set `MPIDR_EL1` affinity before the topology is final. Also `hv_gic_config_set_distributor_base/redistributor_base/msi_region_base/msi_interrupt_range`, `hv_gic_set_spi(intid, level)`, `hv_gic_send_msi(ipa, intid)`, `hv_gic_get_*_size/alignment`, `hv_gic_get_spi_interrupt_range`, `hv_gic_state_create/get_size/get_data` and `hv_gic_set_state` (save/restore), and `hv_gic_get/set_{distributor,redistributor,icc,ich,icv,msi}_reg`. — [Apple hv_gic_create](https://developer.apple.com/documentation/hypervisor/hv_gic_create(_:)); [Apple GIC functions](https://developer.apple.com/documentation/hypervisor/gic-functions)
- QEMU uses distributor base `0x08000000`, redistributor base `0x080A0000`, inside a `macOS 15.0` availability check. libkrun loads `hv_gic_*` via `dlopen` so the binary still runs on macOS < 15. — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c); [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- No `KVM_IRQFD` or `KVM_IOEVENTFD`: "every virtio doorbell becomes a full VM exit"; IRQs are injected synchronously with `hv_gic_set_spi` or `hv_vcpu_set_pending_interrupt`. — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)

**Nested virtualization / EL2**
- `hv_vm_config_set_el2_enabled(config, true)` [15] "Sets whether the specified VM configuration enables support for Exception Level 2 (EL2)"; query with `hv_vm_config_get_el2_supported`. — [Apple hv_vm_config_set_el2_enabled](https://developer.apple.com/documentation/hypervisor/hv_vm_config_set_el2_enabled(_:_:))
- Hardware requirement: "Nested virt is only supported by macOS on Apple M3 and later" (QEMU mailing-list statement, not Apple documentation); the forum reproducer ran on an M3 Pro / macOS 15.3.1. — [QEMU nested-virt patch series](https://patchew.org/QEMU/20260316130642.13246-1-mohamed@unpredictable.fr/20260316130642.13246-6-mohamed@unpredictable.fr); [Apple forums 775546](https://developer.apple.com/forums/thread/775546)
- QEMU nested-virt notes: EL2 boot needs `HCR_EL2`, `CNTHCTL_EL2`, `ID_AA64PFR0_EL1` changes; "SME is not implemented with nested virt on the Apple side" (QEMU clears `ID_AA64PFR1.SME`); `HV_SYS_REG_MDCR_EL2` defined as `0xe089` for pre-macOS-26 SDKs because "MDCR_EL2 was defined incorrectly". — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c); [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- Without EL2 enabled, the guest runs at EL1/EL0 only (the forum thread shows `CurrentEL` = EL1 by default). — [Apple forums 775546](https://developer.apple.com/forums/thread/775546)

**Other HVF quirks reported by QEMU**
- MIDR is hard-coded because "Apple deliberately doesn't expose a divergent MIDR across systems"; `MDCCSR_EL0` reads return 0 because "injecting an undefined instruction here turns a legal read into a fatal trap"; `hvf_arch_get_registers` asserts the vCPU is not dirty (register state must be explicitly synced). — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)
- Carrick (production Linux-ABI-on-HVF runtime) reports "rare HVF coherence exceptions" under heavy concurrent memory operations with the Go runtime as a guest. — [Carrick site](https://carrick-website.pages.dev/)

### Inferences
- HVF arm64 maps almost 1:1 onto the subset of KVM that gVisor's KVM platform uses: `hv_vm_create` ~ `KVM_CREATE_VM`; `hv_vm_map/unmap/protect` ~ `KVM_SET_USER_MEMORY_REGION` (with permissions); `hv_vcpu_create` ~ `KVM_CREATE_VCPU` (but thread-bound); `hv_vcpu_run` ~ `KVM_RUN`; `hv_vcpus_exit` ~ signal-based kick; `hv_vcpu_get/set_reg` + `get/set_sys_reg` ~ `KVM_GET/SET_ONE_REG`. The published libkrun/Firecracker mapping table is the best existing cross-reference.
- gVisor's KVM platform does not need irqfd/ioeventfd/dirty logging/GIC/PSCI (it uses the VM as a privileged execution context, not a device model), so most of what HVF lacks relative to KVM is irrelevant. What matters is: HVC (`EC 0x16`) and data aborts to unmapped IPA as the "hypercall" and fault channels; `hv_vcpus_exit` for preemption; `hv_vm_protect` for read-only/absent mappings.
- Thread affinity is compatible with gVisor's design (the KVM platform already pins each vCPU to an OS thread), but in Go it requires `runtime.LockOSThread` for every vCPU thread and all `hv_vcpu_*` calls must happen on that thread; cross-thread work must go through `hv_vcpus_exit`.
- Page granularity is the biggest architectural mismatch: the host page is 16 KB, so Sentry-side memory (mmap'd host VA) and `hv_vm_map` regions are 16 KB-granular on macOS <= 15. On macOS 26 the stage-2 granule can be 4 KB, but host-side mmap/mprotect granularity (and therefore `hv_vm_protect` on host-backed memory that must track host permissions) is still 16 KB. The guest (Sentry's own stage-1 page tables) may use 4 KB stage-1 granule architecturally, but a 4 KB guest page would be backed by a 16 KB host page, so memory accounting, `madvise`, and partial-page protections cannot be done at 4 KB on the host.
- "Can I `hv_vm_map` MAP_SHARED file-backed memory?" Apple only says "a single VM region ... typically mmap or mach_vm_allocate"; third-party code maps `MAP_SHARED` file-backed memory successfully; Apple's engineer recommends `hv_vm_allocate` for guest RAM to avoid double-counting. There is no Apple statement of a maximum region count or total mapped size (the only published limit is one VM per process).

### Gaps
- No Apple documentation (and no measured numbers found) on the maximum number of `hv_vm_map` regions, maximum total mapped size, or the cost of `hv_vm_map`/`hv_vm_protect` per call.
- Apple does not document whether `hv_vm_map` accepts file-backed `MAP_SHARED` mappings; only third-party code shows it working.
- Apple does not document the M3+ requirement for EL2; it is reported only by QEMU developers and the setup-docker-macos-action README.
- The full text of `Hypervisor.h` (e.g. the exact `hv_exit_reason_t` numeric values and the `hv_vcpu_exit_t` layout) was not retrievable from Apple's site; the applevisor-sys binding fetch returned 404. Values above come from QEMU/libkrun usage.

## Key question 2: Hypervisor.framework on Intel Macs and whether to target arm64 only

### Takeaway
Intel HVF is a different, older API (`hv_vmx_vcpu_read/write_vmcs`, `hv_vcpu_run_until`, `hv_vm_space_*` for multiple address spaces, no nested VMX). Apple has announced macOS 26 Tahoe as the last major release for Intel Macs, so a 2026 effort should target Apple Silicon only.

### Cited Findings
- Apple's Intel index: `hv_vm_create(hv_vm_options_t)`, `hv_capability(hv_capability_t,...)`, VMCS access via `hv_vmx_vcpu_read_vmcs`/`write_vmcs` ("must be called by the owning thread", available since macOS 10.10), PIO notifiers (`hv_vm_add_pio_notifier` delivering Mach messages), TSC functions (`hv_tsc_clock`, `hv_vcpu_set_tsc_relative`). — [Apple Intel-based Mac](https://developer.apple.com/documentation/hypervisor/intel-based-mac); [Apple hv_vmx_vcpu_read_vmcs](https://developer.apple.com/documentation/hypervisor/hv_vmx_vcpu_read_vmcs(_:_:_:))
- Intel memory management includes "Process-specific memory": `hv_vm_space_create`, `hv_vm_space_destroy`, `hv_vm_map_space`, `hv_vm_unmap_space`, `hv_vm_protect_space`, plus `HV_CAP_ADDRSPACEMAX`. `hv_vm_space_create` (macOS 10.15+): "The guest address space has the maximum allowable size, with a base IPA of 0 and a 4096-byte page size." These are listed only under the Intel page; the Apple Silicon memory-management page lists only `hv_vm_map/unmap/protect`. — [Apple Intel Memory Management](https://developer.apple.com/documentation/hypervisor/intel-based_mac-memory-management); [Apple hv_vm_space_create](https://developer.apple.com/documentation/hypervisor/hv_vm_space_create(_:)); [Apple (arm64) memory management](https://developer.apple.com/documentation/hypervisor/memory-management)
- `hv_vcpu_run_until(vcpu, deadline)` (macOS 10.15+): "supersedes `hv_vcpu_run` on Intel-based Mac computers. Unlike `hv_vcpu_run`, it doesn't return on transparently handled VMEXITs"; uses the VMX preemption timer unless `HV_DEADLINE_FOREVER`. Apple's `hv_vcpu_run` page: "On an Intel-based Mac, `hv_vcpu_run` exits from causes external to the guest. To avoid the overhead of spurious exits use `hv_vcpu_run_until` with the deadline `HV_DEADLINE_FOREVER`." — [Apple hv_vcpu_run_until](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run_until(_:_:)); [Apple hv_vcpu_run](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run(_:))
- QEMU Intel HVF discussion: "hv_vcpu_run() exits very frequently, and often there is actually nothing for the VMM to do except call hv_vcpu_run() again"; switching to `hv_vcpu_run_until()` without `hv_vcpu_interrupt()` makes the vCPU "not exit for long periods"; an unresolved race between `hv_vcpu_interrupt()` and the run calls was raised. — [QEMU patch thread (Phil Dennis-Jordan)](https://patchew.org/QEMU/20230922140914.13906-1-phil@philjordan.eu/)
- No nested VMX on Intel HVF: Parallels KB says nested virtualization "is currently not supported for the Apple hypervisor" on both Intel and Apple Silicon Macs; VMware Fusion 12 on macOS 11+ moved to a user-level monitor on HVF and documents nesting limitations (Fusion 12.1 removed the VMCS-shadowing requirement). — [Parallels KB 116239](https://kb.parallels.com/116239); [Broadcom KB 315276](https://knowledge.broadcom.com/external/article/315276/limitations-of-nested-virtualization-wit.html)
- Apple DTS engineer: nested virtualisation is not supported with macOS guests (Virtualization.framework). — [Apple forums 827663](https://developer.apple.com/forums/thread/827663)
- macOS 26 Tahoe is the last major macOS release for Intel Macs (announced at WWDC 2025); macOS 27 is Apple Silicon only; supported Intel models get 3 years of security updates. — [Engadget](https://www.engadget.com/computing/macos-tahoe-is-the-end-of-the-line-for-intel-macs-113036626.html); [Tom's Hardware](https://www.tomshardware.com/software/macos/macos-tahoe-is-the-last-release-for-intel-macs-apple-silicon-exclusivity-will-mark-end-of-hackintoshes)
- GitHub's hosted Intel macOS runner labels still exist as `macos-15-intel` and `macos-26-intel` (4 CPU, 14 GB RAM). — [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)

### Inferences
- Target arm64 only. Intel HVF would require a second, divergent backend (VMCS-level programming, different exit model) for hardware that leaves Apple's support window in 2028; it also has the spurious-exit problem that `hv_vcpu_run_until` only partially fixes.
- The Intel-only `hv_vm_space_*` API would have been the natural fit for a multi-address-space (per-process) design, but it is absent on Apple Silicon, so a gVisor port must use a single IPA space with Sentry-managed stage-1 page tables, exactly as the existing KVM platform does.

### Gaps
- No Apple deprecation notice for the Intel `hv_vmx_*` API was found; Apple's pages still list it as available. Treat "deprecated" as a practical (hardware EOL) rather than API-level status.

## Key question 3: Entitlements, code signing, sandbox/notarization, CI availability

### Takeaway
`com.apple.security.hypervisor` is mandatory in every process that calls HVF; an ad-hoc signature (`codesign -s - --entitlements ...`) carrying that entitlement works without an Apple developer account (this is how Homebrew-distributed QEMU/Carrick/Lima-style tools ship). GitHub-hosted arm64 macOS runners cannot use HVF at all (no nested virtualization), so CI must use self-hosted bare-metal Macs or a third-party provider.

### Cited Findings
- Apple: `com.apple.security.hypervisor` [11] "is required to use the Hypervisor APIs in any process." "If your app has a deployment target of macOS 10.15 or earlier, add the `com.apple.vm.hypervisor` entitlement ... in addition." — [Apple entitlement page](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hypervisor)
- Apple: HVF is usable "from your entitled, sandboxed, user-space process" and apps are "suitable for distribution on the Mac App Store". — [Apple Hypervisor overview](https://developer.apple.com/documentation/hypervisor)
- Related entitlements listed by Apple: `com.apple.vm.hypervisor` (legacy), `com.apple.vm.networking` (vmnet), `com.apple.vm.device-access`. — [Apple Hypervisor overview](https://developer.apple.com/documentation/hypervisor)
- Ad-hoc signing works: a Rust packaging tool signs with `codesign --force --sign -` plus an entitlements plist containing the hypervisor key, documenting that no certificate is needed for local development and distribution. — [smolvm-pack signing.rs](https://docs.rs/crate/smolvm-pack/latest/source/src/signing.rs)
- Homebrew's build tooling: re-signing with a Developer ID that lacks a matching provisioning profile makes Virtualization/Hypervisor calls fail at runtime; the fix forces ad-hoc signing for such binaries because "some entitlements, including the hypervisor one, require either ad-hoc signing or a Developer ID with a matching provisioning profile." — [pkgxdev/brewkit PR 353](https://github.com/pkgxdev/brewkit/pull/353)
- QEMU on macOS 11 (2020): the entitlement plist with `com.apple.security.hypervisor` (and legacy `com.apple.vm.hypervisor`) signed with `codesign -s -`. — [qemu-arm list, Nov 2020](https://lists.endsoftwarepatents.org/archive/html/qemu-arm/2020-11/msg00586.html)
- Carrick: "The binary is codesigned with the Hypervisor.framework entitlement during install" (Homebrew from source). — [Carrick site](https://carrick-website.pages.dev/)
- libkrun port analysis: "Requires the `com.apple.security.hypervisor` entitlement. Ad-hoc codesigning works for local development." — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- Hardened Runtime: "To upload a macOS app to be notarized, you must enable the Hardened Runtime capability." Runtime exception entitlements: `com.apple.security.cs.allow-jit`, `allow-unsigned-executable-memory`, `allow-dyld-environment-variables`, `disable-library-validation`, `disable-executable-page-protection`, `debugger`. "You add entitlements only to executables." — [Apple Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)
- GitHub-hosted arm64 macOS runners (labels `macos-latest`, `macos-15`, `macos-26`, `xcode-27`; 3-core M1, 7 GB RAM): "Nested-virtualization is not supported due to the limitation of Apple's Virtualization Framework." — [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
- On those runners QEMU fails with `HV_UNSUPPORTED` and Virtualization.framework reports "Virtualization is not available on this hardware" (the runner is itself a VM). — [actions/runner-images issue 9254](https://github.com/actions/runner-images/issues/9254)
- Third-party CI note: nested virtualization needs M3+ on macOS 15; GitHub's fleet is M1-based. — [setup-docker-macos-action README](https://github.com/bennycode/setup-docker-macos-action)

### Inferences
- A Go-built `runsc` binary for macOS must be post-processed with `codesign -s - --entitlements` (or signed with a Developer ID + provisioning profile) before HVF calls succeed; without it `hv_vm_create` fails. This is a packaging step, not a blocker.
- Notarization and the Hardened Runtime are only required for Gatekeeper-friendly GUI distribution; a CLI tool installed via Homebrew or a tarball can stay ad-hoc signed. If hardened runtime is enabled, JIT-style page handling (W^X) applies, but gVisor's Sentry does not generate code so this is not a constraint.
- CI: hosted GitHub runners cannot run HVF tests; plan for self-hosted Apple Silicon hardware (bare metal, or an M3+/macOS 15+ VM host that exposes nested virtualization).

### Gaps
- No Apple document explicitly states that ad-hoc signatures satisfy the hypervisor entitlement; the evidence is from working open-source projects and Homebrew tooling.
- Whether any hosted CI provider offers M3+/macOS 15+ runners with nested virtualization enabled was not verified.

## Key question 4: Performance characteristics of HVF (exit latency, hv_vm_map cost, known issues)

### Takeaway
No published microbenchmark of `hv_vcpu_run` exit latency on Apple Silicon (vs. KVM) was found. Available qualitative evidence: HVF is "a relatively thin wrapper around CPU features"; on Intel, `hv_vcpu_run` has many spurious exits (fixed by `hv_vcpu_run_until`); on arm64, the known costs are userspace handling of WFI/timer/PSCI, lack of ioeventfd (every doorbell = full exit), and the deferred-read MMIO pattern. Carrick measured fork at ~5.7 ms and fork+exec at ~7.8 ms through HVF context rebuilds.

### Cited Findings
- Apple on Intel: `hv_vcpu_run` "exits from causes external to the guest"; use `hv_vcpu_run_until(HV_DEADLINE_FOREVER)` to avoid spurious exits. — [Apple hv_vcpu_run](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run(_:))
- QEMU (Intel): the move to `hv_vcpu_run_until` was expected to bring "a few percent" improvement; a QEMU bug in dirty tracking "went unnoticed because the hypervisor generated extra fault exits that re-ran the handler" and switching to `hv_vcpu_run_until()` exposed it. — [QEMU patch thread](https://patchew.org/QEMU/20230922140914.13906-1-phil@philjordan.eu/); [QEMU commit 3e2c6727](https://qemu.googlesource.com/qemu/+/3e2c6727cb6b6311ee129c24b561bb87495f1a25%5E%21)
- "There is no KVM_IOEVENTFD, so there are no fast MMIO doorbells, and every virtio kick is a full vmexit-to-userspace round trip"; the author calls this "a measurable performance gap worth benchmarking" (i.e. unmeasured). — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- Carrick (DTrace USDT measurements of `carrick run /bin/true`): first boot ~90 ms; fork ~5.7 ms ("page table copy and an HVF context rebuild"); fork+exec ~7.8 ms vs ~1 ms native Linux; child teardown ~7 us; process teardown ~175 ms. No syscall round-trip latency published. — [Carrick site](https://carrick-website.pages.dev/); [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)
- A reverse-engineering write-up describes Hypervisor.framework as a relatively thin wrapper around the CPU's virtualization features; eclecticlight.co measured that compute-bound code in Apple Silicon VMs runs essentially unaltered (throughput, not exit latency). — [Eclectic Light: Virtualisation on Apple silicon](https://eclecticlight.co/2022/07/04/virtualisation-on-apple-silicon-macs-1-how-well-does-it-work/); [Eclectic Light 2026](https://eclecticlight.co/2026/04/29/virtualisation-on-apple-silicon-macs-is-different/)
- `hv_vcpu_get_exec_time` returns cumulative vCPU execution time in nanoseconds (useful for instrumenting exits). — [Apple vCPU Management](https://developer.apple.com/documentation/hypervisor/vcpu-management)
- Known behavioral issues: vtimer auto-mask on `VTIMER_ACTIVATED` exit (must unmask), `VTIMER_ACTIVATED` only delivered inside `hv_vcpu_run` (needs host timer for halted vCPUs), MMIO reads must be completed on next `run()` entry, SMC needs manual PC advance while HVC does not, `hvc #0` may be consumed as SMCCC. — [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c); [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html); [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)

### Inferences
- For gVisor the hot path is "guest EL0 svc -> guest EL1 (Sentry) handles it, or -> HVC exit to host for host syscalls". The second hop's cost (hv_vcpu_run return + re-entry) is the number that matters and must be measured on real hardware; nothing published substitutes for that measurement.
- Register syncing is explicit (`hv_vcpu_get/set_reg` per register, each a framework call), unlike KVM's shared `kvm_run` mmap; a platform that reads many registers per exit will pay per-call overhead. The syndrome/virtual/physical addresses are delivered in the `hv_vcpu_exit_t` without extra calls.

### Gaps
- No measured `hv_vcpu_run` round-trip latency on M1-M5 (microseconds or cycles) was found in Apple docs, QEMU, libkrun, Carrick, or blogs. A microbenchmark (e.g. with applevisor bindings or C) is required.
- No numbers for `hv_vm_map`/`hv_vm_protect` call cost or TLB-invalidation (`hv_vcpu_invalidate_tlb`) cost.

## Key question 5: Alternatives to a hypervisor for syscall interception on macOS (ptrace, Mach exception ports, task ports, Rosetta, DTrace/Endpoint Security, in-process trapping)

### Takeaway
macOS has no primitive that lets a supervising process intercept another process's valid BSD syscalls synchronously: `ptrace` has no `PTRACE_SYSEMU`/`SYSCALL` or register/memory requests, and XNU raises `EXC_SYSCALL` only for invalid Mach trap numbers, never for valid BSD syscalls. Mach exception ports do deliver faults (`EXC_BAD_ACCESS`), breakpoints and signals, and are inherited across fork/exec, but that only covers page faults, not syscalls. Therefore neither a ptrace-like nor a seccomp/systrap-like gVisor platform can be built on macOS; HVF is the only mechanism that intercepts `svc` from untrusted code.

### Cited Findings

**ptrace**
- macOS `ptrace(2)` documents only: `PT_TRACE_ME`, `PT_DENY_ATTACH`, `PT_SIGEXC` ("any signals from the calling process to be delivered as Mach exceptions"), `PT_CONTINUE`, `PT_STEP`, `PT_KILL`, `PT_ATTACH` (deprecated, replaced by `PT_ATTACHEXC`), `PT_ATTACHEXC` ("signals from the child are delivered to the parent as Mach exceptions on the task's exception port"), `PT_DETACH`. `PT_GETREGS`/`PT_SETREGS`/`PT_GETFPREGS`/`PT_SETFPREGS` appear only in the ERRORS section; no `PT_READ_*`/`PT_WRITE_*`, no syscall-stop request. — [ptrace(2) man page, Xcode SDK](https://keith.github.io/xcode-man-pages/ptrace.2.html)
- XNU: `PT_STEP` calls `thread_setsinglestep` and returns `ENOTSUP` if that fails. — [xnu-7195 mach_process.c](https://opensource.apple.com/source/xnu/xnu-7195.81.3/bsd/kern/mach_process.c.auto.html)

**Mach exceptions and syscalls**
- XNU arm64 `mach_syscall()`: `exception_triage(EXC_SYSCALL, &exc_code, 1)` is reached only via `goto bad` when `call_number >= MACH_TRAP_TABLE_COUNT` or the entry is `kern_invalid`; "assert(call_number < 0); /* Otherwise it would be a Unix syscall */". No per-call Mach exception for valid traps. — [xnu osfmk/arm64/bsd_arm64.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/arm64/bsd_arm64.c)
- XNU arm64 `unix_syscall()`: reads the syscall number from the syscall-code register (x16 on arm64; falls back to x0 for indirect syscalls), redirects out-of-range numbers to `sysent[SYS_invalid]`, dispatches `(*callp->sy_call)(...)`, sets `x0`/`x1` and the carry flag (`PSR64_CF`) on error, rewinds PC by 4 on `ERESTART`, and returns via `thread_exception_return()`. The file contains no `exception_triage`/`EXC_SYSCALL` reference. — [xnu bsd/dev/arm/systemcalls.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/dev/arm/systemcalls.c)
- `ux_exception.c`: `EXC_SYSCALL` maps to `SIGSYS` only when a `send_sigsys` flag is set; `EXC_UNIX_BAD_SYSCALL` (0x10000) is the BSD-side bad-syscall code. — [xnu ux_exception.c](https://cs.iossec.tech/xnu/latest/source/bsd/uxkern/ux_exception.c); [ux_exception.h](https://opensource.apple.com/source/xnu/xnu-4570.41.2/bsd/sys/ux_exception.h.auto.html)
- Exception type constants: `EXC_SYSCALL` = 7, `EXC_MASK_SYSCALL` = 128 (and `EXC_BAD_ACCESS`, `EXC_BREAKPOINT`, `EXC_MACH_SYSCALL` etc.). — [mach2 exception_types.rs](https://docs.rs/crate/mach2/latest/source/src/exception_types.rs)
- Exception ports are inherited: `ipc_task_init` copies `task->exc_actions[i] = parent->exc_actions[i]` and takes a send right (`exception_port_copy_send`); `ipc_task_reset` (which "only happens during sugid or corpsify") clears non-privileged exception ports. So a parent's task exception ports survive fork and a non-setuid exec. — [xnu osfmk/kern/ipc_tt.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/kern/ipc_tt.c)
- Alternatively, set exception ports at spawn time with `posix_spawnattr_setexceptionports_np` (used in XNU tests and recommended on crashpad-dev). — [xnu tests/immovable_send.c](https://opensource.apple.com/source/xnu/xnu-7195.81.3/tests/immovable_send.c.auto.html); [crashpad-dev thread](https://groups.google.com/a/chromium.org/g/crashpad-dev/c/vyfIdRfvGz8)
- Handler registration pattern: allocate a receive port, insert a send right, `thread_set_exception_ports`/`task_set_exception_ports` with a state-based behavior and `MACH_EXCEPTION_CODES`; arm64 exception state is delivered to the handler. — [xnu tests/exc_helpers.c](https://opensource.apple.com/source/xnu/xnu-7195.101.1/tests/exc_helpers.c.auto.html)

**task ports / cross-process memory**
- `task_for_pid_posix_check` (as mirrored by Crashpad from xnu-2422): returns true for root; otherwise requires the target's real, effective and saved UIDs to match the caller's; `task_for_pid` then calls `mac_proc_check_get_task()` under `CONFIG_MACF`, and a nonzero result becomes `KERN_FAILURE`. — [Crashpad task_for_pid.cc](https://fuchsia.googlesource.com/third_party/crashpad/+/refs/heads/main/util/mach/task_for_pid.cc); [xnu-1228 vm_unix.c](https://opensource.apple.com/source/xnu/xnu-1228.3.13/bsd/vm/vm_unix.c.auto.html)
- `com.apple.security.get-task-allow` lets processes holding `com.apple.security.cs.debugger` obtain the task port; without it, hardened/SIP-protected processes cannot be inspected; `com.apple.system-task-ports` (formerly `task_for_pid-allow`) is Apple-only. (Security-community reference, secondary.) — [HackTricks macOS dangerous entitlements](https://book.hacktricks.xyz/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-dangerous-entitlements)
- Practitioners report `task_for_pid` failing (error 5) even with `get-task-allow` and sudo on modern macOS; "modern versions of macOS severely restrict the use of that call such that it's only really useful for developers tools." — [Swift forums thread](https://forums.swift.org/t/how-do-i-get-swift-inspect-to-work-on-macos/70648)
- Cross-process reads/writes use `mach_vm_read_overwrite` (preferred over `vm_read` because it handles unaligned reads into a caller buffer) and `mach_vm_write`; Wine reduced a read from four syscalls to one by switching to `mach_vm_read_overwrite`. — [process-memory crate macos.rs](https://docs.rs/crate/process-memory/latest/source/src/macos.rs); [Wine MR 4826](https://list.winehq.org/archives/list/wine-gitlab@list.winehq.org/thread/WIS6BHVMBV6RFK4CVCRT3ZEEDEX2M3SU)
- `vm_remap`/`mach_vm_remap` "maps the memory objects underlying a portion of the specified source_task's virtual address space into the address space belonging to target_task", with a copy flag (COW vs shared) and inheritance (`VM_INHERIT_SHARE`). — [xnu vm_remap man page](https://opensource.apple.com/source/xnu/xnu-792/osfmk/man/vm_remap.html)
- Crashpad's `ProcessMemoryMac` reads another task's memory via a send right to its task port. — [Crashpad process_memory_mac.h](https://chromium.googlesource.com/crashpad/crashpad/+/refs/heads/cxx17/util/process/process_memory_mac.h)

**Existing "Linux ABI via HVF trap" projects (evidence that the only workable interception is the hypervisor)**
- Noah (2017, Intel): "Load ELF binary into VM and let it run instead of kernel, trap system calls from it by hypervisor, and translate them"; VMs "have NO kernel inside"; one host Noah process + VM per Linux process; fork clones VM state; memory uses a straight (identity) guest-virtual-to-guest-physical mapping to avoid double translation; "Virtualization is per syscall, not per device I/O"; performance data was never published in the slides. — [Noah slides (Linux Foundation)](https://events.static.linuxfound.org/sites/events/files/slides/Noah%20Hypervisor-Based%20Darwin%20Subsystem%20for%20Linux.pdf)
- Carrick (2026, Apple Silicon, Rust): guest runs at EL0; `svc #0` -> synchronous exception via `VBAR_EL1` (guest-side EL1 stub) -> `hvc #2` exits to the host runtime -> handler reads x8/x0-x5, calls Darwin APIs, writes x0, resumes; stage-1 identity-mapped page tables with MMU on (`SCTLR_EL1.M=1`) so `ldaxr/stlxr` work; one host pthread + one HVF vCPU per guest thread; `fork` = quiesce sibling vCPUs, real macOS `fork()`, child re-registers RAM with `hv_vm_map` and rebuilds a vCPU; 216/338 aarch64 syscalls implemented; "Not a security sandbox." — [Carrick site](https://carrick-website.pages.dev/); [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)
- elfuse (C): same design; requires macOS 13+ and `com.apple.security.hypervisor`; supports fork/clone/execve/wait/ptrace. — [elfuse project listing](https://awesome.ecosyste.ms/projects/github.com%2Fsysprog21%2Felfuse)
- alvm (Rust experiment): handles "the syscall `svc` instruction, which is trapped as a hardware exception, in the user land Rust code." — [alvm listing](https://awesome.ecosyste.ms/projects/github.com%2Fmathetake%2Falvm)

**Rosetta**
- Rosetta 2 continues to work in macOS 26 and 27; from macOS 28 it supports only a subset of apps. — [Macworld](https://www.macworld.com/article/2808358/if-you-own-an-intel-mac-you-have-12-months-to-upgrade-to-a-new-model.html)
- Carrick uses "Rosetta for Linux (`softwareupdate --install-rosetta`)" for x86_64 images; static-musl (Alpine) binaries hit a static-PIE limitation in Apple's Rosetta stack (also seen in Docker Desktop's Rosetta backend). — [Carrick site](https://carrick-website.pages.dev/); [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)

**DTrace / Endpoint Security**
- The Endpoint Security client entitlement (`com.apple.developer.endpoint-security.client`) must be granted by Apple via a request form; one applicant waited 13 months; unapproved binaries are killed with "unsatisfied entitlements". — [Apple forums 743263](https://developer.apple.com/forums/thread/743263); [Apple forums 688261](https://developer.apple.com/forums/thread/688261)

### Inferences
- Mach exception ports are an adequate substitute for `SIGSEGV`/`ptrace` fault delivery (EXC_BAD_ACCESS, EXC_BREAKPOINT, EXC_ARITHMETIC) and have the advantage of being inheritable across `fork` and settable at `posix_spawn`, which sidesteps `task_for_pid`. But because XNU dispatches valid BSD syscalls without any exception, an untrusted Linux binary executing `svc #0` in a native macOS process would have its Linux syscall number interpreted by XNU as a Darwin syscall (no seccomp exists to block it). This rules out both a ptrace-style and a systrap/seccomp-style platform; it is a security blocker, not merely a performance issue.
- Endpoint Security is an asynchronous auditing/authorization facility for security products with an Apple-gated entitlement; DTrace is tracing (and restricted under SIP). Neither provides synchronous, per-thread syscall emulation with register rewriting, so neither can serve as a platform.
- In-process trapping (running the app in the Sentry's own address space and catching SIGILL/SIGSEGV) would give no isolation at all (shared address space, direct XNU syscalls) and is unacceptable for gVisor's threat model.
- `task_for_pid` restrictions are moot for the HVF design (the guest lives inside the Sentry's own process); they matter only if one tried a multi-process design, where same-uid non-hardened children are reachable but AMFI/hardened-runtime policies make this fragile.

### Gaps
- The current XNU `task_for_pid` source (its location moved out of the fetched `bsd/vm/vm_unix.c` region) was not retrieved; the policy summary above comes from older XNU and Crashpad's mirror.
- Apple's "Rosetta for Linux" documentation page returned 404 at both URLs tried; details on its page-size and static-PIE limitations come from Carrick.

## Key question 6: Host memory primitives on macOS (memfd alternatives, hole punching, madvise, mincore, address space, 16 KB pages, W^X, PAC)

### Takeaway
macOS lacks `memfd_create`, `MADV_DONTNEED`-as-discard and `MADV_REMOVE`; the substitutes are `shm_open`/`mach_make_memory_entry_64`/`hv_vm_allocate` for shareable anonymous memory, `F_PUNCHHOLE` for file holes, and `MADV_FREE_REUSABLE`/`MADV_FREE_REUSE` for discardable anonymous pages. The host page is 16 KB on Apple Silicon, user VA tops out just below 2^47, and W^X applies to JIT regions (MAP_JIT + `pthread_jit_write_protect_np`), which matters only if the Sentry writes executable memory.

### Cited Findings
- Apple Silicon page size is 16 KiB (`PAGE_SIZE = 0x4000` in HVF bindings; "guard pages are sized to the host page size, 16 KiB on Apple silicon"). — [applevisor-sys](https://docs.rs/applevisor-sys/latest/aarch64-unknown-linux-gnu/src/applevisor_sys/lib.rs.html); [hyperlight PR 1681](https://github.com/hyperlight-dev/hyperlight/pull/1681)
- XNU arm64 `vm_param.h`: on macOS/DriverKit the raw maximum user address is `0x00007FFFFE000000` (just under 2^47); other platforms (iOS etc.) use `0x0000000FC0000000`. — [xnu osfmk/mach/arm/vm_param.h (saurik mirror)](https://git.saurik.com/apple/xnu.git/blame/HEAD:/osfmk/mach/arm/vm_param.h)
- Named memory for sharing: `mach_make_memory_entry_64` with `MAP_MEM_NAMED_CREATE` mapped twice works with `hv_vm_map`; `hv_vm_allocate` (macOS 12.1+) is Apple's recommended allocator for guest RAM. — [Apple forums 851651](https://developer.apple.com/forums/thread/851651); [Apple hv_vm_allocate](https://developer.apple.com/documentation/hypervisor/hv_vm_allocate(_:_:_:))
- `F_PUNCHHOLE` (`fcntl(2)`): "Deallocate a region and replace it with a hole"; reads return zeros; file size unchanged; "Holes must be aligned to file system block boundaries"; `EINVAL` if offset/length are not multiples of the FS block size or negative or if `fp_flags`/`reserved` are nonzero; `ENOSPC` possible on a cloned-file filesystem; `EPERM` without write permission; "will fail on file systems that do not support this interface" (no FS list given). Struct: `fp_flags`, `reserved`, `fp_offset`, `fp_length`. QEMU maps `ENODEV` to "not supported". — [fcntl(2) man page](https://keith.github.io/xcode-man-pages/fcntl.2.html); [QEMU file-posix macOS commit](https://git.cs.tu-dortmund.de/SYS-OSS/FRET-qemu/commit/0dfc7af2b287323dde0725c04f5765e0e508d9fd)
- `F_PREALLOCATE` (`fstore_t`, `F_ALLOCATECONTIG`/`F_ALLOCATEALL`/`F_ALLOCATEPERSIST`), `F_NOCACHE`, `F_GETPATH`, `F_DUPFD_CLOEXEC` are documented in the same page. — [fcntl(2) man page](https://keith.github.io/xcode-man-pages/fcntl.2.html)
- `madvise(2)`: `MADV_FREE` ("pages can be reused immediately; the address range stays valid"), `MADV_DONTNEED` is only a hint ("not expecting to access this address range soon"), `MADV_ZERO_WIRED_PAGES`, `MADV_ZERO` ("could return ENOTSUP in some situations"); errors `EINVAL` (unallocated regions), `ENOMEM`, `EPERM`, `ENOTSUP`. `MADV_FREE_REUSABLE`/`MADV_FREE_REUSE` are not in the man page. — [madvise(2) man page](https://keith.github.io/xcode-man-pages/madvise.2.html)
- libkrun: "the MADV_DONTNEED flag is no-op on macOS because it preserves the data, so the OS cannot discard the pages"; libkrun uses `MADV_FREE` for balloon reclaim. — [libkrun PR 703](https://github.com/containers/libkrun/pull/703)
- `MADV_FREE_REUSABLE` is "the same behavior as MADV_FREE except that it doesn't count these pages towards RSS" (Firefox 70 switched to it); jemalloc: MADV_FREE'd memory "is counted against our process's RSS until the system starts running low on memory". — [Mozilla bug 1567366](https://bugzilla.mozilla.org/show_bug.cgi?id=1567366); [jemalloc-discuss 2011](https://jemalloc.net/mailman/jemalloc-discuss/2011-October/000037.html)
- Ruby calls `MADV_FREE_REUSE` on macOS to keep `task_info` accounting accurate, retrying on `EAGAIN`. — [Ruby commit 875c85a8](https://source-hub.etos-pro.ru/github/ruby/commit/875c85a8bdca6cc2c7d0a26291ec4a6b2647b195.patch)
- `mincore(2)` flags: `MINCORE_INCORE` 0x1, `MINCORE_REFERENCED` 0x2, `MINCORE_MODIFIED` 0x4, `MINCORE_REFERENCED_OTHER` 0x8, `MINCORE_MODIFIED_OTHER` 0x10; errors `EINVAL`, `EFAULT`. — [mincore(2) man page](https://keith.github.io/xcode-man-pages/mincore.2.html)
- W^X: on Apple Silicon (macOS 11+) no page can be RWX at once; `MAP_JIT` + `pthread_jit_write_protect_np(bool)` toggles per-thread write vs. execute view; threads that call JIT code must be in execute mode; Firefox 116 ships `MAP_JIT` with `pthread_jit_write_protect_np` plus the `allow-jit` entitlement. — [Outflank macOS JIT memory (Feb 2026)](https://www.outflank.nl/blog/2026/02/19/macos-jit-memory/); [Mozilla bug 1837194](https://bugzilla.mozilla.org/show_bug.cgi?id=1837194); [Wasmtime issue thread](https://bytecodealliance.github.io/zulip-archive/stream/225357-git-wasmtime/topic/wasmtime.20.2F.20issue.20.2312076.20Cranelift.3A.20Non-deterministic.20JIT.20.2E.2E.2E.html)
- Pointer authentication: XNU's arm64 thread-state header marks `fp`, `lr`, `pc` as opaque when pointer-auth calls are enabled (arm64e); accessor macros read them as plain pointers. — [xnu osfmk/mach/arm/_structs.h](https://git.saurik.com/apple/xnu.git/blob/HEAD:/osfmk/mach/arm/_structs.h)
- Go on Darwin makes syscalls through `libSystem` (since Go 1.12) rather than raw `svc`. — [Go 1.12 release notes](https://go.dev/doc/go1.12)

### Inferences
- memfd replacement for gVisor's `pgalloc` backing file: `shm_open`+`ftruncate` (POSIX shm; cannot be hole-punched on macOS) or a regular APFS file with `F_PUNCHHOLE` for `MADV_REMOVE`-like decommit, or `hv_vm_allocate`/named memory entries for anonymous shared memory. `mach_make_memory_entry_64` objects can be mapped multiple times (the gVisor "memory file" pattern of mapping the same pages at different VAs).
- Decommit semantics differ: Linux `MADV_DONTNEED` zero-fills on next access; the macOS equivalent that actually releases memory is `MADV_FREE_REUSABLE` (then `MADV_FREE_REUSE` before reuse for accounting), and contents after `MADV_FREE` are undefined-until-reclaimed rather than guaranteed zero. A gVisor port must not rely on zero-fill from madvise.
- The 16 KB host page is the single largest porting issue: gVisor hardcodes a 4 KB page size across `hostarch`, `pgalloc`, `mm`, and the platform layer. Either the Sentry adopts 16 KB everywhere on macOS (and Linux guest apps that assume 4 KB `getpagesize()` may break; the same compatibility issue exists for Linux on 16 KB-page arm64 kernels) or the 4 KB IPA granule on macOS 26 is used with 16 KB host backing and 4 KB bookkeeping only inside the guest.
- PAC: Go produces arm64 (not arm64e) binaries, so the Sentry itself is unaffected; only Mach thread-state structs passed to/from the kernel need care if signal/exception handlers inspect `pc`/`lr`.
- W^X/MAP_JIT is irrelevant to a Sentry that executes guest code via HVF (guest pages are just data in the host; execute permission is a stage-2 attribute set with `HV_MEMORY_EXEC`).

### Gaps
- Apple's "Addressing architectural differences in your macOS code" page (page size, Rosetta 4 KB emulation) fetched empty; page size facts are from headers/bindings.
- `MADV_FREE_REUSABLE`/`MADV_FREE_REUSE` semantics are not in the public man page; evidence is from Mozilla/Ruby/jemalloc.
- Whether `F_PUNCHHOLE` works on POSIX shared memory objects (`shm_open`) or only on APFS/HFS+ files was not confirmed; the man page says only "file systems that support this interface".
- `mmap(MAP_FIXED)` replace-semantics and `MAP_FIXED_NOREPLACE` absence were not verified from a primary source.

## Key question 7: Event / notification primitives (kqueue vs epoll, eventfd/signalfd/timerfd replacements, fd passing, pipe2, utun, vmnet, BSD sockets)

### Takeaway
kqueue covers epoll (EVFILT_READ/WRITE), signalfd (EVFILT_SIGNAL), timerfd (EVFILT_TIMER), and eventfd (EVFILT_USER, or faster, a Mach port via EVFILT_MACHPORT). Unix sockets, socketpair and SCM_RIGHTS exist. `pipe2` does not exist (CLOEXEC is non-atomic). For a netstack link, `utun` needs root and `vmnet` needs `com.apple.vm.networking` or root; the practical alternative is a userspace proxy over Unix sockets (gvproxy/passt style) or a hostinet-like passthrough on BSD sockets.

### Cited Findings
- kqueue filters (Xcode man page): `EVFILT_READ`, `EVFILT_WRITE`, `EVFILT_EXCEPT` (`NOTE_OOB`), `EVFILT_AIO`, `EVFILT_VNODE` (`NOTE_DELETE/WRITE/EXTEND/ATTRIB/LINK/RENAME/REVOKE/FUNLOCK/LEASE_*`), `EVFILT_PROC` (`NOTE_EXIT/EXITSTATUS/FORK/EXEC/SIGNAL`), `EVFILT_SIGNAL` (fires even if `SIG_IGN`, before normal delivery, auto `EV_CLEAR`, `data` = count), `EVFILT_MACHPORT` (port or port set; `MACH_RCV_MSG` in `fflags` receives into `ext[0]/ext[1]`), `EVFILT_TIMER` (`NOTE_SECONDS/USECONDS/NSECONDS/MACHTIME/ABSOLUTE/CRITICAL/BACKGROUND/LEEWAY`, periodic unless `EV_ONESHOT`). Flags `EV_ADD/ENABLE/DISABLE/DELETE/RECEIPT/ONESHOT/CLEAR/EOF/OOBAND/ERROR/UDATA_SPECIFIC`. `kevent64`, `kevent_qos` (`KEVENT_FLAG_IMMEDIATE`, `KEVENT_FLAG_STACK_DATA`). "The queue is not inherited by a child created with fork(2)." — [kqueue(2) man page](https://keith.github.io/xcode-man-pages/kqueue.2.html)
- `EVFILT_USER` and `EVFILT_MACHPORT` are Darwin-specific constants in BSD bindings. — [kqueue2-sys darwin.rs](https://docs.rs/crate/kqueue2-sys/latest/source/src/constants/darwin.rs); [nix event.rs](https://docs.rs/crate/nix/0.24.3/source/src/sys/event.rs)
- Chromium's macOS message pump: "MessagePumpKqueue will directly use Mach ports in the kqueue if it is possible. This is significantly faster than using an EVFILT_USER event, especially when triggered across threads." Pre-10.12 kqueues could only watch port sets; "As of macOS 10.14, updating a timer from the thread that reads the kqueue does not cause spurious wakeups." — [Chromium message_pump_kqueue.cc](https://chromium.googlesource.com/chromium/src/+/b9e60ddc7606689e508f295077656389380288ba/base/message_loop/message_pump_kqueue.cc)
- `pipe2` absent: Go's darwin path uses `pipe` followed by `fcntl(FD_CLOEXEC)` on each fd; the Rust `os_pipe` crate: "macOS doesn't support pipe2. ... call pipe() followed by fcntl(), and hope that no other threads fork() in between." — [Go commit 0ebaca6b](https://lab.nexedi.cn/kirr/go/-/commit/0ebaca6ba27534add5930a95acffa9acff182e2b); [os_pipe unix.rs](https://docs.rs/os_pipe/latest/src/os_pipe/unix.rs.html)
- `utun`: open `socket(PF_SYSTEM, SOCK_DGRAM, SYSPROTO_CONTROL)`, resolve `"com.apple.net.utun_control"` with `CTLIOCGINFO`, `connect` with unit 0 to let the kernel pick; name read back via `getsockopt(SYSPROTO_CONTROL, UTUN_OPT_IFNAME)`; `PF_SYSTEM` = 32, `SYSPROTO_CONTROL` = 2; "L3 on macOS needs root; run the daemon with sudo." (project code, not Apple docs). — [filament-cli tun/macos.rs](https://docs.rs/crate/filament-cli/0.8.1/source/src/tun/macos.rs); [geph5 vpn/macos](https://docs.rs/crate/geph5-app/0.4.2/source/src/vpn/macos/mod.rs); [Apple forums 758461](https://developer.apple.com/forums/thread/758461)
- vmnet (macOS 10.10+): host mode / shared mode (and bridged via `operating_modes_t`); "A sandboxed user space process must have the `com.apple.vm.networking` entitlement"; max 32 interfaces, 4 per guest; each read/write up to 200 packets / 256 KB; functions `vmnet_start_interface(xpc_object_t, dispatch_queue_t, handler)`, `vmnet_interface_start_with_network`, `vmnet_interface_set_event_callback`, `vmnet_read/vmnet_write(interface_ref, vmpktdesc*, int*)`, `vmnet_stop_interface`; newer network-object API `vmnet_network_create`, `vmnet_network_configuration_create(vmnet_mode_t)`, `..._add_port_forwarding_rule`, `..._add_dhcp_reservation`, `..._disable_nat44/nat66/dhcp/dns_proxy`, `..._set_external_interface`, `vmnet_network_copy_serialization`, `vmnet_enable_virtio_header_key`. — [Apple vmnet](https://developer.apple.com/documentation/vmnet)
- Third-party bindings: "The `com.apple.vm.networking` entitlement, or root, is required to start a vmnet interface." One bridge relays vmnet into a `socketpair` consumed by Virtualization.framework's `VZFileHandleNetworkDeviceAttachment` (reads event-driven via `vmnet_interface_set_event_callback`, writes async on the fd). — [vmnet crate README](https://docs.rs/crate/vmnet/latest/source/README.md); [arcbox-vmnet lib.rs](https://docs.rs/crate/arcbox-vmnet/latest/source/src/lib.rs)
- libkrun porting notes: "No TAP on macOS. Options are a unixgram/unixstream backend (gvproxy/passt, as krunkit does) or vmnet, which needs root or a restricted entitlement." Event loop: port epoll to kqueue or use `mio`; "Jailer/seccomp: Not available ... consider a Seatbelt (`sandbox_init`) profile and a separate uid." — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)

### Inferences
- gVisor's host event loop (`fdnotifier`, epoll-based) ports to kqueue with EVFILT_READ/WRITE + `EV_CLEAR` for edge-triggered behavior; `eventfd`-style wakeups become EVFILT_USER (or a Mach port on a kqueue for lower cross-thread latency); timerfd/signalfd users become EVFILT_TIMER/EVFILT_SIGNAL. The kqueue not being inherited across fork is harmless for runsc's model where the sandbox process is exec'd.
- Netstack link: `utun` gives an L3 TUN (no Ethernet frames) and needs root; `vmnet` gives L2 but needs an entitlement granted via provisioning profile or root. A gvproxy/passt-style userspace NAT over a Unix socket (as krunkit/Carrick do) is the only unprivileged option; `hostinet`-style passthrough maps directly onto BSD sockets.
- The non-atomic `pipe`+`fcntl` race only matters if the Sentry forks while creating pipes; runsc's Go runtime does not fork arbitrarily, so this is a minor caveat.

### Gaps
- Whether vmnet gained a true file-descriptor I/O mode in macOS 15/26 was not confirmed; Apple's page shows only `vmnet_read/vmnet_write` with event callbacks, and the fd-based path belongs to Virtualization.framework (`VZFileHandleNetworkDeviceAttachment`).
- No primary Apple source for the `utun` root requirement; it is reported by multiple VPN implementations.

## Key question 8: Signals on macOS (semantics, ucontext layout, real-time signals, Go's SIGURG preemption)

### Takeaway
BSD signals with `sigaction(SA_SIGINFO)`, `sigaltstack` and `ucontext_t` -> `__darwin_mcontext64` (`__es` exception state, `__ss` `__darwin_arm_thread_state64`, `__ns` NEON state) are available; real-time signals do not exist (which is why Go preempts with SIGURG). Under HVF, guest faults arrive as synchronous `hv_vcpu_run` exits rather than host signals, so the platform does not need SIGSEGV-based fault delivery; signals are only needed for host-side preemption and for Go's own runtime.

### Cited Findings
- `__darwin_mcontext64` holds three members: exception state, thread state, NEON state; `__darwin_arm_thread_state64` = x0..x28, fp, lr, sp, pc, 32-bit cpsr, 32-bit pad (with fp/lr/pc opaque under pointer auth). — [xnu bsd/arm/_mcontext.h](https://git.saurik.com/apple/xnu.git/blob/HEAD:/bsd/arm/_mcontext.h); [xnu osfmk/mach/arm/_structs.h](https://git.saurik.com/apple/xnu.git/blob/HEAD:/osfmk/mach/arm/_structs.h); [Rust libc aarch64 apple align.rs](https://rust.binary.ninja/src/libc/unix/bsd/apple/b64/aarch64/align.rs.html)
- Apple's libplatform `sigtramp` has a comment about passing NULL instead of the context on some platforms, referencing a bug about bad siginfo on arm64 processes. — [libplatform sigtramp.c diff](https://git.saurik.com/apple/libplatform.git/blobdiff_plain/89154bfbfa86dc8977dc06e4201daac587013ec8..HEAD:/src/setjmp/generic/sigtramp.c)
- Go runtime: "We need to deal with platforms without real-time signals (like macOS), so those are out"; `sigPreempt = _SIGURG` because applications rarely use it and spurious SIGURG is harmless. — [Go runtime signal_unix.go](https://sources.debian.org/src/gcc-arm-none-eabi/15:12.2.rel1-1/libgo/go/runtime/signal_unix.go)
- Practical symptom: a Go program on an M1 Mac flooded "urgent I/O" messages until docker-cli extended SIGURG-ignoring to Darwin (Go issue 37942). — [docker-cli commit](https://git.coopcloud.tech/p4u1/docker-cli/src/commit/0dfc5567bc0fdfe4e274fb55388b9aa96fdeb6df/cli/command/container/signals_windows.go)
- `EVFILT_SIGNAL` reports signal generation (even when ignored) and fires before delivery; `PT_SIGEXC`/`PT_ATTACHEXC` convert a traced process's signals into Mach exceptions. — [kqueue(2) man page](https://keith.github.io/xcode-man-pages/kqueue.2.html); [ptrace(2) man page](https://keith.github.io/xcode-man-pages/ptrace.2.html)
- Dart's VM installs its SIGPROF handler with `SA_RESTART | SA_SIGINFO` via `sigaction` on macOS (standard pattern). — [Dart signal_handler_macos.cc](https://dart.googlesource.com/sdk/+/2.1.1-dev.2.0/runtime/vm/signal_handler_macos.cc)
- In HVF the guest's data/instruction aborts, HVC/SMC, WFI, breakpoints and debug exceptions surface as `HV_EXIT_REASON_EXCEPTION` with the syndrome in `hv_vcpu_exit_t`; `hv_vcpus_exit` yields `HV_EXIT_REASON_CANCELED`. — [Apple vCPU Management](https://developer.apple.com/documentation/hypervisor/vcpu-management); [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)

### Inferences
- gVisor's KVM platform on Linux relies on host signals in two places: `SIGSEGV`/`SIGBUS` delivered to the vCPU thread for faults while in "bluepilled" Sentry code, and signal-based vCPU kicks. On HVF, kicks become `hv_vcpus_exit` (callable cross-thread) and faults in guest mode become synchronous exits; only Sentry-side host faults (Go runtime crashes) remain signals. The absence of real-time signals removes the option of per-vCPU RT-signal kicks, but `hv_vcpus_exit` makes them unnecessary.
- Go's SIGURG preemption continues to work inside a vCPU thread only while the thread is executing host code; a thread blocked in `hv_vcpu_run` will have SIGURG delivered when the call returns (or the kernel interrupts it), so Go's scheduler must be prevented from needing to preempt vCPU threads (use `LockOSThread` and keep them out of the Go scheduler's view, as the Linux KVM platform already does via `entersyscall`-style annotations).

### Gaps
- No primary Apple document on the exact `ucontext_t` layout; derived from XNU headers and a libc binding.
- Behavior of `hv_vcpu_run` when a signal (e.g. SIGURG) is delivered to the running vCPU thread (does it return `HV_EXIT_REASON_CANCELED`, `EINTR`-like error, or run the handler and continue?) is undocumented; it must be tested.

## Cross-cutting assessment: which gVisor platform model maps to macOS, and how hard each is

### Takeaway
Only the KVM-like model is implementable on macOS, via Hypervisor.framework on Apple Silicon. The ptrace-like and systrap/seccomp-like models have no macOS equivalent because XNU exposes no syscall-interception hook for valid syscalls and no seccomp. Difficulty of the HVF route is dominated not by the HVF API (which is close to the KVM subset gVisor uses) but by (1) the 16 KB host page size, (2) Go/cgo integration with strict thread affinity and Apple's signing requirements, and (3) replacing Linux host primitives (memfd, madvise semantics, epoll/eventfd, TUN) with Darwin ones.

### Cited Findings
- KVM vs HVF mapping table (libkrun/Firecracker analysis): `KVM_CREATE_VM` -> `hv_vm_create` (one VM per process); `KVM_SET_USER_MEMORY_REGION` -> `hv_vm_map` ("nearly 1:1"); `KVM_CREATE_VCPU` -> `hv_vcpu_create` (thread-bound); `KVM_RUN` -> `hv_vcpu_run` (raw syndrome); `KVM_SET_ONE_REG` -> `hv_vcpu_set_reg`/`set_sys_reg`; signal kick -> `hv_vcpus_exit`/`hv_vcpu_request_exit` (`CANCELED`); in-kernel PSCI/WFI/dirty-log/irqfd/ioeventfd -> none. libkrun's entire macOS-specific layer is ~2,400 lines plus a 731-line HVF wrapper and ~4,712 lines of generated bindings. — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- XNU raises no Mach exception for valid BSD syscalls; `EXC_SYSCALL` is only for invalid Mach trap numbers. — [xnu bsd_arm64.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/arm64/bsd_arm64.c); [xnu systemcalls.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/dev/arm/systemcalls.c)
- macOS ptrace has no syscall-stop, register, or memory requests. — [ptrace(2) man page](https://keith.github.io/xcode-man-pages/ptrace.2.html)
- "Jailer/seccomp: Not available" on macOS; Seatbelt (`sandbox_init`) is the available process-confinement mechanism. — [vadika KVM->HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)
- Working precedents for "untrusted ELF runs in an HVF VM with no guest kernel, syscalls trapped to host": Noah (Intel, 2017), Carrick/elfuse/alvm (Apple Silicon, 2024-2026). Carrick runs the guest at EL0 under a tiny guest-EL1 vector that forwards via `hvc #2`. — [Noah slides](https://events.static.linuxfound.org/sites/events/files/slides/Noah%20Hypervisor-Based%20Darwin%20Subsystem%20for%20Linux.pdf); [Carrick site](https://carrick-website.pages.dev/)
- Go uses libSystem for syscalls on Darwin, and Hypervisor.framework is a C API (consumed via cgo/Objective-C in Go projects such as Code-Hex/vz). — [Go 1.12 release notes](https://go.dev/doc/go1.12)

### Inferences (effort estimate per model)
- KVM-like (HVF, arm64 only): feasible. The gVisor KVM platform's structure (map the Sentry's address space into the guest, run the Sentry at EL1 in the guest with its own stage-1 page tables, run apps at EL0, exit to host for host syscalls) maps to: `hv_vm_map` of the Sentry's mmap'd regions (16 KB aligned, or `hv_vm_allocate`), `hv_vcpu_create` per locked OS thread, `HV_REG_CPSR` + `hv_vcpu_set_sys_reg` to enter EL1 with `TTBR0/TTBR1/TCR/SCTLR` set, `hvc #imm` (imm != 0 to avoid SMCCC interception) as the "redpill" to return to host, `hv_vcpus_exit` as the preemption kick, `hv_vm_protect` for permission changes, and syndrome decoding of `EC 0x24/0x20` for guest faults. Unlike the Linux KVM platform, the Sentry's own host syscalls while in guest mode cannot be issued directly (there is no host kernel beneath the guest EL1); every host syscall needs an explicit exit (HVC) and host-side execution, which is what the Linux KVM platform already does for syscalls from "bluepilled" code. Estimated size: on the order of libkrun's macOS layer (a few thousand lines) for the platform itself, plus the host-primitive ports.
- ptrace-like: not implementable (no SYSEMU, no register access, no syscall stops; untrusted `svc` reaches XNU directly).
- systrap/seccomp-like: not implementable (no seccomp; no way to turn a syscall into a trap).
- The largest risks are page size (16 KB vs gVisor's 4 KB assumptions), unmeasured exit latency, Go runtime interaction with thread-bound vCPUs and SIGURG, and CI (no hosted HVF).

### Gaps
- No existing Go project was found that drives Hypervisor.framework directly (Code-Hex/vz wraps the higher-level Virtualization.framework); cgo cost per `hv_vcpu_run` exit is unmeasured.
- Whether a Go binary can call HVF without cgo (e.g. via dlopen/purego) was not researched.
