## Q1. Go runtime on darwin: libSystem trampolines vs raw `svc`, and what happens to gVisor's `RawSyscall6` users

### Takeaway
On darwin the Go runtime and every `//sys`-generated wrapper in `syscall`/`x/sys/unix` call libSystem through assembly trampolines (`libcCall` + `//go:cgo_import_dynamic ... "/usr/lib/libSystem.B.dylib"`). However the *exported* `syscall.Syscall/RawSyscall{,6}` (and therefore `unix.Syscall/RawSyscall{,6}`) on darwin/arm64 still execute a literal `SVC $0x80` with a BSD syscall number in R16 — they work, but Apple does not support direct syscalls and Go moved off them in 1.12 "ensuring forward-compatibility". gVisor's own `pkg/hostsyscall` assembly issues Linux-style `SVC` with Linux numbers and must be replaced on darwin.

### Cited Findings
- Go 1.12: "`libSystem` is now used when making syscalls on Darwin, ensuring forward-compatibility with future versions of macOS and iOS. The switch to `libSystem` triggered additional App Store checks for private API usage." — [Go 1.12 release notes](https://go.dev/doc/go1.12). Tracking issue: [golang/go#17490](https://golang.org/issue/17490) (search summary: Apple "recommends against doing direct system calls that Go 1.11 and earlier did").
- `x/sys` removed its pre-1.12 direct-syscall darwin files: "unix: drop support for pre-1.12 direct syscalls on darwin" — [golang/sys commit 6fcdbc0](https://github.com/golang/sys/commit/6fcdbc0bbc04dcd9e7dc145879ceaf9bf1c6ff03).
- Mechanism (Go 1.27.3, `runtime/sys_darwin.go`): "`syscall_rawsyscalln` is a wrapper around the libc call with variable arguments. The scheduler is not notified about the system call." It builds a `libcCallInfo{fn, n, args}` and calls `libcCall(abi.FuncPCABI0(syscallN_trampoline), ...)`; the file has 47 `//go:cgo_import_dynamic libc_* ... "/usr/lib/libSystem.B.dylib"` lines (mmap, munmap, madvise, mlock, pthread_create, sigaction, ...) — [runtime/sys_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/sys_darwin.go). `sys_darwin_arm64.s` header: "System calls are implemented in libSystem, this file contains trampolines that convert from Go to C calling convention." — [runtime/sys_darwin_arm64.s](https://github.com/golang/go/blob/go1.27.3/src/runtime/sys_darwin_arm64.s).
- `syscall` package internals on darwin take a *function pointer*, not a number: `func syscall(fn, a1, a2, a3 uintptr)`, `rawSyscall(fn, ...)` with `//go:nosplit //go:norace //go:uintptrkeepalive`, comment: "//go:norace, on RawSyscall, to avoid race instrumentation if RawSyscall is called after fork, or from a signal handler." Generated wrappers call e.g. `syscall(abi.FuncPCABI0(libc_read_trampoline), fd, p, n)`. These unexported symbols are deliberately kept `//go:linkname`-able for x/sys and others ("hall of shame ... github.com/tetratelabs/wazero ... See go.dev/issue/67401") — [syscall/syscall_darwin.go lines 361-445](https://github.com/golang/go/blob/go1.27.3/src/syscall/syscall_darwin.go).
- BUT the exported numeric API is still raw: `syscall/asm_darwin_arm64.s`: `TEXT ·RawSyscall(SB),NOSPLIT,$0-56 / MOVD trap+0(FP), R16 // syscall entry / ... / SVC $0x80 / BCC ok`; `·Syscall` is identical plus `runtime·entersyscall/exitsyscall` — [syscall/asm_darwin_arm64.s](https://github.com/golang/go/blob/go1.27.3/src/syscall/asm_darwin_arm64.s). `x/sys/unix/asm_bsd_arm64.s` (`//go:build (darwin || freebsd || netbsd || openbsd) && gc`): `TEXT ·RawSyscall6(SB) ... JMP syscall·RawSyscall6(SB)` — [x/sys asm_bsd_arm64.s](https://cs.opensource.google/go/x/sys/+/master:unix/asm_bsd_arm64.s). `x/sys/unix/zsysnum_darwin_arm64.go` still ships BSD numbers (e.g. `SYS_KILL = 37`, `SYS_SIGACTION = 46`, `SYS_MPROTECT = 74`, `SYS_MMAP = 197`) — [zsysnum_darwin_arm64.go](https://cs.opensource.google/go/x/sys/+/master:unix/zsysnum_darwin_arm64.go).
- No "Deprecated:" marker exists on `syscall.RawSyscall` in Go 1.27.3's `syscall/syscall_darwin.go` (lines 20-23 are bare declarations) — [syscall/syscall_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/syscall/syscall_darwin.go).
- gVisor today: `pkg/hostsyscall/hostsyscall_arm64.s` does `MOVD trap+0(FP), R8 // syscall entry ... SVC` with Linux errno convention (`CMN $4095, R0`), and `pkg/sentry/platform/kvm`, `pkg/safecopy`, `pkg/sighandling`, `pkg/sentry/platform/systrap` together contain 131 `hostsyscall.RawSyscall*`/`unix.RawSyscall*` call sites (local grep, `/home/jing/workspace/gvisor/pkg/hostsyscall/hostsyscall_arm64.s`).
- A darwin stub already exists: `pkg/sighandling/sighandling_darwin.go` returns "IgnoreChildStop not supported on Darwin" / "ReplaceSignalHandler not supported on Darwin"; `tools/bazeldefs/go.bzl` has `select_goos()` with a `darwin` arm (local files).
- cgo cost: Go issue 42469 measured a simple cgo call at ~49-51 ns (Windows/Ryzen), ~60 ns on a laptop, dominated by `entersyscall/exitsyscall` — [golang/go#42469](https://go.dev/issue/42469); Go 1.26 notes claim faster cgo calls with "~30% lower baseline overhead" (not darwin-specific) — [Go 1.26 release notes](https://go.dev/doc/go1.26).

### Inferences
- Raw `svc #0x80` from Go on darwin is mechanically possible (the stdlib still does it) but is an unsupported ABI per Apple and the Go team's own rationale for 1.12; a port should route all host calls through libSystem trampolines (either `x/sys/unix` wrappers, or project-owned `//go:cgo_import_dynamic` + `syscall.syscall6` linknames, exactly as purego and `crypto/x509/internal/macos` do — see Q2).
- The darwin libc path means a "syscall" from a signal handler is a C call into libSystem: it is `nosplit`, does not touch the scheduler (`rawsyscalln`), but it is not guaranteed async-signal-safe for every libc function; the set gVisor uses in handlers (sigreturn-like work, `write`, `mprotect`, `tgkill`) needs individual review. On darwin there is no `rt_sigreturn` to call manually; the libc `sigtramp` handles return.
- `hostsyscall`'s Linux `SVC`/R8 convention cannot be reused: darwin uses R16 for the number, `SVC $0x80`, carry-flag errno, and different numbers.

### Gaps
- I found no Go issue proposing to deprecate or remove the raw `syscall.Syscall/RawSyscall` darwin path; status as of Go 1.27.3 is "still present, still raw". Treat as unspecified.
- No measurement of libSystem-trampoline overhead vs raw `svc` on Apple Silicon was found.

## Q2. Calling Hypervisor.framework from Go: cgo vs cgo-free, thread affinity, bindings, signing

### Takeaway
HVF is a C framework; Go can call it either with cgo (`-framework Hypervisor`) or cgo-free via `//go:cgo_import_dynamic` + assembly trampolines (the exact mechanism Go's own `crypto/x509/internal/macos` uses for Security.framework, and that purego generalizes). vCPUs are thread-bound (`hv_vcpu_create` "for the current thread"; "The owning thread must call" `hv_vcpu_run`), which maps onto `runtime.LockOSThread`. No maintained hand-written Go HVF binding exists; `github.com/tmc/apple/hypervisor` (generated, v0.6.18, Aug 2026) covers the arm64 API. Any binary needs `com.apple.security.hypervisor`, applied by re-signing the Go linker's ad-hoc signature with `codesign --entitlements ... -s -`; tests are signed via `go test -exec`.

### Cited Findings
- Entitlement: "The entitlement is required to use the Hypervisor APIs in any process." Boolean, macOS 11.0+; deployment targets <= 10.15 also need deprecated `com.apple.vm.hypervisor` — [Apple: com.apple.security.hypervisor](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hypervisor).
- Thread affinity: `hv_vcpu_create` "Creates a vCPU instance for the current thread."; `hv_vcpu_destroy` "Destroys the vCPU instance associated with the current thread." — [Apple: hv_vcpu_create](https://developer.apple.com/documentation/hypervisor/hv_vcpu_create(_:_:_:)). `hv_vcpu_run`: "Call blocks until the next exit of the vCPU. The owning thread must call this function." (macOS 11+) — [Apple: hv_vcpu_run](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run(_:)). Hyperlight's HVF backend: "Cancellation uses `hv_vcpus_exit`, the only HVF call allowed from a non-owning thread" and "HVF allows only one VM per process and has no cross-process mapping API" — [hyperlight PR #1681](https://github.com/hyperlight-dev/hyperlight/pull/1681). `hv_vm_create`: "Creates a VM instance for the current process." — [Apple: Hypervisor on Apple silicon](https://developer.apple.com/documentation/hypervisor/apple-silicon).
- Go side: "A goroutine should call LockOSThread before calling OS services or non-Go library functions that depend on per-thread state." and "If the calling goroutine exits without unlocking the thread, the thread will be terminated." — [runtime/proc.go LockOSThread](https://github.com/golang/go/blob/go1.27.3/src/runtime/proc.go).
- cgo-free framework calls are a supported compiler feature: compiler allows `//go:cgo_import_dynamic` outside cgo-generated files ("This is permitted for general use because Solaris code relies on it in golang.org/x/sys/unix and others"), with the library path validated by `safeArg`; all other `//go:cgo_*` pragmas are rejected ("For security, we disallow //go:cgo_* directives other than cgo_import_dynamic outside cgo-generated files") — [cmd/compile/internal/noder/noder.go](https://github.com/golang/go/blob/go1.27.3/src/cmd/compile/internal/noder/noder.go). Precedent: `crypto/x509/internal/macos/security.go` has 24 lines like `//go:cgo_import_dynamic x509_SecTrustEvaluateWithError SecTrustEvaluateWithError "/System/Library/Frameworks/Security.framework/Versions/A/Security"`, dispatched via `runtime.crypto_x509_syscall` → `libcCall` — [crypto/x509/internal/macos/security.go](https://github.com/golang/go/blob/go1.27.3/src/crypto/x509/internal/macos/security.go), [runtime/sys_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/sys_darwin.go).
- purego: "A library for calling C functions from Go without Cgo"; macOS amd64/arm64 are Tier 1 with `CGO_ENABLED=0`; "This is beta software so expect bugs and potentially API breaking changes"; it ships `internal/fakecgo` adapted from `runtime/cgo` — [ebitengine/purego README](https://github.com/ebitengine/purego/blob/main/README.md).
- Go bindings found: `github.com/penberg/go-osxhv` — cgo, x86 VMX only (HV_X86_*, VMCS), last published Jan 8, 2015, 0 importers — [pkg.go.dev go-osxhv](https://pkg.go.dev/github.com/penberg/go-osxhv) (GitHub repo URL returned 404 when fetched). `github.com/tmc/apple/hypervisor` v0.6.18 published Aug 22, 2026, MIT, "Code generated from Apple documentation. DO NOT EDIT.", exports `HVVmCreate/HVVmMap/HVVmProtect/HVVCPUCreate/HVVCPURun/HVVCPUGetReg/SetReg/GetSysReg/SetSysReg/SIMDFP/SME`, 0 known importers — [pkg.go.dev tmc/apple/hypervisor](https://pkg.go.dev/github.com/tmc/apple/hypervisor). Rust reference binding: `applevisor-sys` 1.0.0 lists the full arm64 surface incl. `hv_vm_config_{get,set}_ipa_granule`, `hv_vm_config_*_ipa_size`, `hv_vm_config_*_el2_*`, `hv_vm_allocate/deallocate`, `hv_vcpus_exit` — [docs.rs applevisor-sys](https://docs.rs/applevisor-sys/latest/applevisor_sys/).
- Signing: Go's linker ad-hoc signs internally linked Mach-O output (`if ctxt.IsInternal() && ctxt.NeedCodeSign() { ... codesign.Sign(...) }`; package `cmd/internal/codesign` "provides basic functionalities for ad-hoc code signing of Mach-O files ... the same ad-hoc signing algorithm as the Darwin linker") — [cmd/link/internal/ld/macho.go](https://github.com/golang/go/blob/go1.27.3/src/cmd/link/internal/ld/macho.go), [cmd/internal/codesign](https://github.com/golang/go/blob/go1.27.3/src/cmd/internal/codesign/codesign.go). Code-Hex/vz (Virtualization.framework; needs `CGO_ENABLED=1`, macOS 12+): "codesign --entitlements vz.entitlements -s - <YOUR BINARY PATH>" — [vz README](https://github.com/Code-Hex/vz/blob/main/README.md); its tests run `go test -p 1 -exec "go run $(PWD)/cmd/codesign" ./... -timeout 2m -v` — [vz Makefile](https://github.com/Code-Hex/vz/blob/main/Makefile). Hyperlight: surrogate "ad-hoc codesigned with the entitlement at extraction time"; a cargo rebuild after signing "discard[ed] the entitlement, so the `test-hvf` recipe now runs test binaries directly after signing" — [hyperlight PR #1681](https://github.com/hyperlight-dev/hyperlight/pull/1681).
- Go 1.16 darwin/arm64 "supports cgo, internal and external linking, c-archive, c-shared, and pie build modes, and the race detector" — [Go 1.16 release notes](https://go.dev/doc/go1.16). Go 1.27 linker: "-macos and -macsdk command-line options ... By default, it selects the oldest supported macOS version (currently 13.0.0) and a recent SDK version (currently 26.2.0)" — [Go 1.27 release notes](https://go.dev/doc/go1.27).
- Go runtime signal handlers on darwin: `setsig` uses `sa_flags = _SA_SIGINFO | _SA_ONSTACK | _SA_RESTART`, handler `sigtramp` (or `cgoSigtramp` when `iscgo`) via libc `sigaction` — [runtime/os_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/os_darwin.go). Signals arriving on a thread with no Go `g` and no cgo: "fatal: bad g in signal handler" (`badsignal`: `if !iscgo && !cgoHasExtraM { ... exit(2) }`) — [runtime/signal_unix.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/signal_unix.go).

### Inferences
- A cgo-free HVF binding is feasible with ~stdlib-only tooling: `//go:cgo_import_dynamic hv_x hv_x "/System/Library/Frameworks/Hypervisor.framework/Versions/A/Hypervisor"`, a tiny ABI0 asm trampoline per function, and `//go:linkname` to `syscall.syscall6`/`syscall.rawSyscall6` (kept linkname-able per the Go source comments). Blocking `hv_vcpu_run` should go through the `entersyscall` variant so the P is released — analogous to how gVisor's KVM platform treats `KVM_RUN` as a blocking ioctl.
- With cgo-free calls, Go's non-cgo signal handling stays in effect (`sigtramp`, not `cgoSigtramp`); all threads are Go-created Ms, so the "bad g" path is not hit. If cgo is used instead, Go switches to `cgoSigtramp` and the extra-M machinery; both are workable but should be chosen once.
- cgo/libc call overhead (~50-60 ns) is negligible against a hypervisor exit (a kernel transition; see Gaps for numbers) — the fixed per-call cost is not the design driver; the exit count is.
- `go test` for an HVF platform needs `-exec <signing wrapper>` (vz pattern), or a Bazel `go_test` wrapper doing the same; Bazel's test runner will need the same hook.

### Gaps
- Apple's doc for `hv_vcpu_run` does not state what happens when a POSIX signal (e.g. Go's SIGURG preemption) is delivered to the thread inside `hv_vcpu_run` (does it return with an exit reason, or is the signal deferred?). Not found; must be tested. gVisor's KVM platform depends on `KVM_RUN` returning `EINTR` on signal.
- No published latency figure for an HVF exit round-trip on M-series hardware was found.
- Whether the hardened runtime (`codesign --options runtime`) is required or merely compatible for HVF-entitled binaries: Apple's entitlement page is silent; vz/hyperlight use plain ad-hoc signatures with entitlements, suggesting hardened runtime is not required (inference).
- `tmc/apple/hypervisor` import mechanism (cgo vs dlopen) could not be confirmed from the truncated pkg.go.dev page.

## Q3. Page size: 16 KiB host pages, HVF IPA granule, and gVisor's 4 KiB assumptions

### Takeaway
Apple Silicon macOS uses 16 KiB pages for user space (`PAGE_MAX_SHIFT 14`; Go reads `hw.pagesize`), so `mmap/mprotect/madvise` are 16 KiB-granular and `hv_vm_map` requires page-aligned host and guest addresses. The CPU supports 4 KiB *and* 16 KiB stage-1 granules (no 64 KiB) on M1, so a gVisor guest kernel can keep 4 KiB application pages; the stage-2 (IPA) granule defaults to the host page size but macOS 26 adds `hv_vm_config_set_ipa_granule(HV_IPA_GRANULE_4KB)` (with a reported double-digit performance cost). gVisor already has a `PageShift` build-variant mechanism (`hostarch_arm64_4k.go`/`_64k.go`), so a 16 KiB build is mechanically straightforward; the Android and Asahi experiences document the app-compat fallout of exposing 16 KiB pages.

### Cited Findings
- XNU arm64: `PAGE_MAX_SHIFT 14`, `PAGE_MIN_SHIFT 12`; userspace `PAGE_SIZE` is `vm_page_size`; kernel page shift is `__ARM_16K_PG__`-dependent — [xnu osfmk/mach/arm/vm_param.h](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/arm/vm_param.h). Apple: "Virtual memory page sizes are different. Fetch the value from the `vm_page_size` global variable." — [Apple: Addressing architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code).
- Go runtime: `physPageSize = getPageSize()` using `sysctl` `hw.pagesize` — [runtime/os_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/os_darwin.go). Go's darwin heap uses `MADV_FREE_REUSABLE`/`MADV_FREE_REUSE` — [runtime/mem_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/mem_darwin.go).
- `hv_vm_map(addr, ipa, size, flags)`: `addr` "must be page-aligned", `ipa` "must be page-aligned", `size` "must be a multiple of the page size", "The host memory must encompass a single VM region, typically allocated with `mmap` or `mach_vm_allocate` instead of `malloc`." macOS 11+ — [Apple: hv_vm_map](https://developer.apple.com/documentation/hypervisor/hv_vm_map(_:_:_:_:)). QEMU asserts `size` against `qemu_real_host_page_size()`/`page_mask` in `hvf_set_phys_mem`/`do_hv_vm_protect` — [QEMU accel/hvf/hvf-all.c](https://gitlab.com/qemu-project/qemu/-/raw/master/accel/hvf/hvf-all.c).
- macOS 26 IPA granule: `hv_vm_config_set_ipa_granule(config, granule)` — "Set the intermediate physical address granule size in virtual machine configuration.", macOS 26.0+ — [Apple: hv_vm_config_set_ipa_granule](https://developer.apple.com/documentation/hypervisor/hv_vm_config_set_ipa_granule(_:_:)). Apple forum announcement: "support for configuring the intermediate physical address (IPA) memory granularity of a VM. This allows for more granular memory mappings, enabling granularity sizes down to 4KB." — [Apple forums: New Virtualization features in macOS Tahoe](https://developer.apple.com/forums/thread/787491). QEMU series (Lucas Amaral, Mar-Apr 2026) adds `-accel hvf,ipa-granule={auto,4k,16k}` ("'auto' defaults to host page size"), calls `hv_vm_config_set_ipa_granule()` with `HV_IPA_GRANULE_4KB`/`HV_IPA_GRANULE_16KB`, "Falls back with a warning on macOS < 26", motivated by `mmap(MAP_FIXED)` failing with EINVAL "where the page size exceeds the guest's (ARM64 with 16KB/64KB pages, macOS ARM64)" — [patchew v5 cover letter](https://patchew.org/QEMU/20260424000544.9617-1-lucaaamaral@gmail.com/). Reviewer Mohamed Mediouni on v1: making 4K the default caused "a double-digit performance hit on compilation workloads" — [patchew v1 thread](https://patchew.org/QEMU/20260309214906.92578-1-lucaaamaral@gmail.com). Hyperlight: "Requires macOS 26 (4 KiB IPA granule; a clear `IpaGranuleUnsupported` error is raised on older systems)"; "Size guard pages to the host page size (16 KiB on Apple silicon) instead of the 4 KiB guest page granule; mprotect requires host-page-aligned ranges." — [hyperlight PR #1681](https://github.com/hyperlight-dev/hyperlight/pull/1681).
- Hardware granules (M1, Icestorm and Firestorm, `ID_AA64MMFR0_EL1 = 0x000012120f100001`): "TGran4: 0x0: 4KB granule", "TGran16: 0x1: 16KB granule", "TGran64: 0xf: No 64KB granule", "PARange: 0x1: 36bits/64GB"; `ID_AA64MMFR1`: "VH: 0x1: Virtualization Host Extensions supported", "HAFDBS: 0x0: Access and Dirty flags not supported" — [M1 ID-register dump (ryo gist)](https://gist.github.com/ryo/f533af313ac9dfd971f682b7ae951d63). Corroborated: Qu Wenruo on LKML, Apple M1 supports only 4K and 16K, no 64K — [LKML 2022](https://lkml.indiana.edu/2201.0/05138.html).
- Asahi Linux: 16K-page breakage is "almost always due to incorrect/incomplete support for 16K pages"; a 4K kernel "requires some very hacky patches, as the IOMMUs only support 16K-aligned pages"; Linux has no per-process page size: "we have no such mechanism in Linux and likely never will"; ELF `LOAD` segments need `ALIGN` >= `0x4000`; `muvm` "is, by default, configured to virtualize a 4K kernel" and x86-64 software runs through "a 4k page size microVM running FEX". Fixed: jemalloc (5.3.1+), Chromium (102+; cppgc `kGuardPageSize` crash fixed 133.0.6943.141), Wine 10.5+, box64 0.2.8+, QEMU/KVM, Redis, Rust, Zig, VS Code...; still broken: hardened_malloc, Waydroid — [Asahi: Broken Software](https://asahilinux.org/docs/sw/broken-software/).
- Android 16 KiB migration lessons: all Play apps targeting API 35+ must support 16 KB; "Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates"; measured gains: app launch under memory pressure -3.16% avg (up to 30%), power during launch -4.56%, boot +8%; failures come from hardcoded `PAGE_SIZE`/4096, ELF `LOAD` align < `2**14`, `GNU_RELRO` end not 16K-aligned (adjacent `.data` becomes read-only → SIGSEGV), `mmap` offset assumptions, and custom allocators ("a single 16-byte live object pins an entire 16 KB page"); a "16 KB backcompat mode" exists for 4K-aligned apps — [Android: Support 16 KB page sizes](https://developer.android.com/guide/practices/page-sizes).
- gVisor today: `pkg/hostarch/hostarch_x86.go` `PageShift = 12`; `hostarch_arm64_4k.go` `PageShift = 12`, `HugePageShift = 21`; `hostarch_arm64_64k.go` `PageShift = 16`, `HugePageShift = 29`; each has `init()` warning "host page size mismatch" via `unix.Getpagesize()`; `pkg/hostarch/BUILD` selects between them (local files). `ring0` amd64: `UserspaceSize = 1 << (VirtualAddressBits-1)`, `MaximumUserAddress = (UserspaceSize-1) &^ (PageSize-1)`; `kvm/physical_map.go` builds regions up to `ring0.MaximumUserAddress` (local files `/home/jing/workspace/gvisor/pkg/ring0/lib_amd64.go`, `/home/jing/workspace/gvisor/pkg/sentry/platform/kvm/physical_map.go`).

### Inferences
- Two viable designs: (a) **16 KiB everywhere**: build gVisor with `PageShift = 14` on darwin/arm64 (adding `hostarch_arm64_16k.go` alongside the existing 4k/64k variants); host mmap/mprotect/madvise, `hv_vm_map`, and guest stage-1 all agree; applications see 16 KiB pages and inherit the Android/Asahi compatibility profile (jemalloc <5.3.1, old Chromium, 4K-aligned ELF `LOAD`s, hardcoded 4096 all break; most mainstream software has been fixed since 2022-2025). (b) **4 KiB guest over 16 KiB host**: keep `PageShift = 12` for the application view (TGran4 is supported, so the ring0 EL1 stage-1 tables can use 4K), but every host-side operation that backs memory (Sentry `mmap`, `mprotect` for `safecopy`, `madvise` for reclaim, `hv_vm_map/protect`) must be rounded to 16 KiB, which breaks gVisor's current assumption that host and guest page sizes are equal (MemoryFile allocation, `mincore`, decommit granularity). Option (b) also wants `HV_IPA_GRANULE_4KB` (macOS 26+) only if guest-physical mappings themselves need 4K granularity; with a 16K IPA granule the Sentry can still present 4K pages to apps because stage-1 is independent of stage-2.
- Memory accounting changes with 16K: minimum RSS per touched page quadruples; gVisor's MemoryFile and page-cache reclaim heuristics tuned for 4K would need re-evaluation (Android's allocator guidance applies to the Sentry's own allocators too).
- The 36-bit PARange reported by M1 (64 GiB physical) is irrelevant to IPA sizing per se, but `hv_vm_config_get_default_ipa_size`/`get_max_ipa_size` exist, so a KVM-style "map the whole host VA into guest PA 1:1" design must check the IPA size limit rather than assume a 47-bit guest-physical space.

### Gaps
- Apple does not document the default or maximum IPA size for HVF VMs, nor the exact enum values of `hv_ipa_granule_t` (QEMU patches name `HV_IPA_GRANULE_4KB`/`16KB`). Confirm with `hv_vm_config_get_default_ipa_size`/`get_max_ipa_size` at runtime.
- No Apple statement was found confirming that a guest may program `TCR_EL1.TG0 = 4K` under HVF; evidence is indirect (4K Linux distro kernels run in VZ/HVF; Hyperlight's "4 KiB guest page granule"; Asahi muvm 4K guests under KVM). Validate with a probe guest.
- ID register dumps for M2/M3/M4/M5 (TGran, PARange, HAFDBS, MTE) were not found; only M1 is cited.
- Whether `mincore`/`madvise(MADV_FREE_REUSABLE)` semantics on darwin match what gVisor expects from Linux `MADV_DONTNEED`/`MADV_REMOVE` was not researched.

## Q4. W^X, Hardened Runtime, MAP_JIT, and whether the host needs PROT_EXEC for guest code

### Takeaway
On Apple Silicon no process may hold a page that is simultaneously writable and executable; W+X needs `mmap(MAP_JIT)` and per-thread `pthread_jit_write_protect_np` toggling, and the `allow-jit` entitlement only matters for Hardened-Runtime binaries. For a gVisor HVF platform this is mostly moot: guest execute permission is expressed through `HV_MEMORY_EXEC` on the stage-2 mapping, and QEMU maps guest RAM from plain RW host memory without ever calling `mprotect(PROT_EXEC)` on the host side.

### Cited Findings
- "Apple silicon enables memory protection for all apps, regardless of whether they adopt the Hardened Runtime. Intel-based Mac computers enable memory protection only for apps that adopt the Hardened Runtime." "When this entitlement [allow-jit] is present, the system allows your app to call `mmap` with the `MAP_JIT` flag. If you don't have this entitlement, calls using that flag return an error." "The `com.apple.security.cs.allow-jit` entitlement is required only when an app adopts the Hardened Runtime capability. If you don't adopt this capability, you don't need the entitlement to use the `MAP_JIT` flag." Hardened Runtime + allow-jit: "it can only create one memory region with the `MAP_JIT` flag set." `pthread_jit_write_with_callback_np` "Makes the memory region writable, and not executable, for the current thread only." "Always call `sys_icache_invalidate` before you execute the machine instructions on a recently updated memory page. On Apple silicon, the instruction caches aren't coherent with data caches" — [Apple: Porting JIT compilers to Apple silicon](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon).
- "Update the workflow of any just-in-time compilers to support Apple silicon, which prevent all memory pages from being simultaneously writable and executable." — [Apple: Addressing architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code).
- `hv_memory_flags_t`: `HV_MEMORY_READ`, `HV_MEMORY_WRITE`, `HV_MEMORY_EXEC`; "Set with the `hv_vm_map` and `hv_vm_protect` functions." — [Apple: hv_memory_flags_t](https://developer.apple.com/documentation/hypervisor/hv_memory_flags_t).
- QEMU maps guest RAM with `flags = HV_MEMORY_READ | HV_MEMORY_EXEC | (writable ? HV_MEMORY_WRITE : 0)` and write-protects for dirty logging with `HV_MEMORY_READ | HV_MEMORY_EXEC`; the file "never calls `mprotect` and never uses `PROT_EXEC`" — [QEMU accel/hvf/hvf-all.c](https://gitlab.com/qemu-project/qemu/-/raw/master/accel/hvf/hvf-all.c).
- x/sys darwin constants: `MAP_JIT = 0x800`, `MAP_RESILIENT_CODESIGN = 0x2000`, `PROT_EXEC = 0x4`, `MAP_ANON = 0x1000`, `MAP_SHARED = 0x1`, `MAP_FIXED = 0x10` — [x/sys zerrors_darwin_arm64.go](https://cs.opensource.google/go/x/sys/+/master:unix/zerrors_darwin_arm64.go).

### Inferences
- gVisor's ring0 kernel text executed at EL1 inside the VM is just bytes in host memory mapped with `HV_MEMORY_EXEC`; the host-side mapping can stay RW (QEMU precedent). Page tables are data. So W^X does not block the platform design unless the Sentry itself generates host-executable code (it does not today).
- The KVM platform's trick of mapping the Sentry's *own* text/data (the whole process VA) into guest physical space requires `hv_vm_map` on regions that include the signed, R-X `__TEXT` segment; Apple says the host range must be "a single VM region", so a 1:1 whole-VA map must be done region-by-region (as `physical_map.go` already does from `/proc/self/maps`; darwin needs `mach_vm_region`/`proc_regionfilename`-style enumeration instead).
- A plain `mmap(PROT_READ|PROT_WRITE|PROT_EXEC)` without `MAP_JIT` should be expected to fail or be downgraded on Apple Silicon (Apple: W+X "prevent[ed] ... for all apps"); gVisor should simply not request it.

### Gaps
- Apple does not document whether `hv_vm_map` with `HV_MEMORY_EXEC` requires or forbids host-side `PROT_EXEC`, nor whether mapping a code-signed `__TEXT` region into a guest is permitted; QEMU's RW-only usage is the strongest evidence. Test needed.
- Exact errno/behaviour of RWX `mmap` without `MAP_JIT` on current macOS was not found in Apple docs.

## Q5. Maximum user virtual address space on macOS vs gVisor's 47-bit assumptions

### Takeaway
macOS limits user VA to just under 2^47 on both architectures: arm64 `MACH_VM_MAX_ADDRESS = 0x00007FFFFE000000` (2^47 minus 32 MiB) and x86_64 `VM_MAX_PAGE_ADDRESS = 0x00007FFFFFE00000` (2^47 minus 2 MiB). This matches gVisor's 47-bit `UserspaceSize` model closely; the subtraction at the top is the only delta, and the 1:1 host-VA→guest-PA scheme must respect the HVF IPA size limit rather than the host VA limit.

### Cited Findings
- arm64 macOS: `MACH_VM_MAX_ADDRESS_RAW 0x00007FFFFE000000ULL` under `XNU_PLATFORM_MacOSX || XNU_PLATFORM_DriverKit` (iOS: `0x0000000FC0000000ULL` unless `EXTENDED_USER_VA_SUPPORT`); `MACH_VM_MIN_ADDRESS_RAW 0x0` — [xnu osfmk/mach/arm/vm_param.h](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/arm/vm_param.h).
- x86_64 macOS: `VM_MAX_PAGE_ADDRESS ((user_addr_t) 0x00007FFFFFE00000ULL)`, `MACH_VM_MAX_ADDRESS = VM_MAX_PAGE_ADDRESS`; `I386_PGBYTES 4096` — [xnu osfmk/mach/i386/vm_param.h](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/i386/vm_param.h).
- gVisor amd64: `UserspaceSize = 1 << (VirtualAddressBits-1)` with `VirtualAddressBits` clamped to 48 (so 2^47), `MaximumUserAddress = (UserspaceSize-1) &^ (PageSize-1)`, `KernelStartAddress = ^0 - (UserspaceSize-1)`; `kvm.go` reports `MaxUserAddress = ring0.MaximumUserAddress`; `physical_map.go` adds a valid region `[lastSpecialEnd, MaximumUserAddress)` and truncates regions beyond it (local files `/home/jing/workspace/gvisor/pkg/ring0/lib_amd64.go:97-106`, `/home/jing/workspace/gvisor/pkg/sentry/platform/kvm/physical_map.go:222-255`).
- HVF exposes `hv_vm_config_get_default_ipa_size`, `hv_vm_config_get_max_ipa_size`, `hv_vm_config_set_ipa_size` — [docs.rs applevisor-sys function list](https://docs.rs/applevisor-sys/latest/applevisor_sys/).

### Inferences
- Applications under gVisor on macOS can be offered the same 47-bit layout as on Linux (the guest's stage-1 is gVisor's), but Sentry-side `mmap` hints at or above `0x00007FFFFE000000` will fail on the host, so `MaximumUserAddress`-adjacent regions (gVisor's "special regions" near the top of the KVM physical map) need a darwin-specific bound.
- The guest-physical window available for the 1:1 map is bounded by the IPA size returned by HVF, which may be smaller than 47 bits; `physical_map.go` must be driven by that query on darwin.

### Gaps
- Default/max IPA size values on M1-M5 were not found in Apple documentation.
- Whether `mmap(MAP_FIXED)` at arbitrary 16K-aligned addresses below the limit is honoured on macOS the way gVisor relies on under Linux (no ASLR reservations in the way) was not verified.

## Q6. Rosetta 2 and running amd64 Linux binaries under a native Apple Silicon gVisor

### Takeaway
Rosetta for Linux is delivered only as a Virtualization.framework directory share (`VZLinuxRosettaDirectoryShare`, macOS 13+) consumed inside a Linux guest VM; Apple exposes no API to translate x86-64 Linux binaries in a native process or an HVF guest. A native gVisor on Apple Silicon would need a user-space emulator inside the sandbox (FEX or Box64; both are 16K-page compatible per Asahi).

### Cited Findings
- `VZLinuxRosettaDirectoryShare`: "The Linux directory share for Rosetta." "This directory share exposes the Rosetta directory from the host file system to the guest." macOS 13.0+; init "returns an error if Rosetta isn't installed"; includes `installRosetta`, `availability`, AOT `cachingOptions` — [Apple: VZLinuxRosettaDirectoryShare](https://developer.apple.com/documentation/virtualization/vzlinuxrosettadirectoryshare).
- Asahi/Fedora run x86-64 software via "a 4k page size microVM running FEX"; box64 16K support fixed since 0.2.8 — [Asahi: Broken Software](https://asahilinux.org/docs/sw/broken-software/).
- Apple's JIT guidance marks the Intel transition's end: "If you need to run Xcode on an Intel-based processor, use Xcode 26 or earlier." and Xcode 27 requires adding `x86_64` to `ARCHS` to build Intel slices — [Apple: Porting JIT compilers](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon).

### Inferences
- Rosetta's Linux runtime binary (`/Library/Apple/usr/libexec/oah/RosettaLinux/rosetta`) is only reachable via the VZ share and is designed to be registered through `binfmt_misc` inside a VZ Linux guest; gVisor (which is the "kernel") would have to implement the Rosetta-side ioctl/translation-cache protocol itself and still would not be a VZ VM, so this path is not realistic. FEX/Box64 inside the sandbox is the practical option, with a 4K-page guest view favouring FEX (per Asahi's choice of a 4K microVM).

### Gaps
- Apple's "Running Intel binaries in Linux VMs with Rosetta" article could not be fetched (404 on both doc endpoints tried); its statements on requirements/limitations are not quoted here.

## Q7. Memory primitives available to Go on darwin (mmap, shm, punch-hole, madvise, mach_vm)

### Takeaway
`x/sys/unix` on darwin provides `Mmap/MmapPtr/Munmap/Mprotect/Madvise/Msync/Mlock` plus constants `MAP_ANON|MAP_SHARED|MAP_FIXED|MAP_JIT`, `MADV_FREE_REUSABLE`, `F_PUNCHHOLE`, and `FcntlInt/FcntlFstore(Fstore_t)`, but it has no `Shm_open`, no `Fpunchhole_t` struct, and no memfd (darwin has none). ### Cited Findings

### Inferences
- gVisor's MemoryFile today is a Linux memfd/tmpfs file with `fallocate(PUNCH_HOLE)` for decommit; on darwin the equivalents are an anonymous `MAP_SHARED` mapping or a `shm_open`/unlinked file plus `fcntl(F_PUNCHHOLE)` (struct must be hand-defined: `fpunchhole_t{fp_flags, reserved, fp_offset, fp_length}`) or `madvise(MADV_FREE_REUSABLE)` for anonymous memory. `MAP_SHARED|MAP_ANON` is standard BSD and should work (not separately verified).

### Gaps
- Not verified from a primary source: that `fcntl(F_PUNCHHOLE)` works on anonymous shared memory objects (it is documented for files/APFS); and the behaviour of `mincore` on darwin for gVisor's usage.

## Q10. Signals, faults, and Go assembly on darwin/arm64 (what gVisor's low-level packages must change)

### Takeaway
Go's darwin signal model is the generic Unix one (SA_SIGINFO|SA_ONSTACK|SA_RESTART handlers through libc `sigaction`, SIGURG for preemption, SIGSEGV/SIGBUS → panic only when the fault is in user Go code on the user stack), with one darwin-specific detail: the sigaltstack top page is `mlock`ed. A foreign handler can be installed and chained (the `os/signal` rules), but gVisor's `sigframe`/`safecopy`/`bluepill` assembly encodes Linux `ucontext`/`siginfo` layouts and `rt_sigreturn`, so darwin variants are required. Go's arm64 assembler never uses R18 and gVisor's arm64 assembly does not either, so the Apple platform-register rule is already satisfied; Go's own ABI0 is identical across darwin/linux arm64, and only C-calling-convention trampolines differ (variadic args on the stack).

### Cited Findings
- darwin sigtable: SIGBUS/SIGSEGV `_SigPanic + _SigUnblock`, SIGPIPE `_SigNotify`, SIGURG `_SigNotify + _SigIgn`, SIGEMT `_SigThrow` — [runtime/signal_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/signal_darwin.go). `const sigPreempt = _SIGURG`; `preemptMSupported = true` — [runtime/signal_unix.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/signal_unix.go).
- Panic injection is refused when `gp.throwsplit || gp != mp.curg` ("Either we're in the runtime, or we're running C code. Either way we cannot recover.") → `_SigThrow` — [runtime/signal_unix.go ~line 700](https://github.com/golang/go/blob/go1.27.3/src/runtime/signal_unix.go). `debug.SetPanicOnFault` "allows such programs to request that the runtime trigger only a panic, not a crash ... applies only to the current goroutine"; the error may carry `Addr() uintptr` — [runtime/debug](https://github.com/golang/go/blob/go1.27.3/src/runtime/debug/garbage.go).
- `os/signal`: "Synchronous signals are signals triggered by errors in program execution: SIGBUS, SIGFPE, and SIGSEGV."; for non-Go handlers: "it must use the SA_ONSTACK flag with sigaction. Failing to do so is likely to cause the program to crash"; "If the non-Go code installs a signal handler for any of the synchronous signals (SIGBUS, SIGFPE, SIGSEGV), then it should record the existing Go signal handler. If those signals occur while executing Go code, it should invoke the Go signal handler"; "The non-Go code should not change the signal mask on any threads created by the Go runtime." — [os/signal package doc](https://pkg.go.dev/os/signal).
- Go forwards to pre-existing handlers only via its `fwdSig` table captured at init (`sigfwdgo`), and `setsigstack` rewrites foreign handlers to add `SA_ONSTACK` — [runtime/signal_unix.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/signal_unix.go), [runtime/os_darwin.go setsigstack](https://github.com/golang/go/blob/go1.27.3/src/runtime/os_darwin.go).
- darwin specifics: `mlock(gsignal.stack.hi-physPageSize, physPageSize)` on each M's signal stack (os_darwin.go:331); `sigaltstack_trampoline` comment: "sigaltstack on iOS is not supported and will always run the signal handler on the main stack" — [runtime/os_darwin.go](https://github.com/golang/go/blob/go1.27.3/src/runtime/os_darwin.go), [runtime/sys_darwin_arm64.s](https://github.com/golang/go/blob/go1.27.3/src/runtime/sys_darwin_arm64.s).
- Assembler: `REGPR = REG_R18 // ARM64 platform register, unused in the Go toolchain` — [cmd/internal/obj/arm64/a.out.go](https://github.com/golang/go/blob/go1.27.3/src/cmd/internal/obj/arm64/a.out.go). C-ABI difference on darwin arm64: "arg 3 is variadic, pass on stack" in `open_trampoline` — [runtime/sys_darwin_arm64.s](https://github.com/golang/go/blob/go1.27.3/src/runtime/sys_darwin_arm64.s); Apple: "On `arm64`, the compiler always places variadic parameters on the stack, regardless of whether registers are available." — [Apple: Addressing architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code).
- gVisor arm64 asm never touches R18: only `pkg/ring0/entry_arm64.s` mentions it, in comments "The following registers are not saved: R18, R19." / "not loaded: R18, R19." (local grep). gVisor's arm64/amd64 `.s` inventory (local `find`): `safecopy/{memcpy,memclr,atomic,sighandler}_{amd64,arm64}.s`, `hostsyscall/hostsyscall_*.s`, `ring0/{entry,lib}_*.s`, `ring0/pagetables/pcids_aarch64.s`, `sigframe/sigframe_amd64.s`, `sentry/platform/kvm/bluepill_*.s`, `sentry/platform/{systrap,ptrace}/stub_*.s`, `sentry/time/{vdso,tsc,muldiv}_*.s`, `sentry/hostcpu/getcpu_*.s`, `hosttid/*.tmpl.s`, `goid/*.tmpl.s`, `rawfile/blockingpoll_*.s`, `cpuid/native_amd64.s`, `sentry/arch/fpu/fpu_amd64.s`, `atomicbitops`, `bits`, `sync` fences.

### Inferences
- Needs darwin variants (OS-specific semantics): `hostsyscall` (syscall ABI), `safecopy/sighandler_*.s` + `sigframe` (darwin `ucontext_t`/`mcontext`/`siginfo` layouts differ from Linux; no `rt_sigreturn`), `kvm/bluepill_*.s` (built around Linux signal frames + KVM ioctls; an HVF platform is a new platform rather than a port of `kvm`), `hosttid` (`gettid` → `pthread_threadid_np`), `hostcpu/getcpu` (no `getcpu` syscall on darwin), `sentry/time/vdso_*` (Linux vDSO → darwin commpage/`mach_absolute_time`), `rawfile/blockingpoll` (`ppoll` → `poll`/`kqueue`), `systrap`/`ptrace` (Linux-only platforms). OS-agnostic and reusable as-is: `ring0/entry_arm64.s` (guest EL1 code), `pagetables`, `safecopy/memcpy|memclr|atomic`, `fpu`, `cpuid`, `atomicbitops`, `bits`, `sync`, `goid`, `sentry/time/{tsc,muldiv}`.
- `safecopy`'s Linux approach (own SIGSEGV/SIGBUS handler that rewrites the fault PC) can be reproduced on darwin by installing a handler with `SA_ONSTACK|SA_SIGINFO` through libc `sigaction` that chains to Go's saved handler, exactly what `pkg/sighandling` does on Linux today; the darwin stub must be replaced. Alternatively, `debug.SetPanicOnFault` covers faults in Go code only (not in `nosplit` asm or on g0), so it cannot replace `safecopy`'s handler.
- Because Go's darwin runtime already installs handlers for every signal through libc, gVisor's handler replacement happens after runtime init, so Go's `fwdSig` forwarding does not know about it; gVisor must keep the old (Go) handler and chain, as it does on Linux.

### Gaps
- Darwin `ucontext_t`/`__darwin_mcontext64` layout for arm64 (`__es`, `__ss`, `__ns` sub-structs, `__pad`), needed to write the darwin `sigframe`/`safecopy` handlers, was not fetched (available in xnu `bsd/arm/_mcontext.h`); not quoted here.
- Go's TLS implementation on darwin/arm64 (how `g` is found in `sigtramp`) was not inspected; relevant if any gVisor asm reads `g` via `R28`/TLS.

## Q11. Pointer authentication (arm64e) and memory tagging (MIE/EMTE) on Apple Silicon

### Takeaway
Go builds plain `arm64` (not `arm64e`) binaries, so host-side PAC is not in play; Apple reserves arm64e/PAuth_LR for its own and opt-in binaries (arm64e.x1 on "Macs using the M6 chips or newer"). M1 reports no MTE; an M5 Mac reports `FEAT_MTE: 1` per a developer forum post, with Apple's Memory Integrity Enforcement opt-in and poorly documented for third parties. Neither feature blocks a gVisor port, but exposing PAC/MTE to guests through HVF is undocumented.

### Cited Findings
- Apple: "Mac and iPads with Apple silicon" support arm64e; adoption is "when you build and deploy a binary that targets the arm64e architecture"; failures surface as `KERN_INVALID_ADDRESS ... (possible pointer authentication failure)`; `arm64e.x1`/PAuth_LR devices "include ... Macs using the M6 chips or newer" — [Apple: Preparing your app to work with pointer authentication](https://developer.apple.com/documentation/security/preparing-your-app-to-work-with-pointer-authentication).
- M1 `ID_AA64ISAR1`: "APA: 0x0", "API: 0x2: EnhancedPAC", "GPI: 0x1"; `ID_AA64PFR1`: "MTE: 0x0: Memory Tagging Extension not implemented" — [M1 ID-register dump](https://gist.github.com/ryo/f533af313ac9dfd971f682b7ae951d63).
- M5: a researcher reports `hw.optional.arm.FEAT_MTE: 1` on an M5 Mac (Feb 2026), stack tagging via `-fsanitize=memtag-stack` works, heap tagging only "in soft mode"; no Apple staff reply — [Apple Developer Forums thread 817284](https://developer.apple.com/forums/thread/817284). Sept 2025 commentary: EMTE "not yet available in an M-series chip for Macs" at that time, and apps "have to opt in" — [Eclectic Light Co.](https://eclecticlight.co/2025/09/15/will-macs-get-apples-new-memory-protection/).
- HVF exposes guest feature registers via `hv_vcpu_config_get_feature_reg` (`hv_feature_reg_t`) — [docs.rs applevisor-sys](https://docs.rs/applevisor-sys/latest/applevisor_sys/).

### Inferences
- gVisor's ring0 and the Sentry are unaffected by PAC/MTE on the host because Go emits neither. Inside the guest, gVisor should mask PAC/MTE ID-register bits it does not virtualize (as it does for CPUID on amd64) unless HVF already hides them.

### Gaps
- No Apple documentation found on whether HVF guests see PAuth or MTE, or how PAC keys are context-switched per vCPU.
- No primary Apple statement on whether third-party arm64e binaries are permitted on macOS without boot-args.
