# Prior art and ecosystem context for running gVisor (or Linux-ABI sandboxes) natively on macOS (as of 2026-11-06)

Scope note: findings are split into "Cited Findings" (verified against a fetched page or GitHub API response, URL given) and "Inferences" (my reasoning). GitHub metadata (stars, dates, release tags, line counts) was pulled live via the GitHub API on 2026-11-06 and is cited by repository URL.

## KQ1. gVisor itself: past/current attempts, team position, non-Linux builds, sandboxexec

### Takeaway
gVisor has never officially supported a non-Linux host (upstream says so since 2018), but the October 2026 CNCF-donation blog post names "gVisor-on-Mac" (Wine-like) as an explicit non-commercial goal, and an independent fork (maci0/gvisor, April–May 2026) already runs Alpine Linux on Apple Silicon via a Hypervisor.framework platform with ~17.7k added lines. The netstack (`pkg/tcpip`) has been built and shipped on darwin/windows/BSD for years (Tailscale, Fuchsia, gvisor-tap-vsock), and upstream CI compile-checks it for GOOS=darwin/windows/freebsd/openbsd.

**The maci0/gvisor macOS fork (the only known working port)**
- Repo stats: 7 stars, 1 fork, `pushed_at` 2026-11-05; vs google/gvisor master it is 16 commits ahead, 2,416 behind, touching 283 files with +17,672 / −467 lines. Port commits are dated 2026-05-15 ("port: sentry darwin compatibility layer", "port: Hypervisor.framework platform backend", "port: add macOS sentry binary, test suite, and benchmarks") through 2026-05-28 ("docs: update architecture docs for post-review changes"). — [maci0/gvisor](https://github.com/maci0/gvisor); [compare](https://github.com/google/gvisor/compare/master...maci0:master)
- README-MACOS.md status header: "Functional — full interactive shell with devpts PTY and job control ... gVisor runs on macOS Apple Silicon via Hypervisor.framework. Alpine Linux boots with full shell, networking, package management, and multi-CPU support. 68+ packages installed and tested." Feature table marks Working: HVF platform, ARM64 4-level page tables (4K default, per-MM, COW), fork/exec COW, signals, 14 vCPUs, in-process gofer (lisafs over socketpair) + `--directfs`, TCP/UDP, three host-networking modes (userspace proxy default/no root; utun needs root; vmnet via socket_vmnet daemon), VDSO clock_gettime ~5ns via CNTVCT_EL0, safecopy via Mach exception ports, devpts PTY, MRS ID-register trap-and-emulate, checkpoint/restore. Partial: FEX-Emu x86_64 ("COW fault loop"). Blocked: Java/HotSpot ("HotSpot's AArch64 assembler assuming 4K page alignment"). — [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)
- Architecture: "The port replaces gVisor's KVM platform with a Hypervisor.framework (HVF) platform. The guest runs at EL1 inside an HVF virtual machine. The sentry intercepts syscalls via exception vectors and handles them in Go". Guest EL0 runs the Linux ELF; EL1 exception vectors at IPA 0 either handle a fast-path syscall table (getpid/getppid/getuid/geteuid/getgid/getegid/gettid + sched_yield/getpgid/getsid) via MOVZ+ERET (~0.1 µs, no VM exit) or `HVC #9` to exit to the host (~4 µs). TTBR0 = per-process page tables (ASID-tagged), TTBR1 = shared kernel pages (vectors, per-vCPU state page, dispatch page). Per-vCPU 16K state page holds X0–X30, ESR, SP_EL0, TPIDR_EL0, signal mask, pid/tid/brk/uid. — [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)
- HVF platform package files and sizes: `vcpu_arm64.go` 25.6 KB, `context.go` 18.8 KB, `ipa_allocator.go` 13.1 KB, `pagetable.go` 8.3 KB, `machine.go` 8.0 KB, `address_space.go` 5.5 KB, `kernel_pagetable.go` 5.5 KB, `hvf.go` 5.1 KB, `memory_el1.go` 2.1 KB. `cmd/sentrydarwin/main.go` +1,191 lines; `pkg/sentry/fsimpl/gofer/directfs_inode_darwin.go` +917; `pkg/fdnotifier/fdnotifier_darwin.go` +303 (kqueue); `pkg/safecopy/machexc/machexc_darwin.go` +245; `pkg/rawfile/rawfile_darwin.go` +247. — [maci0/gvisor pkg/sentry/platform/hvf](https://github.com/maci0/gvisor/tree/master/pkg/sentry/platform/hvf)
- Linux→macOS host-API mapping table (selected): `/proc/self/fd/N` → `fcntl(F_GETPATH)`+`open`; `O_PATH` → `O_RDONLY|O_NONBLOCK` or `O_SYMLINK`; `getdents64` → `getdirentries`; `fallocate`/`tee`/`splice` → ENOTSUP; `statx` → `fstat`; `memfd_create` → `tmpfile()+dup+unlink`; `futex` → "Polling + usleep"; `eventfd` → `pipe`; `epoll` → `kqueue`; `recvmmsg/sendmmsg` → loops; `seccomp` → ENOSYS; `gettid` → `SYS_THREAD_SELFID`; `CLOCK_MONOTONIC` 1→6; `SIGBUS` 7→10; `SOCK_SEQPACKET` → `SOCK_STREAM` (macOS AF_UNIX lacks SEQPACKET); memfd seals no-op; flipcall FD donation disabled ("Hangs on macOS"); `mmap(MAP_SHARED)` of quarantined downloaded files rejected by HVF → MAP_PRIVATE; "No cgroups on macOS". Split page model: `GuestPageSize`=4K (syscall-facing) vs host `PageSize`=16K; uses `hv_vm_config_set_ipa_granule(HV_IPA_GRANULE_4KB)` and `TCR_EL1.TG0=4K`; 74/77 Alpine tests pass with the split model. — [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)
- Performance (docs/SYSCALL-SPEEDUP.md): "Non-fast-path guest syscalls take a full HVF VM exit round-trip (~4µs)" vs "On Linux KVM, gVisor handles most syscalls at EL1 without a VM exit (~100ns). The 100x overhead makes syscall-heavy workloads ... ~1600x slower than native" (before fast-paths). Measured: getpid fast-path ~0.1 µs (was ~4 µs, "16M calls/second"); fork+exec ~1.9 ms; VDSO clock_gettime ~5 ns; memory bandwidth ~1.3x native; native macOS getpid ~32 ns. Switch() breakdown for a getpid loop: loadRegisters 496 ns, `hv_vcpu_run` 2,971 ns, saveRegisters 844 ns, total 4,312 ns; "`hv_vcpu_run` is 60-90% of total (Apple VM exit floor, ~3µs minimum)"; register load/save were ~4.5 µs each before batching the cgo calls. Tested on "M4 Pro, macOS 26.4". — [SYSCALL-SPEEDUP.md](https://github.com/maci0/gvisor/blob/master/docs/SYSCALL-SPEEDUP.md)
- Known limitations (g3doc hvf_platform.md): crypto instructions hidden "due to intermittent HVF EC=0 traps during OpenSSL init"; "Fork-heavy workloads: ~50% reliability at 50 concurrent fork+exit operations. HVF can reset vCPU state on cancel (CPSR=0x800003c5, all GP regs zeroed)"; fast-path PID/TID values only correct for init process; FEX-Emu "Blocked by Apple Silicon L3 permission upgrade hardware bug" (author's attribution). — [hvf_platform.md](https://github.com/maci0/gvisor/blob/master/g3doc/architecture_guide/macos/hvf_platform.md)
- MRS trapping (docs/MRS-TRAPPING.md): without EL2, EL0 `MRS` of ID registers traps to EL1 then `HVC` to host; the port uses binary patching MRS→MOV in shadow-copied code pages plus trap-and-emulate via ESR_EL1 (EC=0x18). "EL1 code CAN read ESR_EL1 after EL0→EL1 exception (confirmed May 2026)"; `ELR_EL1/SPSR_EL1/FAR_EL1 return 0 (must use API for these)`. — [MRS-TRAPPING.md](https://github.com/maci0/gvisor/blob/master/docs/MRS-TRAPPING.md)
- Build/signing: `bazel build --config=hvf //cmd/sentrydarwin` with `--@io_bazel_rules_go//go/config:pure=false` (cgo required for Hypervisor.framework); then `codesign --force --sign - --entitlements hvf.plist sentrydarwin` with `com.apple.security.hypervisor`. Test suite: 97 tests (95–97 pass), 19/19 Alpine packages (python3, curl, git, gcc, nginx, sqlite, ...). — [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)

### Inferences
- The upstream team's stance has shifted from "Linux only" (2018) → "help wanted, nobody has time" (2024) → an explicitly stated post-CNCF goal (Oct 2026). A port proposal now has top-cover from the project's own public roadmap language, but there is no evidence of upstream engineering or a design doc; the maci0 fork has not been proposed as a PR and is 2,400+ commits behind master.
- The maci0 fork's measured ~3 µs `hv_vcpu_run` floor is the single most important datapoint: an HVF platform cannot replicate KVM-platform's in-guest EL1 syscall handling unless syscall handling moves into the guest (the fork's "dispatch code page" direction) — otherwise every syscall costs ≥4 µs, which is in the same ballpark as gVisor's systrap/ptrace platforms rather than KVM.
- The 2021-dated darwin stubs (`platforms_darwin.go`, `host_darwin.go` with a #1270 TODO) are almost certainly the "work to get us closer" by kevinGC referenced in #1270; they only make a few packages compile on darwin.
- Netstack portability is a solved problem (compile-checked in CI for darwin/arm64, used by Tailscale and gvproxy on macOS). The non-portable surface is everything host-facing in the Sentry (platform, hostfd, fdnotifier/epoll, memfd/pgalloc, safecopy signals, seccomp, cgroups, gofer/directfs) — exactly the set of `_darwin.go` files the fork had to add.

### Gaps
- No gvisor-users / gvisor-dev mailing-list threads about macOS were found via web search (Google Groups content is not indexed well); unknown whether the topic was discussed there.
- No public "sandboxexec" announcement/blog post was found (only the in-tree experimental README); its platform-support goals are unknown.
- Whether Fuchsia still uses the Go netstack: the mirror exists, but I did not find a source stating current usage (Fuchsia's Rust netstack3 replacement is not verified here).
- No independent (non-author) benchmark or review of the maci0 fork was found; all numbers are self-reported.

## KQ2. Noah (linux-noah/noah): architecture, reach, performance, why it stalled

### Takeaway
Noah (2016–2020, University of Tokyo, C/C++, Intel-only) is the closest historical analog: it ran unmodified Linux ELF binaries in a kernel-less Hypervisor.framework VM per Linux process, trapping syscalls to a host process that translated them to Darwin, reached "apt-get, gcc, vim, Ruby, X apps" with a 16% Linux-kernel-build overhead (VEE 2020), and was archived on 2020-06-09 with the README admitting "Most Linux apps don't work well due to missing system calls."

### Cited Findings
- GitHub: created 2016-04-07, archived, last push 2020-06-09 ("Update README.md"), 1,937 stars, 90 forks, 933 commits, primary language C (14.5 MB C, 3.7 MB C++, 9.6 KB Objective-C by byte count, likely incl. vendored code), dual "MITL/GPL" licence; no GitHub releases; MacPorts version 0.5.1. README: "Noah is a Darwin subsystem for Linux, or 'Bash on Ubuntu on Mac OS X'. Noah is implemented as a hypervisor that traps linux system calls and translates them into Darwin's system calls"; "Noah is an experimental product. Most Linux apps don't work well due to missing system calls"; "Currently, this repository is not actively maintained. It might not run on the latest macOS"; default rootfs Ubuntu 16.04 in `~/.noah/tree`; "macOS Sierra or higher is required". — [linux-noah/noah](https://github.com/linux-noah/noah); [MacPorts](https://ports.macports.org/port/noah/)
- Source layout: `src/{fs,ipc,mm,net,proc,sys}`, `include/linux/{errno,fs,futex,ioctl,ipc,mman,ptrace,random,signal,socket,termios,time}.h`, `include/x86` — x86-only. — [linux-noah/noah tree](https://github.com/linux-noah/noah/tree/master/src)
- 2017 LinuxCon slides (Takaya Saeki, Yuichi Nishiwaki, grad students at U. Tokyo, funded by Japan's MITOH programme): three components — "VT-x Virtual Machines [that] have NO kernel inside it, but directly boot an ELF binary", "Host Noah Processes ... which actually work as Linux compatibility layer", and the VMM API ("Apple Hypervisor Framework in macOS, KVM in Linux"). "A pair of host Noah process and VM corresponds to a Linux application." Memory: guest-virtual 48-bit → guest-physical 39-bit with straight (identity) mapping to avoid "Duplicated Address Translation". VFS mounts: `/Users`, `/dev`, `/tmp` passthrough, `/usr`, `/etc` from `~/.noah/tree`. Claimed advantages: robustness ("Bugs in Noah never cause kernel panic ... let's google 'WSL bluescreen'"), portability ("Syscall calling convention, memory layout, page fault handling rules ... are all configurable"), smooth host interaction. Status 2017: apt-get, pacman, vim, gcc, make, Ruby, binutils, X apps (xeyes, doom 3), sudo, curl, nc, man; "The most easiest way to build Linux kernel on macOS is to use Noah!" — [LinuxCon slides PDF](https://events.static.linuxfound.org/sites/events/files/slides/Noah%20Hypervisor-Based%20Darwin%20Subsystem%20for%20Linux.pdf)
- VEE 2020 paper "A Robust and Flexible Operating System Compatibility Architecture" (Saeki, Nishiwaki, Shinagawa — U. Tokyo; Honiden — Waseda/NII), VEE 2020 Lausanne, 17 March 2020, DOI 10.1145/3381052.3381327: existing compat layers trade robustness (in-kernel) vs flexibility (pure userspace); Noah stays at user level and uses "standardized virtualization interfaces"; "can run many of Ubuntu Linux binary applications"; a Windows prototype "confirmed the generality"; "Noah's overhead on a Linux kernel build was 16%." — [conf.researchr.org VEE 2020](https://conf.researchr.org/details/vee-2020/vee-2020-papers/13/A-Robust-and-Flexible-Operating-System-Compatibility-Architecture)
- Fork on HVF: the Aug 2020 Container Runtime Meetup slides state Apple's framework "does not support fork() with a VM", so Noah does "Save and destroy the VM before fork() • Restore the VM after fork()"; the Windows prototype (NoahW) instead implements COW via shared memory and "Trap page faults in the VMs to implement copy-on-write". — [speakerdeck (Saeki)](https://speakerdeck.com/nullpo_head/noah-a-robust-and-flexible-operating-system-compatibility-architecture)
- An earlier 2017 ACM paper by the same authors, "Bash on Ubuntu on macOS" (DOI 10.1145/3124680.3124733), described the same architecture. — [unpaywall record](https://unpaywall.org/10.1145%2F3124680.3124733)
- The Carrick project (2026) frames itself as "a modern-day `noah`" and describes Noah as "the first userspace Hypervisor.framework translation for Intel Macs", archived. — [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)

### Inferences
- Why it stalled: a two-person, grant-funded student project; x86/VT-x-only design a few months before Apple announced Apple Silicon (June 2020 — the archive date is 2020-06-09); and the long tail of Linux syscalls/semantics that a from-scratch C implementation had to reproduce. gVisor already has that long tail implemented, which is the core argument that a gVisor port is more tractable than Noah was.
- Noah's "VM per Linux process + host fork()" model is exactly what HVF makes painful (no fork with a live VM). gVisor's model (one VM, many address spaces, no host fork for guest fork) sidesteps that — and the maci0 fork confirms COW fork works inside a single HVF VM.
- Noah's 16% kernel-build overhead (mostly compute-bound) is consistent with the "VM exit per syscall" cost being tolerable for compile workloads but not for syscall-heavy ones.

### Gaps
- Per-syscall latency numbers for Noah were "unpublished materials" in the 2017 deck and were not retrieved from the paywalled ACM paper (403).
- The exact count of implemented syscalls was not found.
- No Hacker News thread was located by search.

## KQ3. Other Linux-ABI-on-macOS efforts without a full VM (Carrick, hyper-linux, runm, LKL/containerd, Darling, unikernels)

### Takeaway
2026 produced a new wave of Noah-like userspace-kernel-on-HVF projects for Apple Silicon — most notably Carrick (Rust, ~194k LOC, 1 vCPU per guest thread, 216/338 syscalls, LTP 75%, launched June 2026, AI-assisted) — alongside VM-delegation hybrids (runm) and the older LKL/containerd port (FOSDEM 2021). None is a security sandbox and all are small-team efforts; unikernel toolchains (Unikraft, Solo5/MirageOS, OSv) have at most unofficial HVF forks.

### Cited Findings
- **Carrick** (Apache-2.0 OR MIT, Rust, "about 194,000 lines across 25 crates", Apple Silicon macOS 14+, `brew install --HEAD carrick`): "No VM, no guest kernel, no daemon." Architecture: "Each guest thread gets one host pthread and one HVF vCPU"; guest ARM64 runs at EL0; each `svc #0` traps to the `VBAR_EL1` vector then exits via `hvc #2` to the Rust runtime, which reads x8/x0–x5, translates to Darwin, writes x0, resumes; identity-mapped stage-1 page tables with MMU on "so exclusive loads/stores and mutexes work"; per-subsystem locks (fs, creds, proc, signal, mem); `fork` "quiesces sibling vCPUs, calls the real macOS fork(), and rebuilds HVF vCPUs in parent and child"; epoll→kqueue; synthetic /proc and /sys. Results: Go stdlib 876/880 test binaries; Node.js node-core 5301/5304; libuv 498/507; LTP syscalls 671/893 (75%; mm 42%, ipc 43%); CPython regrtest 425/492. Perf: first boot ~90 ms; fork ~5.7 ms; fork+exec ~7.8 ms "versus about 1 ms native Linux"; process teardown ~175 ms. Limitations: "about 216 of 338 aarch64 syscalls (~64%)"; no ptrace beyond phase 1; host networking only (no `-p`, no isolation); "Not a security sandbox. Guest code runs with the invoking user's privileges"; x86_64 via Rosetta 2 experimental; needs a case-sensitive volume. Other backends in bring-up: Linux/KVM, FreeBSD/bhyve, NetBSD/NVMM. — [carrick-website.pages.dev](https://carrick-website.pages.dev/)
- Carrick launch post (2026-06-05, author @tjfontaine): first commit 2026-05-17, 1,473 commits in ~20 days (~74/day), built with "AI coding agents"; HVF pitfall: "Hypervisor.framework silently consumed some `hvc #0` calls as SMCCC calls when x0 looked like a function ID. Switching to `hvc #2` fixed it"; started with a Big Kernel Lock, replaced after two days; `carrick-hvf` ~10.8k lines, `carrick-mem` (guest page tables) ~4.4k, `carrick-runtime` ~65k; Docker used as the behavioural oracle; the author calls a dead end "highly probable" but useful for low-overhead workloads; "a real Linux kernel in a VM will likely stay more accurate." gVisor is not mentioned. — [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)
- **hyper-linux ("hl")**: search snippet says it "uses the same 1:1 thread-to-vCPU mapping, with a limit of 64 concurrent guest threads"; the site (hyper-linux.pages.dev) did not resolve when fetched. — [search result only](https://hyper-linux.pages.dev/)

### Inferences
- Lessons the newer projects agree on: (1) one HVF vCPU per guest thread is the natural model because Apple maps vCPUs to POSIX threads and allows one VM per process; (2) the identity-mapped-stage-1/EL0 guest + EL1 vector + HVC exit pattern is standard; (3) avoid `hvc #0` (SMCCC interception); (4) fork is the hardest primitive on HVF and either requires host `fork()` plus vCPU rebuild (Noah, Carrick) or in-VM COW address spaces (maci0/gvisor); (5) none provides a security boundary — gVisor's seccomp-based second layer has no macOS equivalent, which matters for gVisor's defence-in-depth story.
- gVisor's differentiator vs Carrick/Noah is a mature Linux ABI implementation (the thing both struggled with); its handicap is that the Sentry's host interface was designed around Linux-only primitives (futex, eventfd, epoll, memfd, seccomp, /proc).

### Gaps
- hyper-linux details are unverified (site unreachable).
- OSv on HVF: no source found either way (search operator limitation; treat as "no evidence of a port").
- No published comparison of Carrick vs gVisor-on-mac exists.

## KQ4. macOS hypervisor/VMM ecosystem a gVisor port would build on (xhyve/hyperkit, libkrun/krunkit, vfkit, vz, QEMU-HVF, Firecracker, language bindings, nested virt)

### Takeaway
Hypervisor.framework (low-level, vCPU-as-thread, cgo/FFI) and Virtualization.framework (high-level, whole-VM, Rosetta and nested-virt features) are the two viable substrates; the mature Go path today is Virtualization.framework via Code-Hex/vz (Lima, vfkit), while direct HVF Go bindings are thin (tmc/apple). Nested virtualization (EL2) is exposed in Virtualization.framework since macOS 15 on M3+ and in Hypervisor.framework since macOS 26 (nVHE-only per QEMU developers), and Firecracker has no macOS plans.

### Inferences
- A Go gVisor HVF platform must use cgo (both HVF bindings and the maci0 fork require `pure=false`); gVisor's current `runsc` is a static pure-Go binary, so build/release tooling changes (Bazel `--config=hvf`, codesign step) are unavoidable. The maci0 fork's finding that register load/save cost ~4.5 µs each until cgo calls were batched shows cgo transition cost is a first-order design constraint.
- Virtualization.framework is the wrong layer for a gVisor *platform* (it boots whole VMs with devices and a kernel), but the right layer for a "runsc inside a Linux microVM" integration; Hypervisor.framework is the only layer where a kernel-less, gVisor-as-guest-kernel design is possible.
- Nested-virt availability (macOS 15/M3+ in VZ; macOS 26 in HVF) matters for *two* different things: (a) running `runsc --platform=kvm` inside a Linux VM on a Mac, and (b) a hypothetical in-guest EL2 for a gVisor HVF platform to do KVM-style syscall handling without VM exits. The QEMU report that macOS 26.3's nested virt is nVHE-only suggests (b) is immature.

## KQ5. Apple's Containerization framework and `container` CLI; would gVisor compete or integrate?

### Takeaway
Apple's `container` (Swift, Apache-2.0, 51k stars, releases 1.3–1.6.1 in Aug–Oct 2026) runs one lightweight Virtualization.framework VM per container with a Swift `vminitd` init over vsock, sub-second starts, Rosetta for amd64, and requires macOS 26 on Apple Silicon; it never mentions OCI runtimes, runc or gVisor, exposes nested KVM to guests only with a user-built CONFIG_KVM kernel, and its one-VM-per-container isolation is the direct competitor to a native gVisor sandbox on macOS.

### Cited Findings
- apple/container: "a tool for creating and running Linux containers as lightweight virtual machines on a Mac ... written in Swift, and optimized for Apple silicon"; consumes/produces OCI images; requires Apple silicon and macOS 26 ("maintainers typically won't address issues that can't be reproduced on macOS 26"); CLI + `container-apiserver` XPC service; experimental `cluster` subcommand; Apache-2.0; 825 commits, 359 open issues, 51.1k stars, 1.8k forks. Releases: 1.6.1 (2026-10-23), 1.6.0 (2026-10-20), 1.5.0 (2026-09-29), 1.4.1 (2026-09-09), 1.3.1 (2026-08-29). It does not mention runc, gVisor, Kata or any alternative OCI runtime. — [apple/container](https://github.com/apple/container); [releases](https://github.com/apple/container/releases)
- Technical overview: "it runs a lightweight VM for each container that you create" with properties Security ("Each container has the isolation properties of a full VM, using a minimal set of core utilities and dynamic libraries to reduce resource utilization and attack surface"), Privacy (mount only needed data per VM), Performance ("require less memory than full VMs, with boot times that are comparable to containers running in a shared VM"). Integrates Virtualization.framework, vmnet, XPC, launchd, Keychain, unified logging. Per-container helper `container-runtime-linux`. Limitations: "The macOS Virtualization framework implements only partial support for memory ballooning ... memory pages freed to the Linux operating system ... are not relinquished to the host"; macOS 15: vmnet "can only provide networks where the attached containers are isolated from one another", no `container network` commands, possible subnet disagreement. — [docs/technical-overview.md](https://github.com/apple/container/blob/main/docs/technical-overview.md)
- apple/containerization: each container in its own lightweight VM; `vminitd` "exposes a gRPC API over vsock for configuring the runtime and launching processes"; macOS backend `VZVirtualMachineManager` (Virtualization.framework), Linux backend `CHVirtualMachineManager` (cloud-hypervisor + KVM, one process per VM); features: Rosetta 2 for linux/amd64, per-container IPs, vsock agent, virtio-fs shares, virtio-blk; kernel: minimal optimized config, tested from 6.14.9, Kata Containers kernel usable as prebuilt; "Containers reach sub-second start times"; Apache-2.0; 0.1.0 "first official release"; API releases 0.26.4/0.26.5 (Feb 2026), 0.33.3 (2026-06-01). — [apple/containerization](https://github.com/apple/containerization); [releases](https://github.com/apple/containerization/releases)
- Nested virtualization in containers: issue #376 "Virtualization support in containers" (closed 2025-07-30): "Containerization already exposes the nested virtualization capabilities on any SoCs that support it. We should expose a flag on run/create ... The kata kernel we use by default doesn't have kvm on iirc, so a user would need to provide their own kernel". Issue #1222 (2026-02-16, closed 2026-03-25) requests a KVM-enabled default kernel; commenters (Apr 2026) found no prebuilt kernel with CONFIG_KVM=y. — [apple/container#376](https://github.com/apple/container/issues/376); [apple/container#1222](https://github.com/apple/container/issues/1222)
- Secondary coverage: `vminitd` "has no core utilities (like ls, cp), no dynamic libraries, and no libc implementation", cross-compiled from a Mac into a single static Linux executable; Podman engineers reported Rosetta "behaves like a segfault on a 6.13 kernel" (June 2025). — [dev.to WWDC25 summary](https://dev.to/arshtechpro/wwdc-2025-meet-containerization-eei); [devclass 2025-06-11](https://devclass.com/2025/06/11/apples-containerization-will-matter-to-developers-but-podman-devs-complain-of-unfixed-issues/)
- No issues in apple/container or apple/containerization mention gVisor (gh search 2026-11-06). — [apple/container issues](https://github.com/apple/container/issues)

### Inferences
- Integration path: `runsc` could in principle run *inside* an Apple `container` VM only if the guest init (`vminitd`) were taught to exec an OCI runtime — it is not runc-based and has no runtime plug-in; so "gVisor as the OCI runtime inside Apple's VMs" would require upstream Apple changes. The Linux backend (cloud-hypervisor) is more conventional but is Linux-host only.
- Competitive positioning: Apple's pitch is VM-grade isolation with container-like boot time and memory; a native gVisor would compete on (a) no Linux kernel/rootfs image to manage, (b) host-process-like integration (shared filesystem/network namespaces, like Noah/Carrick), (c) lower per-container memory floor. It would lose on fidelity (real Linux kernel) and on amd64 (Rosetta is Virtualization.framework-only; see KQ7).

### Gaps
- No performance measurements (boot time ms, memory per container) from Apple itself were found beyond "sub-second".
- Whether `container` on macOS 26 exposes a `--virtualization` flag by that exact name was not verified from primary docs (only secondary/AI-generated summaries claimed it).

## KQ6. Existing ways to run gVisor on a Mac today (Docker Desktop, OrbStack, Colima/Lima, Podman) and nested virtualization

### Takeaway

- Today's practical "gVisor on a Mac" is: Lima/Colima (or Docker Desktop with the unsupported recipe) → Linux VM → containerd/Docker → `runsc --platform=systrap`. systrap needs only seccomp + SIGSYS, so it works in every one of these VMs on any Apple Silicon generation. `--platform=kvm` needs `/dev/kvm`, which only Lima with `nestedVirtualization: true` (M3+/macOS 15+/vz) is documented to provide; Docker Desktop and OrbStack provide no toggle. - Because the VM-based route already works, the marginal value of a *native* port is not "run containers at all" but: no Linux VM to provision/update, finer host integration, lower memory floor, and sandboxing of macOS-hosted Linux binaries (the Wine-like goal in the CNCF post).

- Whether OrbStack or Docker Desktop use Hypervisor.framework directly vs Virtualization.framework is contested in secondary sources and unverified.
- Docker VMM's exact version history (4.35 vs 4.86) is inconsistent in Docker's own page.

## KQ7. Lessons from Rosetta 2, FEX-Emu, Box64, WINE/Darling relevant to syscall interception on macOS

### Takeaway
Rosetta-for-Linux is a Virtualization.framework-only feature (public `VZLinuxRosettaDirectoryShare`; binary checks and undocumented virtio-fs ioctls block its use under raw Hypervisor.framework; libkrun removed its attempt), so a native gVisor on HVF cannot legally reuse Apple's x86-64 translation and would depend on FEX-Emu/Box64 (~40–70% of native per one 2026 survey) — and the one attempt to run FEX inside gVisor-on-mac is still blocked on a COW/permission fault loop.

### Cited Findings
- Apple: "In macOS 13 and later on Mac computers with Apple silicon chips, the Virtualization framework supports apps using Intel binary translation in ARM Linux virtual machines"; "macOS 27 directly integrates support for Intel binary translation, without needing to install Rosetta." Rosetta is shared into the guest as a directory and registered via binfmt_misc. — [Apple: Running Intel binaries in Linux VMs](https://developer.apple.com/documentation/virtualization/running-intel-binaries-in-linux-vms.md)
- Reverse-engineering notes: Rosetta checks it is running under Virtualization.framework via an ioctl passed through virtiofs ("quite trivial to bypass"); the whole VM runs in TSO mode when the Rosetta share is mapped; early Linux Rosetta was JIT-only. — [threedots.ovh 2022](https://threedots.ovh/blog/2022/06/quick-look-at-rosetta-on-linux/)
- Inoki (2026-02-28): Rosetta intercepts certain syscalls and file reads so `uname`/`/proc/cpuinfo` report x86-64; translation includes static translation at load. — [blog.inoki.cc via mirror](https://hn.jakechampion.name/reader/https://blog.inoki.cc/2026/02/28/Apple-Rosetta-Linux-VM-Secret-en/index.html)
- Shion Tanaka, "Rosetta 2 Support for libkrun: Technical Feasibility and Legal Analysis" (March 2026): Rosetta verifies host is Apple Silicon macOS, the VM uses Virtualization.framework, and Rosetta mode is enabled; uses "undocumented ioctl calls on the virtio-fs device and a challenge-response 'secret exchange'"; prototype under HVF failed with "Rosetta is only intended to run on Apple Silicon with a macOS host"; upstream libkrun removed its approach in a commit "macos: drop Rosetta support"; author rates DMCA §1201 risk "Critical" and concludes Rosetta "cannot be legally integrated into libkrun". Performance (relative to native arm64, author's figures): QEMU user-mode ~20–40%, Rosetta 2 ~70–80%, FEX-Emu ~50–70%, Box64 ~40–57%. — [tnk4on.github.io/libkrun-rosetta](https://tnk4on.github.io/libkrun-rosetta/)
- maci0/gvisor's FEX-Emu doc: FEX loads all shared libraries and starts the interpreter inside gVisor-on-macOS; a `page4KRound` bug that rounded `MAP_FIXED` addresses (breaking ld.so segment placement) was fixed; "A remaining L3 permission fault loop on COW break blocks full execution." — [FEX-EMU.md](https://github.com/maci0/gvisor/blob/master/docs/FEX-EMU.md)
- Darling's lesson (reverse direction): "Linux has no support for foreign syscall emulation", so Darling patches libSystem to redirect syscalls and runs a userspace server. — [Darling docs](https://docs.darlinghq.org/internals/basics/system-call-emulation.html)
- Noah's 2017 deck compared itself to WSL1 (in-kernel LXCore/LXSS picoprocesses), FreeBSD Linuxulator (in-kernel), and Foreign LINUX (dynamic binary translation on Windows, "overhead ... a bit heavy"), claiming only Noah and full VMs need no kernel modification while keeping low overhead "with processor hardware virtualization". — [LinuxCon slides](https://events.static.linuxfound.org/sites/events/files/slides/Noah%20Hypervisor-Based%20Darwin%20Subsystem%20for%20Linux.pdf)

### Inferences
- macOS offers no ptrace-SYSEMU or seccomp-trap equivalent for interposing on a *foreign* ABI in a native process; every project that succeeded (Noah, Carrick, maci0/gvisor) used hardware virtualization to make `svc` trap. This is also why gVisor's systrap/ptrace platforms have no macOS analogue: an HVF platform is the only realistic option.
- amd64 containers are a hard gap for a native HVF-based gVisor: Rosetta is unavailable by design, so the choice is FEX/Box64 inside the sandbox (unproven in gVisor-on-mac) or falling back to a Virtualization.framework Linux VM for amd64 images.

### Gaps
- No primary-source benchmark of FEX-Emu/Box64 on Apple Silicon Linux VMs was found; the 40–70% figures are from one secondary survey.
- Whether Apple's macOS 27 "integrated" Intel translation changes the HVF restriction is unknown.

## KQ8. Entitlements, code signing and distribution precedent for Go binaries using HVF/Virtualization.framework

### Takeaway
Ad-hoc signing (`codesign -s -`) with an entitlements plist is the established and sufficient distribution pattern: Lima's Makefile signs `limactl` and `lima-driver-vz` with `com.apple.security.virtualization` during `make`, which Homebrew's formula simply invokes; krunkit's tap signs with `--force -s -`; re-signing with a Developer ID without a matching provisioning profile *breaks* the entitlement (pkgx/brewkit finding).

### Cited Findings
- Apple: `com.apple.security.hypervisor` — "A Boolean value that indicates whether the app creates and manages virtual machines"; apps targeting macOS 10.15 or earlier also need the older `com.apple.vm.hypervisor`. — [Apple entitlement docs](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hypervisor.md)
- Lima `Makefile` (master): `codesign -f -v --entitlements vz.entitlements -s - $@` after building `limactl` when `GOOS=darwin`, and the same for `lima-driver-vz`; `vz.entitlements` contains `com.apple.security.network.server`, `com.apple.security.network.client`, `com.apple.security.virtualization`. Homebrew's `lima.rb` just runs `make native` (so signing happens inside the Makefile) and installs `_output/bin/*`. — [lima Makefile](https://github.com/lima-vm/lima/blob/master/Makefile); [vz.entitlements](https://github.com/lima-vm/lima/blob/master/vz.entitlements); [Homebrew lima.rb](https://github.com/Homebrew/homebrew-core/blob/HEAD/Formula/l/lima.rb)
- krunkit Homebrew tap formula: `system "codesign", "--entitlements", "krunkit.entitlements", "--force", "-s", "-", "target/release/krunkit"` after `install_name_tool -add_rpath` for libkrun. — [slp/homebrew-krunkit](https://github.com/slp/homebrew-krunkit/blob/main/Formula/krunkit.rb)
- Homebrew `qemu.rb` test block verifies the signature on `qemu-system-x86_64` ("valid on disk", "satisfies its Designated Requirement") to catch clobbered signatures. — [Homebrew qemu.rb](https://github.com/Homebrew/homebrew-core/blob/HEAD/Formula/q/qemu.rb)
- QEMU's 2020 patch series signed with `codesign --entitlements ... --force -s -` (ad-hoc). Lima's `entitlementutil` package notes Homebrew's signing for Intel QEMU was broken as of Aug 2023. — [qemu-arm list 2020-11](https://lists.endsoftwarepatents.org/archive/html/qemu-arm/2020-11/msg00586.html); [pkg.go.dev lima entitlementutil](https://pkg.go.dev/github.com/lima-vm/lima/pkg/qemu/entitlementutil)
- pkgx/brewkit PR #353: re-signing `limactl` with a Developer ID lost the entitlement; fix "force adhoc signing for virtualization/hypervisor entitlements", matching the working Homebrew bottle; "a generic Developer ID without a matching provisioning profile is rejected at runtime". — [pkgxdev/brewkit#353](https://github.com/pkgxdev/brewkit/pull/353)
- Code-Hex/vz README: `codesign --entitlements vz.entitlements -s - <YOUR BINARY PATH>`; bridged networking additionally needs `com.apple.vm.networking` (restricted). — [Code-Hex/vz](https://github.com/Code-Hex/vz)
- Solo5 HVF fork README: "Hypervisor.framework refuses to create a VM without the com.apple.security.hypervisor entitlement, and stripping or some installers can drop it." Carrick: "the binary must be codesigned with the Hypervisor entitlement". maci0/gvisor: `codesign --entitlements cmd/sentrydarwin/entitlements.plist -f --sign - ./sentrydarwin`. — [mirage-hello](https://next.tangled.org/tsiry-sandratraina.com/mirage-hello); [carrick](https://carrick-website.pages.dev/); [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)

### Inferences
- For gVisor, the release pipeline would need a darwin/arm64 cgo build plus an ad-hoc codesign step with `com.apple.security.hypervisor` (not `.virtualization`), and any downstream repackaging (Homebrew bottles, pkgx, Nix) must preserve or re-apply it; strip-after-sign and Developer-ID re-signing are known footguns. `com.apple.vm.networking` (bridged networking) is Apple-restricted, which is why Lima/maci0 use socket_vmnet/utun/userspace proxies instead.

### Gaps
- vfkit's Homebrew formula shows no codesign step in `install`; signing presumably happens in its Makefile (not verified).
- Whether Apple notarization is required for Gatekeeper-friendly distribution of a CLI with the hypervisor entitlement was not researched.

## KQ9. Academic / industry work on user-space kernels or unikernels on macOS via HVF

### Takeaway
Peer-reviewed work is thin: Noah's VEE 2020 paper (and the 2017 APSys-era "Bash on Ubuntu on macOS") is the only academic treatment of a Linux-ABI userspace kernel on Hypervisor.framework found; unikernel projects (Solo5/MirageOS, Unikraft) have unofficial or partial macOS support only, and the LKL/containerd port (FOSDEM 2021) remained a prototype.

### Cited Findings
- VEE 2020 Noah paper (details in KQ2). — [conf.researchr.org](https://conf.researchr.org/details/vee-2020/vee-2020-papers/13/A-Robust-and-Flexible-Operating-System-Compatibility-Architecture)
- Solo5 `hvt` on Hypervisor.framework exists only in the tsirysndr fork (Apple Silicon only, no x86_64 HVF backend, no seccomp-equivalent sandboxing, gdb/dumpcore unported). — [mirage-hello](https://next.tangled.org/tsiry-sandratraina.com/mirage-hello)
- Unikraft: macOS dev environment since 0.14 (Aug 2023); local run on macOS lacks networking (kraftkit #841). — [unikraft/kraftkit#841](https://github.com/unikraft/kraftkit/issues/841)
- LKL-based containerd-on-darwin (Tazaki, FOSDEM 2021) — a library-OS approach reusing the Linux kernel itself rather than re-implementing the ABI. — [FOSDEM 2021](https://archive.fosdem.org/2021/schedule/event/containers_darwin_containerd/)
- libvirt added an `hvf` domain type for Hypervisor.framework (patch series). — [libvirt list](https://lists.libvirt.org/archives/list/devel@lists.libvirt.org/thread/RNWP5CVIIX3D4CST3UAJVAKGQFDEW4I5)

### Inferences
- The design space has three proven shapes on macOS: (1) full Linux VM (Docker/Lima/Apple container — robust, dominant), (2) library-OS reuse of Linux (LKL — fidelity, prototype only), (3) re-implemented Linux ABI in a kernel-less HVF VM (Noah, Carrick, maci0/gvisor — lightweight, fidelity-limited). gVisor is the only mature codebase of shape (3), which is why both the CNCF post and the community fork converge on it.

### Gaps
- No OSv-on-HVF or MirageOS-upstream-on-HVF work found; no academic evaluation of HVF VM-exit latency on Apple Silicon was found (the only numbers are the maci0 fork's ~3 µs `hv_vcpu_run` floor and Carrick's fork/exec timings).
