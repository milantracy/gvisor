# A Hypervisor.framework Platform Puts gVisor Natively on macOS

Native macOS host support for gVisor is feasible, but only in one shape: a new `hvf` platform on Apple Silicon built on Hypervisor.framework, with the ptrace and systrap platforms excluded because XNU exposes no mechanism to intercept a valid syscall from another process ([xnu bsd_arm64.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/arm64/bsd_arm64.c), [ptrace(2)](https://keith.github.io/xcode-man-pages/ptrace.2.html)). The existence proof already exists: the community fork `maci0/gvisor` boots Alpine with a shell, 14 vCPUs, networking and checkpoint/restore on macOS 26 via a Hypervisor.framework platform, at the cost of **+17,672 lines across 283 files** and a fork that is 2,416 commits behind master ([compare](https://github.com/google/gvisor/compare/master...maci0:master), [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)). Upstream has top-cover but no engineering: issue #1270 has been open since 2019 at `priority: p3` / `status: help wanted`, and the October 2026 CNCF-donation post names "gVisor-on-Mac" as an explicit non-commercial goal ([google/gvisor#1270](https://github.com/google/gvisor/issues/1270), [gvisor.dev blog](https://gvisor.dev/blog/2026/10/02/gvisor-cncf/)). The kernel core (`kernel`, `mm`, `vfs`, `tmpfs`, `loader`, `syscalls/linux`, and all 92k lines of netstack) is portable Go; the Linux coupling is concentrated in roughly 20 host mechanisms spread across ~25 leaf packages, nine of which block a demo. A minimal `echo hello` / `dmesg` on an Apple Silicon Mac is on the order of **8–12k new lines**, dominated by a 5–7k-line platform; parity is a multi-quarter programme whose hardest items are not the HVF API (which is close to the KVM subset gVisor uses) but **HVF's binding of each vCPU to the thread that created it** (which breaks the KVM platform's vCPU-rebinding scheme and forces a new vCPU-ownership design), the **16 KiB host page size**, a **fork-measured ~3 µs `hv_vcpu_run` exit** that puts every host exit in systrap's class rather than KVM's in-guest ~100 ns class, the loss of seccomp as a defence layer, amd64 images (Rosetta is unavailable under raw HVF), and CI that must run on bare-metal Macs. The recommended path is a two-week spike on the unknowns that no document answers (exit latency measured in C against a KVM calibration run, `hv_vcpus_exit` kick semantics, vCPU count and lifecycle cost, `hv_vm_map` of read-only and file-backed ranges), a design-review gate on #1270, then a Phase 1 demo built with the fork's "Sentry on host, tiny EL1 vector in guest" model and a 16 KiB `hostarch` variant, then increments ordered by user value: host filesystem, networking, TTY, performance, Seatbelt-based hardening, checkpoint/restore, amd64.

## Only a hypervisor can trap a Linux `svc` on macOS, and only on Apple Silicon

gVisor's three Linux platforms rely on three Linux-only interception primitives, and macOS has none of them. The ptrace platform stops the stub at every syscall with `PTRACE_SYSEMU` ([ptrace/subprocess.go:555-580](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/ptrace/subprocess.go#L555)); systrap turns syscalls into `SIGSYS` with `SECCOMP_RET_TRAP`, uses `SECCOMP_FILTER_FLAG_NEW_LISTENER`, memfd-shared signal stacks and futex wake-ups ([systrap/systrap.go:15-42](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/systrap/systrap.go#L15), [systrap/subprocess.go:193-205](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/systrap/subprocess.go#L193)); KVM runs the Sentry at guest EL1 and the application at EL0 ([kvm/machine_arm64_unsafe.go:59-240](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine_arm64_unsafe.go#L59)). On macOS, `ptrace(2)` documents no syscall-stop, register or memory requests at all ([ptrace(2) man page](https://keith.github.io/xcode-man-pages/ptrace.2.html)), and XNU's arm64 `unix_syscall()` dispatches every valid BSD syscall straight to its handler; `EXC_SYSCALL` is raised only for invalid Mach trap numbers ([xnu bsd_arm64.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/arm64/bsd_arm64.c), [xnu systemcalls.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/dev/arm/systemcalls.c)). There is no seccomp; the only process-confinement facility is Seatbelt (`sandbox_init`) ([vadika KVM→HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)). The consequence is sharper than a performance problem: an untrusted Linux binary executing `svc #0` inside a native macOS process would have its Linux syscall number interpreted by XNU as a Darwin syscall, with nothing to stop it. A stub-process design is therefore a security blocker, not merely slow. Every project that has succeeded at running a Linux ABI on macOS without a guest kernel (Noah in 2017, Carrick and `maci0/gvisor` in 2026) reached the same conclusion and used hardware virtualization to make `svc` trap ([Noah slides](https://events.static.linuxfound.org/sites/events/files/slides/Noah%20Hypervisor-Based%20Darwin%20Subsystem%20for%20Linux.pdf), [Carrick](https://carrick-website.pages.dev/)). One non-hypervisor route deserves naming so that it can be dismissed: a debugger-style stub that inherits Mach exception ports via `posix_spawnattr_setexceptionports_np`, rewrites every `svc` in executable pages to `brk` (sound on fixed-width A64, with W^X forcing new code through intercepted `mmap`/`mprotect`) and emulates on `EXC_BREAKPOINT`, confined by a deny-default Seatbelt profile. It is not obviously insecure, but every syscall becomes a Mach IPC round trip (the fork measured ~14 µs per `brk` through an exception port against ~3 µs for an HVF exit), it has no precedent, and it still leaves the stub's own page faults and signals to Mach semantics; it loses on cost, not on principle.

Hypervisor.framework on Apple Silicon is, fortunately, a thin KVM-shaped API covering exactly the subset gVisor's KVM platform uses. `hv_vm_create` ≈ `KVM_CREATE_VM` (one VM per process), `hv_vm_map/unmap/protect` ≈ `KVM_SET_USER_MEMORY_REGION` with permissions, `hv_vcpu_create` ≈ `KVM_CREATE_VCPU` but bound to the calling pthread, `hv_vcpu_run` ≈ `KVM_RUN` returning a raw ESR_EL2 syndrome, `hv_vcpus_exit` ≈ the signal-based kick, and `hv_vcpu_get/set_reg` + `get/set_sys_reg` ≈ `KVM_GET/SET_ONE_REG` ([Apple Hypervisor overview](https://developer.apple.com/documentation/hypervisor), [Apple hv_vcpu_run](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run(_:)), [vadika KVM→HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)). What HVF lacks relative to KVM (irqfd, ioeventfd, dirty logging, in-kernel PSCI/WFI/timer, a GIC before macOS 15) is almost entirely irrelevant because gVisor uses the VM as a privileged execution context, not a device model; the only casualty is the `KVM_IOEVENTFD` MMIO eventfd optimisation, for which `eventfd.Write` already has a plain `write(2)` fallback ([kvm/ioeventfd.go:32-60](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/ioeventfd.go#L32), [eventfd/eventfd.go:79-95](https://github.com/google/gvisor/blob/f51a205a8/pkg/eventfd/eventfd.go#L79)). The guest runs at EL1/EL0, so the ring0 model (Sentry or a vector stub at EL1, application at EL0, exceptions via `VBAR_EL1`) maps 1:1 ([Apple forums 775546](https://developer.apple.com/forums/thread/775546)). Two HVF pitfalls deserve pre-emptive design decisions: Carrick reports (single source, unconfirmed) that some `hvc #0` calls with an SMCCC-shaped x0 were consumed by HVF, while QEMU's PSCI handling shows that HVC exits for `0x84000000`-range function IDs do reach user space, so the cheap mitigation is to use `hvc #imm` with `imm != 0` for the host-exit hypercall regardless ([Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick), [QEMU hvf.c](https://raw.githubusercontent.com/qemu/qemu/master/target/arm/hvf/hvf.c)); and HVF "generally does not provide a reset state for vCPUs", so the platform must program every system register itself, with the current EL set through `HV_REG_CPSR` ([Apple forums 775546](https://developer.apple.com/forums/thread/775546)).

The port should be **arm64-only**. Intel HVF is a different, older API (`hv_vmx_vcpu_read/write_vmcs`, `hv_vcpu_run_until`, no nested VMX) with a well-known spurious-exit problem ([Apple hv_vcpu_run_until](https://developer.apple.com/documentation/hypervisor/hv_vcpu_run_until(_:_:)), [QEMU thread](https://patchew.org/QEMU/20230922140914.13906-1-phil@philjordan.eu/)), Apple has declared macOS 26 Tahoe the last major release for Intel Macs ([Engadget](https://www.engadget.com/computing/macos-tahoe-is-the-end-of-the-line-for-intel-macs-113036626.html)), and the Go team's own tracking issue calls macOS 26 "the very last macOS version that runs on darwin/amd64 hardware" with no builder plan ([golang/go#78388](https://github.com/golang/go/issues/78388)). Ironically Intel's `hv_vm_space_*` multi-address-space API would have been the natural fit for per-process page tables, but it is absent on Apple Silicon, so the port must use a single IPA space with Sentry-managed stage-1 page tables, exactly as the KVM platform does today ([Apple Intel memory management](https://developer.apple.com/documentation/hypervisor/intel-based_mac-memory-management), [Apple arm64 memory management](https://developer.apple.com/documentation/hypervisor/memory-management)).

## Prior art: a working fork, a stated upstream goal, and strong competition from Apple

The upstream position has moved in three steps. In 2018 a maintainer closed a Mac build issue with "gVisor only supports Linux" ([google/gvisor#16](https://github.com/google/gvisor/issues/16)); in 2024 maintainer kevinGC wrote "No reason it can't be done, it's just that nobody has had the time to do it" ([google/gvisor#1270](https://github.com/google/gvisor/issues/1270)); in October 2026 the CNCF-donation post listed "gVisor-on-Mac: Allowing Linux programs to run on macOS, with a similar experience as to how Wine allows Windows programs on macOS" among the directions that were "difficult to prioritize when guided by corporate ownership alone", with Ant Group, Modal and Tines committed as maintainers ([gvisor.dev blog](https://gvisor.dev/blog/2026/10/02/gvisor-cncf/), [website/blog/2026-10-02-gvisor-cncf.md:91-92](https://github.com/google/gvisor/blob/f51a205a8/website/blog/2026-10-02-gvisor-cncf.md#L91)). The tree carries the residue of kevinGC's 2021-2022 groundwork: `platforms_darwin.go` ("makes the platforms package buildable on Darwin"), `sighandling_darwin.go` whose two functions return "not supported on Darwin" errors, and `syserr/host_darwin.go` with a 107-slot host-errno array and a `TODO(gvisor.dev/issue/1270)` ([platforms_darwin.go:15-20](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/platforms/platforms_darwin.go#L15), [sighandling_darwin.go:28-40](https://github.com/google/gvisor/blob/f51a205a8/pkg/sighandling/sighandling_darwin.go#L28), [syserr/host_darwin.go:26-44](https://github.com/google/gvisor/blob/f51a205a8/pkg/syserr/host_darwin.go#L26)). The platforms BUILD already has `select_system(... darwin = [])` so a darwin platform has a slot to plug into ([platforms/BUILD:25](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/platforms/BUILD#L25)). Netstack portability is a solved problem: Buildkite compile-checks the core `pkg/tcpip` package set for `GOOS=darwin GOARCH=arm64`, windows, freebsd and openbsd on every run, Tailscale ships it on all of them, and `pkg/tcpip/stack` has 801 importers on pkg.go.dev ([.buildkite/pipeline.yaml:171-179](https://github.com/google/gvisor/blob/f51a205a8/.buildkite/pipeline.yaml#L171), [google/gvisor#6839](https://github.com/google/gvisor/issues/6839), [pkg.go.dev](https://pkg.go.dev/gvisor.dev/gvisor/pkg/tcpip/stack)). No upstream design doc, PR or mailing-list thread about a native port exists; the fork's author has opened no PR ([google/gvisor pulls](https://github.com/google/gvisor/pulls)).

The `maci0/gvisor` fork is the single most important datapoint because it settles the "can it work at all" question and exposes the real costs. Its port commits are dated 2026-05-15 through 2026-05-28, and its README reports a "full interactive shell with devpts PTY and job control", 14 vCPUs, ARM64 4-level per-MM COW page tables, an in-process gofer over a socketpair plus `--directfs`, TCP/UDP with three host-networking modes (an unprivileged userspace proxy by default, `utun` needing root, vmnet via `socket_vmnet`), a ~5 ns VDSO `clock_gettime` via `CNTVCT_EL0`, safecopy via Mach exception ports, MRS ID-register trap-and-emulate, checkpoint/restore, and 19/19 Alpine packages (python3, curl, git, gcc, nginx, sqlite) passing ([README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)). Architecturally it diverges from upstream KVM in one decisive way: the Sentry's Go code stays on the host, and the guest contains only the Linux ELF at EL0 plus a small EL1 vector page at IPA 0 that either answers a fast-path table (`getpid`, `gettid`, `getuid`, `sched_yield` and friends, via `MOVZ`+`ERET` in ~0.1 µs without a VM exit) or executes `HVC #9` to exit to the host (~4 µs) ([README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)). Its own measurements explain why that fast-path table exists: a `getpid` round trip breaks down as `loadRegisters` 496 ns, `hv_vcpu_run` 2,971 ns, `saveRegisters` 844 ns, total 4,312 ns, with `hv_vcpu_run` being "60-90% of total (Apple VM exit floor, ~3µs minimum)", and register load/save cost ~4.5 µs *each* until the cgo calls were batched; the doc states plainly that "On Linux KVM, gVisor handles most syscalls at EL1 without a VM exit (~100ns)" ([SYSCALL-SPEEDUP.md](https://github.com/maci0/gvisor/blob/master/docs/SYSCALL-SPEEDUP.md)). Its known limitations are equally instructive, and two of them look like fork bugs rather than HVF behaviour. Crypto instructions are hidden because of "intermittent HVF EC=0 traps during OpenSSL init": ESR `EC=0` is an UNDEFINED instruction at EL0, which is exactly what OpenSSL's `armcap` probe produces when it reads `ID_AA64ISAR0_EL1` with `MRS` from EL0, an access Linux emulates in `do_emulate_mrs` and that the guest EL1 stub must emulate too. Fork-heavy workloads show "~50% reliability at 50 concurrent fork+exit operations" because "HVF can reset vCPU state on cancel (CPSR=0x800003c5, all GP regs zeroed)": that CPSR is the architectural state of a *freshly created* vCPU, and the fork's `hvf/machine.go` creates one vCPU per OS thread lazily, never destroys one outside error paths, caps them at `runtime.NumCPU()` (max 64) and **panics** with "vCPU limit reached" when the cap is hit, so a lifecycle bug is the more parsimonious explanation; no other HVF consumer (QEMU, libkrun, Hyperlight, Carrick) reports state loss on `hv_vcpus_exit` ([hvf_platform.md](https://github.com/maci0/gvisor/blob/master/g3doc/architecture_guide/macos/hvf_platform.md), [maci0 hvf/machine.go](https://github.com/maci0/gvisor/blob/master/pkg/sentry/platform/hvf/machine.go)). HotSpot is blocked on 4 KiB page alignment under the fork's split page model, and FEX-Emu for x86-64 is stuck in a COW permission-fault loop ([FEX-EMU.md](https://github.com/maci0/gvisor/blob/master/docs/FEX-EMU.md)). All of these numbers are self-reported and unreviewed, the fork has 7 stars, and its Linux→macOS mapping table (`memfd_create` → `tmpfile()+dup+unlink`, `futex` → "Polling + usleep", `epoll` → `kqueue`, `SOCK_SEQPACKET` → `SOCK_STREAM`, flipcall FD donation disabled because it "Hangs on macOS") shows several shortcuts that upstream review would not accept as-is ([README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md), [maci0/gvisor](https://github.com/maci0/gvisor)).

The wider ecosystem frames both the opportunity and the risk. Noah (University of Tokyo, 2016-2020) is the exact historical analog: a kernel-less Hypervisor.framework VM per Linux process on Intel Macs, 16% overhead on a Linux kernel build, archived in June 2020 with the admission "Most Linux apps don't work well due to missing system calls" ([linux-noah/noah](https://github.com/linux-noah/noah), [VEE 2020](https://conf.researchr.org/details/vee-2020/vee-2020-papers/13/A-Robust-and-Flexible-Operating-System-Compatibility-Architecture)). Carrick (Rust, June 2026, ~194k lines, one HVF vCPU per guest thread, 216/338 syscalls, 75% of LTP, fork ~5.7 ms, "Not a security sandbox") is the 2026 reincarnation, and its author rates a dead end "highly probable" ([Carrick](https://carrick-website.pages.dev/), [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)). Both struggled with precisely the long tail of Linux semantics that gVisor already implements, which is the core argument that a gVisor port is more tractable than a from-scratch effort; gVisor's handicap is the inverse, a host interface designed around Linux-only primitives. The incumbent on macOS is Apple's own `container` (51k stars, macOS 26 only, one Virtualization.framework VM per container with sub-second boots), which never mentions OCI runtimes or gVisor and offers no runtime plug-in ([apple/container](https://github.com/apple/container), [technical-overview.md](https://github.com/apple/container/blob/main/docs/technical-overview.md)). And gVisor already runs on Macs today, inside a Linux VM: `runsc --platform=systrap` works in Docker Desktop (via an unsupported recipe) and Lima/Colima, and Lima has shipped `nestedVirtualization: true` for `/dev/kvm` on M3+/macOS 15+ since v1.0.0 ([dev.to rimelek](https://dev.to/rimelek/using-gvisors-container-runtime-in-docker-desktop-374m), [lima-vm/lima#2530](https://github.com/lima-vm/lima/pull/2530)). The marginal value of a native port is therefore not "run containers at all" but no Linux VM to provision, finer host integration, a lower memory floor, and the Wine-like sandboxing of Linux binaries that the CNCF post describes.

## The Linux coupling lives in ~20 mechanisms in leaf packages, not in the kernel core

Build tags understate the problem and the import graph overstates it. Only 54 Go files in all of `pkg/` carry an explicit `linux` build tag; the real coupling is implicit, through `golang.org/x/sys/unix` constants and raw syscalls in ~25 packages, and 125 of 369 non-test packages import `unix` (mostly for errno constants that exist on darwin) ([hostsyscall.go:15](https://github.com/google/gvisor/blob/f51a205a8/pkg/hostsyscall/hostsyscall.go#L15), [abi_linux.go:15-19](https://github.com/google/gvisor/blob/f51a205a8/pkg/abi/abi_linux.go#L15)). A scratch build of the `go` branch under `GOOS=darwin GOARCH=arm64` found that **333 of 339 packages load**, the 6 failures tracing to `pkg/hostsyscall` (which blocks `kvm`, `systrap`, `slimvm`, `sysmsg`, `sigframe`) and `pkg/shim/v1/plugin`; before stubbing, *every* Sentry package failed to load through just two leaves, `pkg/rawfile` (via `eventfd → unet`) and `pkg/fdnotifier` (via `socket/unix/transport → vfs`), and after stubbing those two the first compile layer failed in exactly 20 packages, all for Linux-only `unix.*` identifiers ([pkg/fdnotifier/fdnotifier.go:70-102](https://github.com/google/gvisor/blob/f51a205a8/pkg/fdnotifier/fdnotifier.go#L70), [pkg/rawfile/rawfile_unsafe.go:15](https://github.com/google/gvisor/blob/f51a205a8/pkg/rawfile/rawfile_unsafe.go#L15)). The kernel core is clean: `pkg/sentry/kernel` (26k lines) has no linux-tagged file at all (only `!false` and per-arch tags); `fd_table.go`, `seccomp.go` and `task_syscall.go` import `unix` only for errno constants, and `pkg/sync`, `pkg/syncevent` and `kernel/futex` contain no `SYS_FUTEX`, so the in-sentry futex is pure Go ([kernel/BUILD:356-413](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/kernel/BUILD#L356)). `dmesg` itself is entirely synthetic: `syslog(SYSLOG_ACTION_READ_ALL)` returns the easter-egg log from `kernel.syslog.Log()` and `uname` comes from the `UTSNamespace`, neither touching the host ([kernel/syslog.go:38-122](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/kernel/syslog.go#L38), [sys_syslog.go:24-56](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/syscalls/linux/sys_syslog.go#L24)).

## Phase 1: `echo hello` and `dmesg` in 8–12k lines, with four design decisions made up front

The demo path is well defined because `loader_test.go` and `fsimpl/testutil.Boot()` already show the minimal object graph: platform → `MemoryFile` → `Timekeeper` (`NewCalibratedClocks`) → `Kernel.Init` with `FeatureSet`, `RootUserNamespace`, loopback `RootNetworkNamespace` and the embedded vDSO, then VFS with a root filesystem, `devtmpfs` with `memdev`/`ttydev`, and stdio imported through `fsimpl/host` ([loader_test.go:86-118](https://github.com/google/gvisor/blob/f51a205a8/runsc/boot/loader_test.go#L86), [fsimpl/testutil/kernel.go:38-104](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/fsimpl/testutil/kernel.go#L38), [kernel.go:527-596](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/kernel/kernel.go#L527)). The concrete work falls into six buckets.

**Build.** The in-tree sources cannot be compiled with plain `go build` (Bazel generates template instantiations, protobufs and stateify code), so iteration on a Mac either runs Bazel natively with a darwin `--platforms` target (the rules already carry `select_system`/`select_goos` darwin arms and nogo already runs on macOS) or consumes the synthetic `go` branch produced by `//:gopath` + `tools/go_branch.sh`, which can only be regenerated on a Linux+Docker host ([tools/go_branch.sh:48-51](https://github.com/google/gvisor/blob/f51a205a8/tools/go_branch.sh#L48), [BUILD:208-221](https://github.com/google/gvisor/blob/f51a205a8/BUILD#L208), [README.md:124-133](https://github.com/google/gvisor/blob/f51a205a8/README.md#L124)). One trap: `//:gopath` collects transitive dependencies as configured on the Linux host, so a package reachable only through a `select_system(darwin = [...])` arm would be missing from the `go` branch; `platforms_darwin.go` is present only because it is listed unconditionally in `srcs` with a `//go:build darwin` tag, and new darwin files should follow that pattern or be added to the explicit extra-package list at `BUILD:232` ([platforms/BUILD:14-18](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/platforms/BUILD#L14), [tools/bazeldefs/defs.bzl:56-60](https://github.com/google/gvisor/blob/f51a205a8/tools/bazeldefs/defs.bzl#L56)). The guest vDSO is a `-nostdlib` Linux ELF built by `vdso/BUILD` and embedded as `vdsodata.Binary`, so macOS builds need a Linux-targeting cross toolchain or a vendored prebuilt ([vdso/BUILD:44-58](https://github.com/google/gvisor/blob/f51a205a8/vdso/BUILD#L44), [loader/vdso.go:182-209](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/loader/vdso.go#L182)). The binary must then be ad-hoc signed with `codesign -s - --entitlements` carrying `com.apple.security.hypervisor`, which Apple requires "in any process" that calls HVF and which the Go linker's own ad-hoc signature does not include ([Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hypervisor), [cmd/link macho.go](https://github.com/golang/go/blob/go1.27.3/src/cmd/link/internal/ld/macho.go)); `go test` needs a `-exec` signing wrapper as Code-Hex/vz does ([vz Makefile](https://github.com/Code-Hex/vz/blob/main/Makefile)).

**Decision 1: cgo or cgo-free HVF bindings.** The fork requires cgo (`pure=false`) and no maintained hand-written Go HVF binding exists; `tmc/apple/hypervisor` is generated from Apple docs with zero known importers ([README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md), [pkg.go.dev tmc/apple/hypervisor](https://pkg.go.dev/github.com/tmc/apple/hypervisor)). A cgo-free binding is nonetheless a supported compiler path: `//go:cgo_import_dynamic` is explicitly permitted outside cgo-generated files, Go's own `crypto/x509/internal/macos` uses 24 such lines to call Security.framework through `libcCall`, and purego generalises the technique ([noder.go](https://github.com/golang/go/blob/go1.27.3/src/cmd/compile/internal/noder/noder.go), [crypto/x509/internal/macos/security.go](https://github.com/golang/go/blob/go1.27.3/src/crypto/x509/internal/macos/security.go), [purego](https://github.com/ebitengine/purego/blob/main/README.md)). The per-call cost (~50-60 ns for cgo) is noise against a ~3 µs exit ([golang/go#42469](https://go.dev/issue/42469)). The recommendation is **cgo-free, in tree**, for three reasons. First, cgo on darwin needs an Apple SDK and clang at build time, so a cgo `runsc` cannot be produced by gVisor's Linux/Docker `make` pipeline, whereas a cgo-free binary cross-compiles with `GOOS=darwin GOARCH=arm64` and can be ad-hoc signed with entitlements from Linux using `rcodesign`, leaving only tests on Macs. Second, a linkname-based binding lets the platform choose its scheduler interaction: cgo always wraps the call in `entersyscall`/`exitsyscall` (P hand-off after 20 µs), while the KVM platform today linknames `runtime.entersyscall`/`exitsyscall` itself around `SwitchToUser` and could equally choose `entersyscallblock` or nothing ([machine_unsafe.go:37-41](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine_unsafe.go#L37), [machine_arm64_unsafe.go:430-433](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine_arm64_unsafe.go#L430)). Third, gVisor's `nogo` checks (`checkunsafe`, `checklinkname`) can audit an in-tree `pkg/hvf` of about a dozen functions but not an external module, and `//:gopath`/`go.mod` pinning stays simple. The named risks are Go's linkname policy (the `syscall.syscall6`/`rawSyscall6` family is on the allow-list, [go.dev/issue/67401](https://go.dev/issue/67401)), hand-maintained `hv_vcpu_exit_t` and enum layouts (copying numeric constants is not an SDK-licence problem; do not vendor `Hypervisor.h`), and `purego` being beta if used instead of stdlib tricks. cgo remains the fallback. Either way, batch register traffic per exit: the fork's unbatched `hv_vcpu_get/set_reg` calls cost ~4.5 µs per direction, and its batched figures (496/844 ns for ~33 registers) show the individual reads are ~25 ns, so the cost is call count, not HVF ([SYSCALL-SPEEDUP.md](https://github.com/maci0/gvisor/blob/master/docs/SYSCALL-SPEEDUP.md)).

**Decision 2: where the Sentry runs.** Upstream's KVM platform runs the Sentry *inside* the guest at EL1 (bluepill), which is why application syscalls cost ~100 ns and why Sentry host syscalls take a HLT→exit→`sigreturn`→re-execute round trip ([bluepill_amd64.go:113-133](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/bluepill_amd64.go#L113)). The fork instead keeps the Sentry on the host and puts only a tiny EL1 vector in the guest, so every non-fast-path syscall is a full `hv_vcpu_run` exit (~4 µs), the same ballpark as systrap rather than KVM ([SYSCALL-SPEEDUP.md](https://github.com/maci0/gvisor/blob/master/docs/SYSCALL-SPEEDUP.md)). Reproducing the KVM model on HVF is conceptually possible, since `hv_vcpu_run` is an ordinary blocking call, but it would run the Go darwin runtime *and libSystem* at guest EL1, and the real unknowns are not the ones first thought of. Pointer authentication is a non-issue: xnu sets `IMGPF_NOJOP` and disables user JOP for every non-arm64e image, Go emits plain arm64, and `_SCTLR_EL1_DEFAULT` enables no PAC keys, so the KVM comment about key synchronisation ([machine_arm64_unsafe.go:329-376](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine_arm64_unsafe.go#L329)) concerns the Linux vDSO's `paciasp` and has no macOS analogue (verify in Phase 0). `svc #0x80` from guest EL1 is the same trap-exit-re-execute path the KVM platform already uses for Sentry host syscalls. The genuine blockers are: the commpage at `_COMM_PAGE64_BASE_ADDRESS = 0x0000000FFFFFC000`, which libSystem reads on every `mach_absolute_time`/`clock_gettime` and which must be `hv_vm_map`-able or trapped; the register-transfer trampoline, because `hv_vcpu_run` returns with no signal frame, so the bluepill's `sigreturn`-based transfer must be hand-written assembly; the kick/preemption protocol; and the fact that each Sentry host syscall would pay a full exit plus register readout, the same class as today's HLT→`sigreturn` path ([xnu cpu_capabilities.h](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/arm/cpu_capabilities.h)). Phase 1 should adopt the fork's host-side model because it is proven to boot, and treat an in-guest Sentry as a Phase 3 spike whose *measurements* belong in Phase 0. Be clear-eyed about the host-side model's ceiling: the in-guest fast-path table can only answer syscalls that need no Sentry state (`getpid` family, `sched_yield`, time), so for everything that matters it is systrap-class, and the fork's `getpid` fast path is only correct for the init process.

**Decision 4: vCPU ownership and cross-vCPU maintenance.** This is the decision the fork did not make. Apple binds a vCPU to the pthread that created it: `hv_vcpu_create` "creates a vCPU instance for the current thread", `hv_vcpu_run` and `hv_vcpu_destroy` must be called by the owning thread, and only `hv_vcpus_exit` is cross-thread ([Apple vCPU management](https://developer.apple.com/documentation/hypervisor/vcpu-management)). The KVM platform relies on the opposite: `machine.Get()` looks up `vCPUsByTID[tid]` and, when the current thread has none, steals an idle vCPU from another thread and rebinds it (`delete(m.vCPUsByTID, origTID); m.vCPUsByTID[tid] = c`), capped at `runtime.NumCPU()` ([machine.go:595-689](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine.go#L595), [machine_arm64.go:236-247](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine_arm64.go#L236)). That works because a KVM vCPU fd can be `KVM_RUN` from any thread; HVF forbids it. Task goroutines migrate across Go Ms between `Switch` calls and Go routinely runs more Ms than CPUs (every blocking syscall can spawn one), so a one-vCPU-per-M scheme leaks vCPUs onto idle Ms and hits the cap, which is what the fork does and why it panics. Go also offers no way to run code on a specific idle M, so once a goroutine unlocks its thread nothing can later wake *that* thread to call `hv_vcpu_destroy`; any "destroy on the owner" protocol therefore requires a goroutine parked on the owning thread, which is a pool thread. That leaves two implementable shapes. **(i) A fixed pool of vCPU-owning locked threads** with a cross-thread hand-off per `Switch` of GPRs, PC/SP/PSTATE, `TPIDR_EL0` and the page-table root, costing one wake-up per syscall on top of the exit. FP/SIMD is the exception to "hand off only what changed": a vCPU's V0–V31/FPSR/FPCR belong to whichever task last ran on it, so the lazy `PullFullState` contract below spares only the *Sentry-side* copy; whenever the pool gives a vCPU to a different task the previous task's SIMD state must be saved and the new one's loaded (32 registers each way, ~1 µs batched at the fork's ~25 ns per register), or the stub must trap first FP use via `CPACR_EL1.FPEN` and load lazily, which is what ring0 does in-guest today (`storeEl0Fpstate`, FPSIMD trap toggle, `SaveFloatingPoint` on exit) except that under option (B) the trap is a full exit because the task's `fpu.State` is not guest-visible ([ring0/kernel_arm64.go:67-95](https://github.com/google/gvisor/blob/f51a205a8/pkg/ring0/kernel_arm64.go#L67), [kvm/context.go:106](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/context.go#L106)). FP transfer is avoided only when the same task re-acquires the same vCPU, which argues for task-to-vCPU affinity in the pool; the CPACR trap cost is a Phase 0 item. This is the plan, and it has an in-tree template: systrap's `Switch` already "sets up proper registers ... wakes up a stub thread by changing `sysmsg->stage` and calling `FUTEX_WAKE`, waits for a new stub event by polling `sysmsg->stage`" with an adaptive spin-versus-sleep controller (`fastPathState`) and a stub-side spinning queue, so the pool's hand-off cost has a known ceiling (systrap's own syscall overhead) and a ready design ([systrap.go:36-41](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/systrap/systrap.go#L36), [systrap/metrics.go:195-273](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/systrap/metrics.go#L195)). **(ii) Permanently locking task goroutines to vCPU threads**, which defeats the Go scheduler and caps *live* tasks (blocked tasks still hold their thread and vCPU) at the vCPU limit; acceptable only as the degenerate few-tasks case. `hv_vm_get_max_vcpu_count` is undocumented and the fork never calls it, so the cap on M1–M4, the create/destroy cost, what happens to a vCPU whose owning thread exits without `hv_vcpu_destroy` (Go terminates a thread whose locked goroutine exits), and the spin-then-futex hand-off latency on macOS are Phase 0 measurements.

The pool must also carry two cross-vCPU duties that the KVM platform performs from inside the guest. The first is `Context.Interrupt`: KVM's `vCPUReady/User/Guest/Waiter` state machine ([machine.go:783-855](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine.go#L783)) closes the race between a kick and guest entry, and whether an `hv_vcpus_exit` issued while the vCPU is *not* in `hv_vcpu_run` is sticky (next run returns `HV_EXIT_REASON_CANCELED`) is undocumented; if it is not, the bounce protocol has a lost-wakeup race that needs a user-space flag plus re-check. The second is **stage-1 TLB maintenance**. When the Sentry changes an application's page tables (munmap, mprotect, COW break), KVM flushes from guest EL1 with `tlbi vale1is`/`aside1is`/`vmalle1is` in `ring0.FlushTlbByVA/ByASID/All`, and `addressSpace.Invalidate()` interrupts every dirty context so each vCPU re-enters and flushes ([ring0/lib_arm64.s:23-52](https://github.com/google/gvisor/blob/f51a205a8/pkg/ring0/lib_arm64.s#L23), [kvm/address_space.go:87-91](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/address_space.go#L87)). A host-side Sentry at host EL0 cannot execute `tlbi` for the guest at all; HVF handles stage-2 changes (`hv_vm_unmap/protect`) but stage-1 belongs to the Sentry. Apple's `hv_vcpu_invalidate_tlb(vcpu, op, param)` would do it from the host, but its availability is macOS 27.0+ and it must be called by the owning thread ([Apple hv_vcpu_invalidate_tlb](https://developer.apple.com/documentation/hypervisor/hv_vcpu_invalidate_tlb(_:_:_:))). On macOS 15/26 the EL1 stub must therefore execute a TLBI mailbox (or a blanket `tlbi vmalle1is`) on every guest entry after a page-table change, and the pool must bounce every vCPU that has run the affected address space since the last invalidation so it re-enters through the stub before the Sentry considers the invalidation complete; KVM's `dirtySet` already computes exactly that set, so the mailbox protocol can reuse it rather than bounce every vCPU. The fork's "0x200 TLB fault handler" suggests it hit this. The per-entry cost and the cost of bounce-all-plus-TLBI per `munmap`/`mprotect` are Phase 0 measurements.

**Lazy register state.** `arch.Context64` carries 32×128-bit V registers plus FPSR/FPCR (0x210 bytes) and `TPIDR_EL0`; KVM saves FP lazily via CPACR trapping in ring0 and implements `PullFullState` as a no-op, while systrap already implements the lazy contract an HVF platform needs: `needToPullFullState` set on `Switch`, `saveFPState` only in `PullFullState`, which the kernel calls only before clone, signal delivery, checkpoint and ptrace ([fpu_arm64.go:24-25](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/arch/fpu/fpu_arm64.go#L24), [kvm/context.go:159-165](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/context.go#L159), [systrap/subprocess.go:927](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/systrap/subprocess.go#L927), [task_clone.go:123](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/kernel/task_clone.go#L123)). A host-side HVF `Switch` therefore needs only GPRs, PC/SP/PSTATE and `TPIDR_EL0` on the common path and can defer the 32 SIMD transfers; this is a larger lever than call batching and should be in the design from the start.

**Decision 3: 16 KiB everywhere versus a 4 KiB guest over a 16 KiB host.** Apple Silicon user space has 16 KiB pages (`PAGE_MAX_SHIFT 14`), `hv_vm_map` requires page-aligned host and guest addresses, and `kvm.go` already refuses to run when the host page size differs from `hostarch.PageSize` ([xnu vm_param.h](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/arm/vm_param.h), [Apple hv_vm_map](https://developer.apple.com/documentation/hypervisor/hv_vm_map(_:_:_:_:)), [kvm.go:81-83](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/kvm.go#L81)). `hostarch` already has a build-tag mechanism for 4K and 64K (`pagesize_64k`, wired through `.bazelrc:55-56`), and the 64K configuration runs in CI ([.buildkite/pipeline.yaml:446-451](https://github.com/google/gvisor/blob/f51a205a8/.buildkite/pipeline.yaml#L446)), so a `pagesize_16k` variant is mostly mechanical: `hostarch_arm64_16k.go` (with `HugePageShift` becoming 25, i.e. 32 MiB, which `mm` uses for alignment heuristics), `ring0/aarch64_16k.go`, `pagetables_arm64_16k.go` plus a new walker for the 4-level 16K geometry (`pteShift 14, pmdShift 25, pudShift 36, pgdShift 47`, 2-entry level-0 table), and a `_TCR_TG0_16K` case in `tcrTGFlags`, roughly 400 lines ([hostarch_arm64_64k.go:24-29](https://github.com/google/gvisor/blob/f51a205a8/pkg/hostarch/hostarch_arm64_64k.go#L24), [.bazelrc:55-56](https://github.com/google/gvisor/blob/f51a205a8/.bazelrc#L55), [kvm_const_arm64.go:114-119](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/kvm_const_arm64.go#L114)). One non-mechanical item hides in the guest vDSO: `vdso_arm64.lds` places `_params = VDSO_PRELINK - 0x1000` and `vdso/BUILD` links with `-z max-page-size=4096`, while the Sentry allocates a `hostarch.PageSize` parameter page immediately below the vDSO and writes `vdsoParams` at its start; with 16 KiB pages the vDSO's `adr _params` lands 12 KiB into the page, reads zeros, sees `ready == 0` and silently falls back to `sys_clock_gettime` on every call, so the linker script and BUILD must be parameterised by page size or the fast `clock_gettime` path is lost ([vdso/vdso_arm64.lds:37](https://github.com/google/gvisor/blob/f51a205a8/vdso/vdso_arm64.lds#L37), [vdso/BUILD:49](https://github.com/google/gvisor/blob/f51a205a8/vdso/BUILD#L49), [loader/vdso.go:216-290](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/loader/vdso.go#L216), [kernel/vdso.go:145-170](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/kernel/vdso.go#L145)). The cost of 16K-everywhere is that applications see 16 KiB pages and inherit the Android/Asahi compatibility profile (old jemalloc, 4K-aligned ELF `LOAD` segments, hardcoded 4096), most of which mainstream software fixed in 2022-2025 ([Asahi broken software](https://asahilinux.org/docs/sw/broken-software/), [Android 16 KB](https://developer.android.com/guide/practices/page-sizes)). The alternative is a 4 KiB guest view over a 16 KiB host. Under the host-side Sentry model the stage-1 granule is whatever the Sentry programs in `TCR_EL1.TG0`, M1 supports both 4K and 16K (no 64K), and every 4K-page Linux distribution has booted under QEMU-HVF and Virtualization.framework for years, so stage-1 4K is not an unknown; macOS 26's `hv_vm_config_set_ipa_granule(HV_IPA_GRANULE_4KB)` changes only the *stage-2* granule and is a separate, unmeasured performance trade ([M1 ID registers](https://gist.github.com/ryo/f533af313ac9dfd971f682b7ae951d63), [Apple hv_vm_config_set_ipa_granule](https://developer.apple.com/documentation/hypervisor/hv_vm_config_set_ipa_granule(_:_:))). The real cost of the split model is bookkeeping: `mincore` returns one byte per *host* page where `pgalloc` expects one per `hostarch.PageSize`, `decommitFile` cannot punch holes smaller than a host page, and `kvm.go:81`-style equality checks must become inequalities ([pgalloc_unsafe.go:29-31](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/pgalloc/pgalloc_unsafe.go#L29)). Go 16K-everywhere for Phase 1 because the symbolic path is proven, and revisit in Phase 2 against a measured compatibility need rather than an assumed one.

**The `hvf` platform itself.** It implements the ~20-method `platform.Platform`/`Context`/`AddressSpace` contract, whose only Linux leakage is `SeccompInfo()` (return empty rules), `hostmm.HostMemBarrier` (return `HaveGlobalMemoryBarrier()=false`) and `linux.SignalInfo` as the fault type (guest ABI, keep) ([platform.go:41-121](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/platform.go#L41), [platform.go:223-319](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/platform.go#L223)). What carries over depends on Decision 2. Under the chosen host-side model, `ring0` proper does **not** run: `ring0.CPU.SwitchToUser`, `kernelExitToEl0`, the `KernelSyscall`/`KernelException` hooks and `entry_arm64.s` all presuppose the Sentry's Go runtime executing at guest EL1 after `bluepill` ([machine_arm64_unsafe.go:430-433](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/machine_arm64_unsafe.go#L430)). Reusable: `ring0/pagetables` (walker, PTE bits, TTBR accessors), the PSTATE/ESR constants, `hostarch.ESRAccessType`, the ESR→`SignalInfo` decoding in `machine_arm64.go:202-233`, and the *structure* of the `kvm/testutil` harness. New: a position-independent EL1 vector stub (~100–300 lines of assembly) placed in guest memory that saves EL0 state, answers the fast-path table or executes `hvc #imm`, emulates EL0 `MRS` of ID registers, and executes pending stage-1 TLB invalidations from a mailbox on every guest entry (Decision 4). The `physical = virtual + offset` whole-address-space scheme of `physical_map.go` is reusable only if the in-guest model is pursued; under the host-side model it is replaced by an explicit host-VA→IPA registry ([physical_map.go:58-209](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/physical_map.go#L58)).

That registry is the second design decision Phase 1 must make. `AddressSpace.MapFile(addr, f memmap.File, ...)` accepts *any* `memmap.File`, and KVM implements it as `f.MapInternal` → host VA → `translateToPhysical` → `pageTables.Map`, which works only because the whole Sentry VA is guest-physical ([address_space.go:112-175](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/address_space.go#L112)). On the demo path this matters immediately: EROFS regular files are a `memmap.File` whose `MapInternal` returns slices of the Sentry's own `mmap` of the image, and the ELF loader maps busybox's `PT_LOAD` segments through it before the first instruction runs ([erofs/regular_file.go:261-271](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/fsimpl/erofs/regular_file.go#L261), [loader/elf.go:235-300](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/loader/elf.go#L235)). So either (A) keep KVM's whole-VA mapping (then `virtual_map.go` → `mach_vm_region_recurse` is needed, the behaviour of `hv_vm_map` on lazily-faulted anonymous ranges matters, and KVM's thin wrapper over `pagetables.RuntimeAllocator` in `bluepill_allocator.go` carries over minus its guest-mode requirement, since HVF stage-2 is hardware nested paging), or (B) map on demand: `MapFile` calls `hv_vm_map` for the backing region of each `memmap.File` (1 GiB `pgalloc` chunks are the easy case; EROFS images, `fsimpl/host` and later gofer host-FD mmaps are not), with overlap handling, and `pagetables` gets a guest-memory `Allocator` because PTE pages must live in IPA ([pagetables/allocator.go:20-36](https://github.com/google/gvisor/blob/f51a205a8/pkg/ring0/pagetables/allocator.go#L20), [pgalloc.go:223-224](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/pgalloc/pgalloc.go#L223)). The fork chose (B) with a 13 KB `ipa_allocator.go`. Three HVF facts constrain the registry. Hyperlight reports that `hv_vm_map` rejects read-only `MAP_SHARED` mappings, so file-backed regions had to use `MAP_PRIVATE`; the EROFS image is mapped `PROT_READ, MAP_SHARED` today and would need a darwin `MAP_PRIVATE` variant, and the same applies to later host-file mmaps ([Hyperlight PR 1681](https://github.com/hyperlight-dev/hyperlight/pull/1681), [erofs.go:254](https://github.com/google/gvisor/blob/f51a205a8/pkg/erofs/erofs.go#L254)). Pages mapped with `hv_vm_map` are **hypervisor-pinned**: libkrun found that "no madvise variant releases them", a reviewer on macOS 26.5 measured that `MADV_FREE_REUSABLE` marked pages reusable without reducing `phys_footprint`, and the only working release is `hv_vm_unmap` → `MADV_FREE_REUSABLE` → remap on the next guest data abort, a full exit ([libkrun PR 794](https://github.com/containers/libkrun/pull/794)). The exit handler must therefore distinguish a stage-2 data abort on an unmapped-but-allocated IPA (registry refault: `hv_vm_map` and resume, invisible to the application) from a stage-1 fault (an application `SIGSEGV`, delivered through the EL1 stub), using the ESR and the `physical_address` field of `hv_vcpu_exit_t`. For gVisor that means `pgalloc` decommit of any stage-2-mapped `MemoryFile` range must `hv_vm_unmap` first, `manuallyZero` zeroes without releasing, `F_PUNCHHOLE` on pinned pages is unverified, the registry must track unmapped-but-allocated ranges and remap on fault, and under option (A) every Sentry heap page the guest ever touched stays pinned until unmapped (the libkrun maintainers note that system-wide pressure does drop even where per-process figures do not, so the effect is accounting plus a remap cost rather than a hard leak). And the IPA space defaults to 36 bits (64 GiB) with a maximum of 39 bits before macOS 15 and 40 bits on macOS 15+ where the hardware allows, so Phase 1 should call `hv_vm_config_set_ipa_size(40)` as the fork does ([QEMU commit d54ffa54](https://gitlab.com/qemu-project/qemu/-/commit/d54ffa54)). Guest RAM backing is a trade-off, not a given: `hv_vm_allocate` avoids pages being double-counted in `phys_footprint` (an accepted forum answer, not an Apple statement) but yields a VA with no file descriptor, so `F_PUNCHHOLE`, `SEEK_DATA/HOLE` for save/restore and multiple mappings are unavailable; Phase 1 should keep `pgalloc`'s file-backed design (`shm_open` or unlinked file + `ftruncate` + `mmap(MAP_SHARED)`) and treat the double count as cosmetic ([Apple forums 851651](https://developer.apple.com/forums/thread/851651)).

Rewritten rather than ported: the 1,165 lines of arm64-relevant `bluepill*` and 761 lines of `machine_arm64*.go` (the KVM platform is 3,921 shared + 1,891 arm64-only lines) become a vCPU loop on vCPU-owning threads per Decision 4; `tgkill`+futex bounce becomes `hv_vcpus_exit` → `HV_EXIT_REASON_CANCELED`; the hypercall uses `hvc #imm` (`imm != 0`) rather than the KVM MMIO trick; `KVM_SET_USER_MEMORY_REGION` slots become `hv_vm_map` calls with no documented slot cap, which removes the `faultBlockSize`/`usedSlots` machinery ([bluepill_fault.go:26-123](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/platform/kvm/bluepill_fault.go#L26)). Estimated size: 5–7k lines, derived from the KVM shared code that survives plus bindings, stub, IPA registry and vCPU pool, and in line with libkrun's ~2,400-line macOS layer plus wrapper ([vadika KVM→HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html)).

**Host-primitive ports and the launcher.** The non-platform surface is ~1.5–2.5k lines: `fdnotifier` on `kqueue` (~400), `rawfile`/`eventfd` (~200), `hostfd` on `pread/pwrite/preadv/pwritev` (~150), `memutil.CreateMemFD` on `shm_open` or an unlinked file (~30), `pgalloc` decommit via the existing `manuallyZero` fallback, a real `sighandling_darwin.go` and a darwin `safecopy` handler (~300), `cpuid`/`hostcpu`/`hostos` on `sysctl` (~100), a `sentry/time` sampler on `clock_gettime` (~100 plus asm), `TCGETS` → `TIOCGETA` if a TTY is wanted (~50), and no-op stubs for `seccomp`, `pinring`, `aio`, `coretag`, `hostmm`. The launcher is a darwin `runsc/sandbox.createSandboxProcess` that `exec`s the boot binary with no `Cloneflags`, `Credential`, uid maps, chroot, `prctl` or `CallSelfAsNobody`, with `DisableSeccomp` forced under `GOOS=darwin`, run as `--ignore-cgroups --network=none --TESTONLY-unsafe-nonroot`. The rootfs is an EROFS image built on Linux with `mkfs.erofs` (optionally `overlay=memory` as `runsc do --erofs` already supports), opened goferless, with `/dev` from `devtmpfs`+`memdev`+`ttydev` and stdout captured through an imported host pipe FD to defer TTY ioctls ([runsc/cmd/do.go:202-205](https://github.com/google/gvisor/blob/f51a205a8/runsc/cmd/do.go#L202), [runsc/boot/vfs.go:117-162](https://github.com/google/gvisor/blob/f51a205a8/runsc/boot/vfs.go#L117)). `dmesg` works the moment the syscall table is reachable.

The total is on the order of **8–12k new or changed lines**. Translating that into calendar time is an estimate rather than a sourced fact: the fork went from a work-in-progress post (2026-04-17) to "It's mostly working now" (2026-05-04) in about 2.5 weeks of one person's effort, and Carrick's author produced 1,473 commits in 20 days with AI coding agents, but neither produced upstream-quality code, and the fork's shortcuts (polling futexes, disabled flipcall, `SEQPACKET` → `STREAM`) are exactly what a reviewable PR must avoid ([google/gvisor#1270](https://github.com/google/gvisor/issues/1270), [Carrick blog](https://carrick-website.pages.dev/blog/introducing-carrick)). A reasonable planning figure for a contributor who knows `kvm` and `ring0` is **2–4 engineer-months of engineering effort** for the demo, preceded by a 2-week spike on the items below that no documentation answers. Calendar time to a *merged* Phase 1 is longer, plausibly **4–8 months**, because "reviewable" adds a darwin Bazel toolchain with codesign in the test runner, a self-hosted Mac runner, the vCPU-ownership design, EL0 `MRS` emulation, 16K syscall-test triage, and gVisor's multi-round review of a new platform.

## Phase 2 onward: parity is gated by filesystem, networking, latency, security and amd64

Once a static binary runs, the increments order themselves by what users touch first and by how much of the Linux host contract each one replaces.

**Host filesystem (first increment; ~3–5k lines).** The gofer and directfs are the only way to see real host directories, and both are a Linux-syscall emulation project: `statx` → `fstat`, `openat2(RESOLVE_NO_SYMLINKS)` → component-wise `openat`, `O_PATH` → `O_RDONLY|O_NONBLOCK` or `O_SYMLINK`, `AT_EMPTY_PATH` → `fcntl(F_GETPATH)`, `getdents64` → `getdirentries`, `renameat2` → `rename`, `fallocate` → `F_PREALLOCATE`, `f*xattr` → the darwin variants with an options argument, and a replacement for `fdchannel`'s `SOCK_SEQPACKET` socketpair (used for flipcall FD donation), since macOS AF_UNIX offers only `SOCK_STREAM` and `SOCK_DGRAM`; lisafs itself already runs over `SOCK_STREAM` with length-prefixed framing, so the fork's `SEQPACKET → STREAM` shortcut only ever concerned `fdchannel` ([container.go:1641-1642](https://github.com/google/gvisor/blob/f51a205a8/runsc/container/container.go#L1641), [lisafs/sock.go:180-205](https://github.com/google/gvisor/blob/f51a205a8/pkg/lisafs/sock.go#L180), [fdchannel_unsafe.go:36](https://github.com/google/gvisor/blob/f51a205a8/pkg/fdchannel/fdchannel_unsafe.go#L36), [runsc/gofer/fs](https://github.com/google/gvisor/blob/f51a205a8/runsc/gofer/fs), [directfs_inode.go](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/fsimpl/gofer/directfs_inode.go), [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)). The fork's 917-line `directfs_inode_darwin.go` is a useful map of the surface ([maci0/gvisor hvf](https://github.com/maci0/gvisor/tree/master/pkg/sentry/platform/hvf)). The `pkg/lisafs` transport is portable (`AF_UNIX` + `SCM_RIGHTS`), but it drags in `flipcall` (futex) and `fdchannel`; `flipcall` can run on `os_sync_wait_on_address` (macOS 14.4+) or be disabled at a latency cost ([pkg/unet/unet.go:43-51](https://github.com/google/gvisor/blob/f51a205a8/pkg/unet/unet.go#L43)). A separate gofer *process* is also the first step toward restoring a security boundary that Phase 1 lacks. Two macOS-specific behaviours affect the gofer: TCC prompts the user (per terminal application) the first time a process touches `~/Desktop`, `~/Documents` or `~/Downloads` and returns `EPERM` on denial, and read-only `MAP_SHARED` file mappings may be rejected by `hv_vm_map` (see the IPA registry discussion above), which decides whether host files can be mapped into the guest or must be copied.

**Networking (~2–3k lines).** Netstack compiles for darwin today; what is missing is a darwin `stack.LinkEndpoint` and a replacement for `runsc/sandbox/network.go`. The three host options each have a catch: `utun` gives an L3 TUN but needs root; `vmnet` gives L2 but needs the Apple-restricted `com.apple.vm.networking` entitlement or root; a gvproxy/passt-style userspace NAT over a Unix socket is the only unprivileged option, and is what krunkit, Carrick and the fork default to ([Apple vmnet](https://developer.apple.com/documentation/vmnet), [vmnet crate README](https://docs.rs/crate/vmnet/latest/source/README.md), [README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md)). Interface enumeration moves from netlink to `getifaddrs`/`PF_ROUTE`. `hostinet` should stay Linux-only.

**Interactive use.** `devpts`, `TIOCGETA`-based TTY detection in `fsimpl/host`, signal forwarding (portable through `os/signal`), and a `runsc do`-style entry point. Note that the OCI/containerd integration has no natural consumer on macOS (Docker Desktop and Apple `container` are VM-based), so the realistic user-facing surface is a `runsc do`-like CLI or `sandboxexec`, which today is a thin client that shells out to `runsc` and inherits every host requirement ([sandboxexec/sandbox.go:341-353](https://github.com/google/gvisor/blob/f51a205a8/sandboxexec/sandbox/sandbox.go#L341)).

**Performance (the long pole).** The fork's numbers set the only available baseline, and they need labelling: they are self-reported, instrumented with `time.Now()` around cgo calls on one M4 Pro running macOS 26.4 (the doc notes that pprof's SIGPROF "interferes with HVF vCPU execution"), and internally inconsistent (the same document quotes an HVF exit at "~7-8 µs" elsewhere); no independent measurement exists. With that caveat: non-fast-path syscalls ~4 µs, of which `hv_vcpu_run` ~3 µs, against ~100 ns on KVM, a "100x overhead" that made syscall-heavy loops "~1600x slower than native" before fast paths, fork+exec ~1.9 ms, memory bandwidth ~1.3× native ([SYSCALL-SPEEDUP.md](https://github.com/maci0/gvisor/blob/master/docs/SYSCALL-SPEEDUP.md)). The honest comparison is not HVF-exit versus KVM-in-guest but HVF-exit versus KVM's own user-space exit round trip, which is also microseconds; KVM's ~100 ns is a consequence of the in-guest Sentry design, not of the hypervisor, which is why the Phase 0 probe should run the same C measurement under KVM on an arm64 Linux box. Remedies in rising order of ambition: the lazy FP/SIMD contract and batched register traffic per exit; extend the in-guest EL1 fast-path table within its low ceiling (only state-free syscalls qualify, and the fork's `getpid` fast path is only correct for the init process) ([hvf_platform.md](https://github.com/maci0/gvisor/blob/master/g3doc/architecture_guide/macos/hvf_platform.md)); and finally the spike on running the Sentry at guest EL1 to recover KVM's model, which is the only route to ~100 ns syscalls and carries the commpage, trampoline and kick-protocol unknowns above. A C or Rust EL1 mini-kernel for "hot" syscalls is not a worthwhile intermediate: every non-trivial syscall needs Sentry state that lives in Go heap objects. Apple's `hv_vcpu_get_exec_time` is available for instrumenting exits ([Apple vCPU management](https://developer.apple.com/documentation/hypervisor/vcpu-management)). Timekeeping can use `CNTVCT_EL0` directly (the fork reports ~5 ns VDSO `clock_gettime`), but note that `mach_timebase_info` is 125/3 on M1 and M2 (a 24 MHz counter, ~42 ns ticks; later chips unverified) and that xnu can present a 1 GHz timebase per task (`uses_1ghz_timebase`), so the guest must derive its counter frequency from `CNTFRQ_EL0` or calibration rather than from `mach_timebase_info`, and `membarrier`/`ioeventfd` optimisations are simply absent.

**Security posture.** On macOS the Sentry runs with neither seccomp nor, in Phase 1, a separate gofer. The VM boundary still isolates the application from the Sentry, but the Sentry-to-host boundary loses the layer `SECURITY.md` describes; the available substitute is a Seatbelt (`sandbox_init`) profile plus a separate uid, as libkrun's porting analysis suggests, and none of the comparable projects (Noah, Carrick, Solo5's HVF fork) provides any such layer ([vadika KVM→HVF map](https://vadika.github.io/ignition/internals/hvf-firecracker-map.html), [mirage-hello](https://next.tangled.org/tsiry-sandratraina.com/mirage-hello)). A written security-posture statement therefore belongs in Phase 1's exit criteria (so that the demo is never mistaken for a sandbox), with the Seatbelt profile and gofer separation as Phase 2 deliverables and a threat-model review before anyone calls macOS a supported platform.

**4 KiB application pages.** The fork's HotSpot failure ("AArch64 assembler assuming 4K page alignment") occurred under its *split* model, is undiagnosed, and is weak evidence of anything: HotSpot sizes by `os::vm_page_size()`, has run on 64K-page aarch64 distributions for years, and OpenJDK is not on Asahi's 16K broken-software list ([README-MACOS.md](https://github.com/maci0/gvisor/blob/master/README-MACOS.md), [Asahi broken software](https://asahilinux.org/docs/sw/broken-software/)). The right order is to test HotSpot, Chromium-era binaries and old jemalloc under 16K-everywhere first, and only then decide whether a 4K guest view (stage-1 4K over a 16K IPA granule, possible on any macOS at the price of 16K-granular host bookkeeping, or stage-2 4K via `HV_IPA_GRANULE_4KB` on macOS 26 at an unmeasured performance cost) is a compatibility increment worth building ([M1 ID registers](https://gist.github.com/ryo/f533af313ac9dfd971f682b7ae951d63)).

**Checkpoint/restore.** `pgalloc/save_restore.go` (2,257 lines) relies on `SEEK_DATA/SEEK_HOLE`, `Fstatfs` and sparse `MAP_SHARED` images; hole punching maps to `fcntl(F_PUNCHHOLE)`, which is documented for files on supporting filesystems but unverified for POSIX shm objects and must be preceded by `hv_vm_unmap` on stage-2-mapped ranges because those pages are hypervisor-pinned (see the IPA registry discussion), and `MADV_DONTNEED` on macOS does not discard contents (pages stay resident until pressure; `MADV_FREE_REUSABLE` is the real discard), so a port must not rely on madvise zero-fill ([save_restore.go:606-633](https://github.com/google/gvisor/blob/f51a205a8/pkg/sentry/pgalloc/save_restore.go#L606), [fcntl(2)](https://keith.github.io/xcode-man-pages/fcntl.2.html), [libkrun PR 703](https://github.com/containers/libkrun/pull/703)).

**amd64 images.** Rosetta for Linux is delivered only as a Virtualization.framework directory share, checks for a VZ host via undocumented virtio-fs ioctls and a challenge-response exchange, and libkrun removed its Rosetta spoofing ("macos: drop Rosetta support", reason not publicly documented); a third-party analysis rates the DMCA §1201 risk of such spoofing "Critical" ([Apple VZLinuxRosettaDirectoryShare](https://developer.apple.com/documentation/virtualization/vzlinuxrosettadirectoryshare), [tnk4on libkrun-rosetta](https://tnk4on.github.io/libkrun-rosetta/)). The only options are FEX-Emu or Box64 inside the sandbox (the same analysis quotes 40–70% of native from the projects' own READMEs, not from measurements; the fork's FEX attempt is blocked on a COW fault loop) or delegating amd64 images to a Virtualization.framework Linux VM ([FEX-EMU.md](https://github.com/maci0/gvisor/blob/master/docs/FEX-EMU.md)).

**CI and release.** GitHub's arm64 macOS runners are 3-core M1 VMs where "Nested-virtualization is not supported", so HVF calls fail with `HV_UNSUPPORTED`; hosted jobs can build darwin/arm64 and run non-HVF unit tests, but platform tests need bare-metal Macs such as EC2 Mac Dedicated Hosts (24-hour minimum) or self-hosted Mac minis ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [actions/runner-images#9254](https://github.com/actions/runner-images/issues/9254), [AWS EC2 Mac](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-mac-instances.html)). Release tooling needs a darwin/arm64 build plus the ad-hoc codesign step (which a cgo-free build can do from Linux with `rcodesign`), and downstream repackagers must preserve it: any re-sign must re-apply the entitlements plist, since `codesign` drops entitlements that are not re-supplied, which is the simplest reading of what bit pkgx/brewkit for Lima; ad-hoc signing is known-good, and Developer ID signing should be verified before relying on it ([pkgxdev/brewkit#353](https://github.com/pkgxdev/brewkit/pull/353), [lima Makefile](https://github.com/lima-vm/lima/blob/master/Makefile)). Ad-hoc-signed binaries cannot be notarized, so a tarball downloaded through a browser carries the quarantine attribute and Gatekeeper blocks it; Homebrew and `curl` paths avoid this and should be the documented install route.

The recommended plan has five phases with a design gate between the first two. **Phase 0 (2 weeks, one engineer, one M-series Mac):** write a C probe (not Go, so that the numbers are free of cgo and scheduler noise) against HVF that measures, on M1–M4: `hv_vcpu_run` round-trip latency with clean and dirty FP state, and the same measurement under KVM on an arm64 Linux box for a like-for-like user-space-exit comparison; `hv_vm_get_max_vcpu_count`, `hv_vcpu_create`/`destroy` cost, and what happens to a vCPU whose owning thread exits without `hv_vcpu_destroy`; `hv_vcpus_exit` semantics (sticky when issued before `hv_vcpu_run`? PC/FP preserved on `CANCELED`?); that a blocked pending signal (SIGURG) does not make `hv_vcpu_run` return an error; `hv_vm_map` of read-only and read-write `MAP_SHARED` file-backed ranges and of anonymous Go-heap ranges; `F_PUNCHHOLE` and `MADV_FREE_REUSABLE` on pages that are currently stage-2-mapped, and the cost of the `hv_vm_unmap` → release → refault-remap cycle per decommit; the cost of bouncing every vCPU and executing a TLBI on re-entry per `munmap`/`mprotect`; the latency of a systrap-style spin-then-futex hand-off between threads on macOS (for the Decision 4 pool); and, as cheap sanity checks rather than unknowns, `TCR_EL1.TG0=4K` and `=16K` from a cold vCPU and `hv_vm_config_get_max_ipa_size`. In parallel, stand up a darwin Bazel build (or the `go` branch flow) and post a design sketch on #1270 inviting the fork's author. **Design gate:** a short design doc on #1270 covering Decision 4 (the vCPU pool with systrap's hand-off as template, kick protocol, and stage-1 TLB maintenance), the IPA mapping scheme (A or B) including pinned-page decommit, lazy register state, the cgo-free binding, and the Phase 0 numbers; no platform code lands before maintainers have seen it. **Phase 1 (2–4 engineer-months, 4–8 months calendar to merge):** the demo as specified above, landed as `pkg/sentry/platform/hvf` plus an in-tree `pkg/hvf` binding, a `pagesize_16k` variant including the vDSO linker-script change, darwin files for the ~12 leaf packages, EL0 ID-register `MRS` emulation in the EL1 stub, a darwin launcher, an HVF twin of the `kvm_test.go` harness, and a written security-posture statement; the exit criterion is static busybox `echo hello` and `dmesg` from an EROFS root with syscall tests runnable on a self-hosted Mac. **Phase 2 (3–6 months):** host filesystem via a darwin gofer process plus directfs emulation, userspace-proxy networking with a darwin link endpoint, devpts/TTY, a Seatbelt profile, and a 4K guest-page mode only if 16K testing of real binaries shows the need; exit criterion is an interactive Alpine shell with package installation, the bar the fork already claims. **Phase 3 (open-ended):** performance, starting with the lazy-FP contract and register batching, then a larger in-guest fast-path table within its ceiling, then the in-guest Sentry spike, with every change gated on A/B benchmarks per the project's performance policy. **Phase 4:** checkpoint/restore, FEX-based amd64, release signing (`rcodesign` from Linux) and Homebrew packaging, and a documented support statement.

## Conclusion

The question "can gVisor sandbox applications natively on macOS" is no longer open; the fork answers it, and Apple's API happens to match the slice of KVM that gVisor depends on. What the notes change is where the difficulty sits. The platform rewrite is the largest line count but not the most uncertain part: `pagetables`, the fault decoding and the test-harness structure carry over, the signal-frame bluepill disappears when `hv_vcpu_run` is an ordinary function call, and the HVF API is close to the KVM subset gVisor uses. The hard, lasting costs are architectural: HVF's vCPU-to-thread binding, which the KVM platform's design actively violates and which the fork never solved, together with the host-side Sentry's inability to flush guest TLBs or release guest-mapped pages without a hypervisor round trip; a 16 KiB host page that forces either a new page-size variant or a split model; a host-side Sentry whose every real syscall is a hypervisor exit, putting the platform in systrap's performance class unless the Sentry itself moves into the guest; and a host with no seccomp, which turns gVisor's two-layer defence into one. A native port therefore makes most sense framed as the CNCF post frames it, a Wine-like developer tool for running and sandboxing Linux binaries on a Mac, rather than as a drop-in for the Linux VM route that already serves container workloads on macOS.

The strategic implication for a contributor is to spend the first two weeks on measurements rather than code. The facts no document provides (exit latency against a KVM calibration, `hv_vcpus_exit` kick semantics, the vCPU cap and lifecycle cost, and what `hv_vm_map` accepts) decide between a vCPU pool and lock-for-lifetime, between whole-VA and on-demand IPA mapping, between the fork's host-side Sentry and a KVM-style in-guest Sentry, and ultimately whether the result is a curiosity or a platform worth maintaining. With those answers in hand, Phase 1 is a well-bounded 8–12k-line project with an existing fork as a map and test oracle, an issue with seven years of accumulated demand, and a project roadmap that now explicitly asks for it.
